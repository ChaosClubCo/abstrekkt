I replaced my entire backend with one API call

No Express server. No auth middleware. No deploy pipeline. Just a browser, a single fetch, and an mcp_servers array. Here's the pattern, the code, and an honest account of where it holds and where it doesn't.

Kyle Rosebrook FlashFusion Tested in production

Most internal tools die before they ship. Not from complexity — from the overhead that comes before the first useful line of code. You need a server. That server needs to run somewhere. It needs auth so it isn't open to the internet. It needs environment variables managed. It needs to stay up. It needs to be updated when the API it calls changes.

For a one-person consultancy or an internal admin panel, that overhead is often larger than the tool itself. So the tool doesn't get built, or it gets built halfway and left running on someone's laptop.

I was building a companion panel for a 152-entity Base44 database — an activity library browser, an event calendar, a record editor. Standard stuff. The canonical B44 app handles auth, RLS, and the full data model. I just needed a faster UI surface for admin work. The usual path is: stand up a small API server, wire in the B44 SDK, deploy it somewhere, add credentials.

I didn't do any of that.

The backend is a system prompt. The API server is the Anthropic API. The database client is the MCP connection it picks up at call time.

The pattern

The Anthropic /v1/messages endpoint accepts an optional mcp_servers array. Pass a Base44 MCP URL there and the model that processes your request gets live MCP tool access — it can query entities, create records, update fields, delete rows. The model returns results as text. Your client-side JavaScript parses it.

No server. No deploy. The entire backend is one helper function:

The complete data layer JavaScript 
const APP_ID = 'your-b44-app-id';
const B44_MCP = 'https://app.base44.com/mcp';
const MODEL   = 'claude-sonnet-4-20250514';

async function b44(systemPrompt, userPrompt) {
  const res = await fetch('https://api.anthropic.com/v1/messages', {
    method: 'POST',
    headers: { 'Content-Type': 'application/json' },
    body: JSON.stringify({
      model: MODEL,
      max_tokens: 4000,
      mcp_servers: [{ type: 'url', url: B44_MCP, name: 'base44' }],
      system: systemPrompt,
      messages: [{ role: 'user', content: userPrompt }]
    })
  });

  if (!res.ok) throw new Error(`API ${res.status}`);

  const data = await res.json();

  // Content blocks may include tool_use / tool_result plumbing.
  // Filter for text only — that's where the data lives.
  const text = data.content
    .filter(b => b.type === 'text')
    .map(b => b.text)
    .join('');

  // Strip ```json fences even when instructed not to include them.
  return text.replace(/```json\n?|```\n?/g, '').trim();
}

That's the complete data layer. Every read, write, update, and delete in the companion runs through that one function. The caller passes a system prompt with the task specification and a short user prompt with the intent. The model executes against the live database and returns JSON. The outer JavaScript handles the UI.

What it looks like in practice

A read query looks like this:

Loading a list of records JavaScript 
async function loadActivities() {
  const raw = await b44(
    /* system — the task spec */
    `You have Base44 MCP access. App ID: ${APP_ID}.
Query ALL records from the Activity entity.
Return ONLY a JSON array. Fields per item: id, title,
description, type, duration, capacity, is_template.
Return [] if no records. No explanation, no markdown.`,
    /* user — the trigger */
    'Load all activities.'
  );
  return JSON.parse(raw);
}

A write looks nearly identical — the system prompt specifies the entity, the operation, and the expected return format. The data flows in through the user prompt as a JSON string. The model creates or updates the record and returns a confirmation object.

System prompt discipline

The system prompt is load-bearing. It must declare MCP access and the App ID explicitly, name every field you need, and end with a hard instruction to return empty arrays instead of prose on null results. The model has no session context between calls — treat each one as a cold start.

What actually holds

I ran this pattern against a production database for several weeks of active internal use before writing this. The honest results:

Verdict — tested under load
List queries, filtered queries, single-record reads
HOLDS — Reliable, fast enough for human interaction speeds, parse errors rare when prompt discipline is maintained
Create and update operations
HOLDS — Works cleanly; return format discipline matters more on writes than reads
Large unbounded queries
BREAKS — max_tokens: 4000 truncates silently on big result sets. Always pass limit: N in the system prompt.
High-frequency interactions, auto-refresh
BREAKS — Each UI action is a full API call. Rate limits surface fast. Debounce everything; no polling loops.
Multi-tenant apps with per-user RLS
NOT FOR THIS — No user session context is passed to B44. RLS does not fire per-user. This is a single-user pattern.
Real-time collaboration, presence, live updates
NOT FOR THIS — Each call is discrete. Polling is prohibitive. Use a websocket layer for anything live.

When to use it

This pattern is not a backend replacement for production apps. It's a backend replacement for the class of internal tools that would otherwise never exist — the admin panel that lives in a Google Doc, the data browser that's currently a manual B44 query, the companion UI that a single person needs and nobody has time to build a server for.

If you're a solo operator or a small team and you need a live data UI in under two hours, this is the fastest path I've found that doesn't involve mocking data or faking persistence.

The pattern is also worth understanding even if you never use it directly. It demonstrates something broader: the distinction between "I need a backend" and "I need data to move between two places" is collapsing. The infrastructure layer that used to sit between your UI and your database is increasingly optional for a meaningful class of use cases. That shift has real implications for how you scope internal tooling, and for how you evaluate what actually needs a server versus what just assumed it did.

The portability note

The b44() function above has no app-specific logic. Swap the APP_ID constant and the pattern works against any Base44 app. I'm running the same function across three different B44 databases — different schemas, different entity names, same helper, same parsing logic.

If you're building on Base44 and you've been putting off a companion tool because the backend overhead felt like too much for what you needed — this is the spec. Copy the function, wire your entity names into the system prompt, and build the UI you actually want.
