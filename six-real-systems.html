05
Lane Sprint Focus
One declared sprint at a time. Everything else accumulates passively. Agent's job is gatekeeper — recognize "not sprint-relevant" and route to the right lane without forcing a context switch.
LIGHT AI MANY PARALLEL LOW COST
  1. Define the sprint contract before anything else

    One sprint, one outcome, hard boundary. Write it as a single sentence with a verifiable end-state. "Three.js showcase scene 03 deployed to chaosclub.com with Cloudflare proxy live" is a sprint. "Work on the Three.js thing" is not.

    Sprint declaration template
    # sprint.yaml — single source of truth name: "Three.js Scene 03 — Cloudflare Path A" start: 2026-04-26 end: 2026-05-10 # 14 days, hard stop done_when: "chaosclub.com/scene-03 returns 200, Worker proxy logs requests, no client-side API key exposed" non_goals: - "Scene 04 work" - "Refactoring shared geometry helpers" - "FlashFusion anything"
  2. Build the router as the smallest Claude call you can

    The router doesn't need to be smart. It needs to be fast and decisive. Single Claude call, four possible outputs.

    Router system prompt
    You are a sprint gatekeeper. The active sprint is: {{sprint.name}} — done_when: {{sprint.done_when}} For each incoming item, return JSON: { "verdict": "sprint" | "lane:<name>" | "trash" | "decide", "one_line_why": "<15 words max>" } Active lanes: flashfusion, chaosclub, intinc-l1, writing, personal-ops "decide" only if you genuinely can't tell — bias toward routing.
  3. Wire the inbox surface to one capture point

    Pick one. Notion DB, a single Things inbox, or a plain markdown file watched by n8n. Multiple inboxes defeat the system because the router can't see what it's not pointed at.

    For your stack, a single Notion DB called /inbox with a status column the router writes to is the lowest-friction path. n8n's Notion node handles it natively.
  4. Run the Friday accountability check on real data

    The agent's most useful weekly output is "did sprint hours actually go to sprint work?" — answered with calendar + commit + PR data, not your memory.

    Friday review prompt (n8n schedule node, Friday 5pm)
    Pull and pass to Claude: - calendar events 2026-04-26 → today, with durations - git commits across {{repos}} in same window - inbox routing log: counts by verdict Ask: "Did this week's deep-work hours move {{sprint.done_when}} closer? Score 0–100. Cite the 3 data points that drove the score. Name the one thing to change Monday."
  5. Track adherence as a single number over time

    Weekly score → simple line chart. The trend matters more than any single week. If three consecutive weeks dip below 60, the sprint declaration was wrong (too vague, too big, or you don't actually want to do it).

    A perfect adherence score against a fake sprint is worse than a 50% score against a real one. The router is honest only if you are.
  6. End-of-sprint shutdown ritual

    Last day of sprint, agent runs a closing pass: what shipped (matches done_when?), what's open in the lanes (what accumulated?), what's the next sprint candidate (top 3 from accumulators by recency × signal). 30-minute human review, declare next sprint, repeat.

  7. Audit log every routing decision

    Cheap insurance. Every router output goes to an append-only log with timestamp, item text, verdict, one_line_why. When you're 6 weeks in and wondering why X never got worked on, the log tells you whether the router routed it wrong or you ignored it.

    Append to a Supabase table — your stack already runs Supabase for the drive automation. One more table costs nothing and you get free SQL queries on six months of routing decisions.
06
Delegate – Review – Own
Agents do first-pass execution. Humans review for correctness, risk, and alignment. Architecture and outcomes stay human. The 2026 operating model that engineering orgs are actually converging on.
HEAVY AI ONE FOCUSED MED COST
  1. Spec doc as the only artifact you must hand-author

    Everything downstream is delegable; the spec is not. It's the contract the agent fulfills and the rubric the human reviews against. Treat the spec as the work — the typing was always the easy part.

    Minimum-viable spec template
    # SPEC — <feature/component name> ## Context What system is this changing? What's the user-visible behavior? ## Requirements - Functional: bullet list, testable - Non-functional: perf, security, accessibility - Out of scope: explicit list (prevents agent scope-creep) ## Interface Inputs, outputs, error modes. API shape if applicable. ## Acceptance - Tests that must pass - Manual checks - Rollback plan
  2. First-pass contract — what the agent ships in one go

    Define the artifact bundle the agent produces: code, tests, docs, commit message, brief PR description. If you have to ask for missing pieces after the fact, the contract is too loose.

    First-pass deliverable bundle
    [ ] Implementation code (matches spec interface) [ ] Unit tests (cover spec acceptance items) [ ] Updated README / API doc if interface changed [ ] Commit message in conventional-commits format [ ] PR description: "what changed, why, risk surface" [ ] Self-review note: agent's own list of concerns
  3. Run it without intervening — let it finish

    The strongest discipline in this system is not editing during the run. Hand-edits while the agent works produce a hybrid artifact nobody can review cleanly. Let the agent ship, then review.

    If you're tempted to intervene, that's signal the spec was incomplete. Stop, kill the run, fix the spec, restart. Don't patch in flight.
  4. Structured review pass, not vibes

    Same checklist every time. The review is the work; speed comes from repetition, not skipping steps.

    Review checklist
    CORRECTNESS [ ] Implementation matches spec interface [ ] Tests cover all acceptance items [ ] Tests actually run and pass SECURITY [ ] No secrets in code or git history [ ] Input validation at trust boundaries [ ] Auth/authz unchanged or correctly modified [ ] No new attack surface unless spec required it ARCHITECTURE [ ] Fits existing patterns or has explicit deviation note [ ] Doesn't import disallowed deps [ ] No dead code, no commented-out blocks BLAST RADIUS [ ] What breaks if this PR is wrong? [ ] Is rollback automatic or manual? [ ] Monitoring/alerting in place?
  5. Own the merge — no rubber-stamping

    The signature on the merge button is yours. If you couldn't defend the change in a post-mortem, you don't merge it. Period. This is the line that separates Delegate-Review-Own from "AI generates code and hopes."

    For Base44 platforms with SOC2 / multi-tenancy concerns, add a second-pair-of-eyes step before merge to main. Even if it's just async — another reviewer, even another Claude session with a fresh context, catches what tunnel vision misses.
  6. Audit trail as a non-negotiable

    Every agent run logs: spec hash, agent version, prompts, tool calls, output bundle, reviewer, merge decision. Six months later when something breaks in prod, you need to be able to reconstruct what was generated and what was reviewed.

    Minimum audit record
    { "run_id": "<uuid>", "timestamp": "<iso8601>", "spec_hash": "<sha256 of spec doc>", "agent": { "model": "...", "tools": [...] }, "prompts": [...], "tool_calls": [...], "output": { "files_changed": [...], "tests_run": [...] }, "review": { "reviewer": "...", "checklist": {...}, "verdict": "merged|rejected|revised" } }
  7. Promote the spec → arch → review pipeline as the team motion

    Once the loop works for you, it scales horizontally. New contributor onboarding becomes "here's how to write a spec, here's the review checklist." Compounds because the spec quality improves with reps and the checklist catches the same five mistakes everyone makes the first time.

07
WSJF Backlog Triage
Weighted Shortest Job First scoring on every backlog item. Agent does the math, surfaces the top three weekly. Removes "what should I do next" as a daily decision.
MEDIUM AI MANY PARALLEL MED COST
  1. Define the rubric before scoring anything

    The rubric IS the strategy. Score on four dimensions, Fibonacci scale (1, 2, 3, 5, 8). The numbers are visible math; the definitions are doing the work.

    WSJF rubric — adjust to your context
    USER_VALUE — does this matter to a real user/customer/audience? 1: nice-to-have, no one will notice 3: improves an active workflow 5: removes a recurring pain 8: enables a new capability that didn't exist TIME_CRITICALITY — does waiting cost you? 1: no decay, can ship anytime 3: opportunity narrows over months 5: there's a date in the next 4 weeks 8: window closes inside 2 weeks RISK_REDUCTION — does this prevent worse outcomes? 1: nothing prevented 3: reduces a known annoyance 5: prevents a likely future problem 8: prevents a security/data/reputation incident JOB_SIZE — your honest effort estimate 1: half a day 3: 2–3 days 5: a week 8: multi-week build WSJF = (USER_VALUE + TIME_CRITICALITY + RISK_REDUCTION) / JOB_SIZE
  2. Make the backlog one list, source-of-truth

    Linear, Notion DB, or a markdown file in a repo — pick one. Every candidate item lives there. If it's not on the list, it doesn't get scored, and if it doesn't get scored, it doesn't get worked on. This part is unforgiving on purpose.

    Notion is fine and matches your existing pattern. Add columns: title, description, value, criticality, risk, size, wsjf, scored_at, status. Agent writes scores back via the Notion MCP.
  3. Scoring agent prompt — keep it tight

    Pass items in batches of 5–10. Bigger batches drift; smaller wastes context.

    Scoring prompt
    You are a backlog scorer using this rubric: {{rubric}} Current strategic context: - Active sprint: {{sprint.name}} - Quarter goals: {{okrs}} For each item, return JSON: { "id": "...", "value": 1|2|3|5|8, "criticality": 1|2|3|5|8, "risk": 1|2|3|5|8, "size": 1|2|3|5|8, "wsjf": <computed>, "rationale": "<25 words why these scores>" } Be ruthless on size — overestimate rather than under.
  4. Weekly cron, Sunday night re-scoring

    Run the scorer against the entire backlog every Sunday at 9pm. Fresh scores Monday morning. Re-scoring matters because criticality shifts as deadlines approach and value shifts as priorities clarify.

    n8n schedule
    Schedule Trigger → Notion: read all backlog items where status=open → Loop: batches of 8 → Claude API: score batch → Notion: write scores back → Final step: post top-3 by WSJF to Slack/Discord
  5. Top-3 surfacing, not a giant ranked list

    The agent's deliverable is "this week's top 3 by WSJF, with one-line rationale each." A 40-item ranked spreadsheet is not actionable; three things are. Anything below position 3 stays in the backlog until next week's re-score.

  6. Quarterly rubric review — the agent reviewing you

    Once a quarter, ask: which items did the scorer rank top-3 that you ignored? If the same kind of item keeps scoring high and you keep skipping it, the rubric is wrong. Fix the rubric, not your discipline.

    Quarterly rubric review prompt
    Given the last 13 weeks of top-3 outputs and my actual completion log, identify: 1. Items that scored top-3 multiple weeks but never got done. Why? 2. Items I worked on that never reached top-3. Why? 3. Suggested rubric adjustments to close the gap.
  7. Tie scoring to your accumulator-platform pattern

    WSJF complements the FlashFusion accumulator model. Things accumulate freely; the scorer decides what becomes top-3 each week. You retain the "low-friction capture" benefit and gain the "ranked exit" benefit.

    Map this to Path Fitness: anything scoring WSJF < 0.5 for 4 consecutive weeks gets auto-archived. Aligns with your existing 0–100% archive rule and prevents zombie backlog items.
08
AI Calendar Time-Blocking
Calendar becomes the source of truth — if it's not blocked, it didn't happen. Agent rebuilds the day around tasks, energy, and shifting meeting reality.
MEDIUM AI ONE FOCUSED LOW COST
  1. Pick one tool — don't try to roll-your-own first

    Reclaim, Motion, and Sunsama all work. Pick one based on shape: Reclaim is best for habit-block defense, Motion for aggressive auto-scheduling, Sunsama for daily-planning ritual. Use it for 30 days before considering custom.

    Building this yourself with n8n + Google Calendar API is tempting but the tools have done years of hard work on edge cases. Roll your own only after you know exactly what default they got wrong for you.
  2. Tag every task with time-estimate AND energy-band

    Time alone produces a packed calendar; energy makes it sustainable. Three bands is enough.

    Energy bands
    DEEP — high focus, no interrupts. 90–120 min blocks. Examples: Three.js scene work, spec writing, lyric drafting. SHALLOW — collaborative or moderate focus. 30–60 min. Examples: PR reviews, client comms, documentation passes. ADMIN — low cognitive load. 10–25 min batches. Examples: ticket triage, scheduling, expense reports.
  3. Define protected blocks before letting the agent schedule

    Non-negotiable windows. The agent's freedom to rearrange ends here. Without protected blocks, deep-work hours get nibbled away by every "quick" meeting.

    Protection rules
    Mon–Fri 09:00–11:00 → DEEP only, no meetings Tue/Thu 14:00–16:00 → DEEP only (longer-arc work) Wed all day → no client meetings (creative day) Daily 12:00–13:00 → lunch, hard stop Daily 17:30+ → no work-blocks, calendar closed
  4. Two-week observation period before judging

    The first two weeks of agent-scheduled days will be wrong. The agent is learning your override patterns — what you reschedule, what you let bump, when you actually start vs. when you said you would. Don't rage-quit on day three.

  5. Track the bumped-task signal

    Tasks that get rescheduled three or more times are telling you something. Either: (a) the time estimate is wrong, (b) the energy band is wrong, or (c) you don't actually want to do it. Three-bump rule means: re-estimate, re-tag, or kill.

    Weekly bump-report prompt
    List tasks rescheduled 3+ times this week. For each: was the issue size, energy, or motivation? Recommend action: re-estimate / re-tag / kill / sprint-it.
  6. Calendar-as-truth for retro and accountability

    Once the calendar is the source of truth, retros become easy. "Where did the week go?" answered by the actual blocks, not memory. Pair with the WSJF Friday review (#7 cross-link) — match scheduled-time against top-3 priorities.

  7. Apply specifically to the L1 service-desk problem
    For Intinc: the failure mode is AI/automation work hours getting eaten by ticket churn. Protect Mon/Tue mornings as DEEP for AI work. Let the agent autonomously slot tickets into SHALLOW/ADMIN windows. Two-week trial with explicit before/after metrics on AI-project hours.

Bullet Journal + Daily Log Extract
Analog or plain-text daily ritual. Morning planning stays human; AI processes the day's log after the fact to extract tasks, decisions, and open loops.
LIGHT AI MIXED LOW COST
  1. Daily log format — five sections, fixed

    Consistency lets the extractor be reliable. Same headers every day, in the same order. Whether it's pen on paper or a daily .md file, the structure carries the value.

    daily/2026-04-25.md
    # 2026-04-25 ## Intentions - Three things I'll move today ## Log - HH:MM bullets through the day, free-form ## Decisions - Anything I committed to, with one-line reasoning ## Open - Questions / loops / things I owe someone ## Reflection - One paragraph, end of day. What worked, what didn't.
  2. Capture path — phone photo OR watched folder

    Two paths, same destination. Analog: nightly photo to a designated folder, OCR runs on it. Digital: save .md to a folder n8n watches.

    Already on iPhone? Use Apple Notes' built-in scanner → Shortcut → save to iCloud folder → n8n watches via cron-poll. Or skip iCloud and write directly to a Supabase storage bucket.
  3. Extraction prompt — strict output schema

    Don't let the agent improvise the structure. JSON output, fixed keys, downstream router writes to your task system.

    Extraction prompt
    Read the daily log below. Return ONLY this JSON: { "date": "YYYY-MM-DD", "actions_taken": [past-tense, what got done], "decisions": [commitments made, one-line each], "open_loops": [ { "text": "...", "owe_to": "self|name|company", "due": "YYYY-MM-DD|null" } ], "questions": [things to chase or research], "signals": [patterns or themes worth tracking] } Do NOT invent items not present in the log. If a field has no items, return [].
  4. Morning brief — yesterday's open loops + today's calendar

    Before you write today's intentions, the agent serves a single page: yesterday's open_loops, this morning's calendar, any decisions you made yesterday that shape today. Cuts the "where was I?" tax.

    Brief composition
    Section 1 — Yesterday's open loops (max 5, ordered by due date) Section 2 — Today's calendar (next 12 hours) Section 3 — Decisions that affect today (max 3) Section 4 — One-line nudge: pattern from past 7 days Total: half a screen. If it grows, prune ruthlessly.
  5. OCR accuracy is the failure mode — design around it
    Bad handwriting wrecks the extraction. Three mitigations: (1) print, don't cursive; (2) use Claude's vision rather than legacy OCR — it handles handwriting better; (3) include the OCR text in the brief output so you can spot misreads at-a-glance.
  6. Weekly pattern surfacing

    Sunday: agent reads the week's seven extractions and answers three questions. Patterns are the second-order value of journaling — invisible day-to-day, obvious when you batch.

    Weekly review prompt
    Given this week's 7 daily extractions: 1. Which open_loops appeared more than twice without resolution? (These are stuck. Why?) 2. Did any decisions contradict an earlier decision? (You're flip-flopping. Worth surfacing.) 3. What signal/pattern shows up across multiple days? (Repeated theme worth investigating.)
  7. Memoir / lyric track — the analog ritual IS the value
    For the writing/memoir/chaosclub side: the analog ritual stays untouched because that's where the cognitive benefit lives. The agent's only job is making sure the signal doesn't evaporate. Extraction → tagged corpus → fuel for the BASB Express loop (#3) when you're drafting.

Multi-Agent Orchestrator
Specialist agents per domain. Meta-agent (you, plus a router) decides who picks up what. The system IS the agents — collapses without them.
HEAVY AI MANY PARALLEL HIGH COST
  1. Map domains ruthlessly — three to five, no more

    Every additional domain adds routing complexity quadratically. Three domains is great, five is the ceiling, six means the orchestrator is laundering chaos. Pick by where you have actual repeated work, not aspirational categories.

    Candidate domain map for your stack
    research-agent → web search, corpus retrieval, fact-check tools: web_search, RAG over /notes, /transcripts code-agent → repo work, tests, CI, deploys tools: github, claude_code, cf_workers, base44_api ops-agent → ticket triage, monitoring, alert response tools: ticketing, supabase, posthog, sentry content-agent → drafts, posts, lyrics, newsletter editions tools: notion, second_brain_search, publishing_apis (Optional 5th) → only if a domain genuinely has its own tool surface AND repeats weekly
  2. Tool surfaces with explicit permissions

    Read-only by default. Writes require either a checkpoint (human approval) or a budget (limited count per run). Never "agent has all the keys" — that's how you wake up to a 3am incident.

    Tool config schema
    tool: github_create_pr agent: code-agent mode: write guardrails: - target_branch != main - approval_required: true - max_files_changed: 25 - blocked_paths: [".github/", "infrastructure/", "secrets/"] tool: supabase_query agent: ops-agent mode: read guardrails: - timeout_ms: 5000 - row_limit: 1000
  3. Audit logging from day one — non-negotiable

    Every tool call, every decision, every output. If you don't have audit logs, you don't have a system, you have a black box that occasionally does the right thing. Worth more than most of the actual code.

    Audit log schema
    CREATE TABLE agent_audit ( id UUID PRIMARY KEY, ts TIMESTAMPTZ NOT NULL, agent_name TEXT NOT NULL, task_id UUID NOT NULL, -- groups related calls tool_called TEXT, inputs JSONB, outputs JSONB, tokens_used INT, cost_usd NUMERIC(10, 6), status TEXT, -- ok | error | blocked reviewed_by TEXT, -- human if checkpoint decision TEXT ); CREATE INDEX idx_audit_task ON agent_audit (task_id); CREATE INDEX idx_audit_ts ON agent_audit (ts DESC);
    You already have Supabase running for the drive automation audit trail. Same pattern, new tables. The Orchestrator AI Base44 platform's existing audit infrastructure is reusable here — that's the leverage.
  4. Router agent — keep it dumb on purpose

    The router is the simplest thing that works: a single Claude call with the domain agent descriptions and the incoming request. Smart routers are where complexity hides — start dumb, add intelligence only when measured failures justify it.

    Router prompt
    You are a request router. Available agents: {{agent_descriptions}} For the request below, return JSON: { "agent": "<agent_name> | clarify | reject", "reason": "<one line>", "task_brief": "<cleaned-up version for the agent>" } "clarify" if the request is genuinely ambiguous. "reject" if it falls outside all agent surfaces. Do not decompose multi-agent tasks here — that's the agents' job.
  5. Token budget + circuit breaker per agent

    Every agent has a per-run budget and a daily ceiling. Hit the ceiling, agent stops, you get notified. Cost overruns are the fastest way to learn your routing is wrong — but only if a circuit breaker exists.

    Budget config
    research-agent: per_run=15K tokens, daily_cap=200K code-agent: per_run=80K tokens, daily_cap=800K ops-agent: per_run=5K tokens, daily_cap=100K content-agent: per_run=40K tokens, daily_cap=300K ON breach: - log to audit table with status="budget_exceeded" - notify operator (Slack, Discord, email) - reject further calls until reset or override
  6. Inter-agent communication via the audit table, not direct calls

    Counter-intuitive but important: agents don't call each other directly. They post results to the audit table and the router reads from it. Direct calls produce tangled dependency graphs; mediated communication stays observable and replayable.

    If two agents need to coordinate tightly enough to require direct calls, you've drawn the domain boundaries wrong. Merge them.
  7. Human checkpoints at strategic points only

    Not every step needs human approval. Define the points where judgment matters: pre-merge, pre-publish, pre-spend-over-threshold, pre-external-comms. Everything else runs autonomously inside its budget. Too many checkpoints kill the leverage.

    Checkpoint policy
    REQUIRES checkpoint: code-agent → before merge to main content-agent → before publish to public surface ops-agent → before any tool with mode=write to prod any agent → before spend > $5 in a single run NO checkpoint: any read operation draft creation in private workspace test runs in CI internal logging or summarization
  8. Decide: extend Orchestrator AI or build separate
    The honest fork-in-the-road: your existing Orchestrator AI Base44 platform is hardened for client-facing SOC2 multi-tenant use. Either (a) extend it with a "personal tenant" — same code path, same audit infra, but extra complexity in tenant logic and policy; or (b) build a stripped-down personal version that shares only the audit schema. Option (a) is more leverage if the client-facing platform stays stable; option (b) is faster to ship and lower risk if the platform is still evolving. There's no right answer that's true regardless of platform stability — make the call based on how stable v1 actually is in production.
