Setup & Security: what it takes to run this for real

The mentor works out of the box on every page. Making its authentication and connectors production-grade needs a few things this document spells out, grounded in current (2025–2026) security guidance.

Last reviewed June 2026 · sources at the end

1. The one rule everything follows

A static site is a public client. Anything shipped in the HTML/JS — or even held in the browser at runtime — is readable by anyone willing to spend a minute in developer tools. The industry pattern for fixing this is Backend for Frontend (BFF): a thin server-side layer holds the secrets and the frontend never sees them.

Non-negotiable

Any secret embedded in browser JavaScript is a secret shared with every user and every attacker. The fix is not obfuscation — it is moving the secret to infrastructure you control. The mentor's proxy-deploy/ package IS that BFF.

2. What is safe in the browser vs. what is not

Not all keys are equal. Two kinds can live client-side:

  • Public / "identifier" keys — keys that identify your app but unlock no private resources (e.g. a Supabase anon key, a Firebase web key). Designed to be shipped.
  • Domain-restricted keys — keys locked to your origin and a usage quota by the provider. Lower risk, but still rate-limit them.

Everything else — Notion tokens, GitHub PATs, Google/Microsoft OAuth secrets, and yes, your LLM API keys — is a private secret and belongs only on the backend/proxy.

Mentor today

The in-browser vault stores LLM keys for personal, single-user use (you, on your device). That's an acceptable risk for a private tool — but it is not how you'd ship to others. For anything shared or public, route LLM calls through the proxy too.

3. Authentication (Supabase) — the live path

Real Google OAuth and email magic links run from a static page through Supabase Auth, because the OAuth client secret stays inside Supabase. The browser only ever holds the public anon key.

One-time setup

  1. Create a free project at supabase.com; copy the Project URL and anon public key.
  2. In Authentication → Providers, enable Google. In Google Cloud, create an OAuth client (type: Web application), add your site URL under Authorized JavaScript origins, and add Supabase's callback URL under Authorized redirect URIs.
  3. In Authentication → URL Configuration, add every URL the mentor lives on to the redirect allow-list (wildcards allowed for preview deploys; use exact paths in production).
  4. In the mentor: Settings → Auth, paste the Project URL + anon key. The gate now shows "Continue with Google" and "Email magic link".
Gotcha

Always set redirectTo explicitly and make sure it's on the allow-list — redirect-mismatch is the single most common Supabase Auth failure. The mentor sets redirectTo to the current page automatically; just make sure that URL is allow-listed.

The offline passphrase remains a zero-setup fallback. It is obfuscation, not authentication — use Supabase Auth when you need real "only me" access control.

4. The backend proxy — deploy & harden

The included proxy-deploy/ Worker is the BFF for every key-based integration. Deploy once (Cloudflare/Vercel/Supabase Edge), set secrets server-side, paste its URL + PROXY_TOKEN into Settings → Connections.

cd proxy-deploy
npm install
npx wrangler login
npx wrangler secret put PROXY_TOKEN      # long random string
npx wrangler secret put NOTION_TOKEN     # per upstream you use
npx wrangler deploy                      # prints your https://…workers.dev URL

Before any real use — harden the proxy

  • Lock CORS to your exact site origin (the scaffold ships * for setup only). An open proxy that forwards requests is just a slower way to leak your keys.
  • Validate the session: every proxy request should verify the caller (the PROXY_TOKEN is the minimum; gating on a Supabase JWT is stronger).
  • Rate-limit at the edge so a leaked token can't run up your bills or trip vendor limits.
  • Validate & sanitize inputs; don't blindly forward user-supplied parameters to upstreams.
  • Least privilege: one scoped secret per upstream, not a god-key.
  • Log usage, never secrets; watch for anomalies.
  • For production, pull secrets from a secrets manager (rotation + auditing) rather than plain env vars.

Self-healing models

Model names deprecate constantly, so the mentor doesn't trust hardcoded ones. Leave the model field blank and it queries each provider's live /models endpoint, auto-selects the newest capable model, and caches it for a day. If a call ever fails with a "model not found / deprecated" error, it marks that model bad, re-discovers, and retries — no edit needed. Use Detect latest now in Settings → Providers to refresh on demand.

6. Operating checklist

  • CORS on the proxy restricted to your origin.
  • PROXY_TOKEN long, random, and secret; rotate on any suspicion.
  • Rate-limiting + input validation live on the proxy.
  • Rotate every API key on a schedule (~90 days) and immediately if exposed.
  • Treat any key ever pasted into a browser vault as compromised the moment the device is shared — rotate it.
  • Use provider-side key restrictions (domain, scope, quota) wherever offered.
  • Supabase redirect allow-list contains exactly your live URLs.
  • Monitor usage dashboards for spend/volume spikes.
