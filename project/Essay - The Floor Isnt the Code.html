The Floor Isn't the Code

Everyone's arguing about method. Nobody's asking about judgment.

Kyle Rosebrook
TL;DR
  • The hate toward vibe-coded apps is aimed at the wrong target.
  • The problem isn't AI-assisted building. It's people using AI to simulate understanding they haven't earned.
  • Domain knowledge is the ceiling. AI is the speed layer. In that order.
  • AI can write the code. It cannot read the room.

The argument is aimed wrong

The argument against vibe-coded apps is wrong. Not because vibe coding is good or bad, tools aren't either, but because it's aimed at the wrong target.

One camp says it's irresponsible: you're shipping code you don't understand, no audit trail, nothing maintainable. The other camp says stop gatekeeping, it's just faster tooling, everyone does it now. Both sides are arguing past each other about method while the actual question, do you understand what you built, goes unasked.

Method doesn't determine quality. Never did. There have always been developers who typed every line themselves and shipped things that broke in predictable ways because they didn't understand the domain they were building in.

What the hate is actually surfacing

Here's what actually happened: people with domain expertise started shipping faster using AI tools. People without domain expertise started shipping things that looked like they worked. Critics watched both, called it a movement, and handed out moral judgments about which kind was real building.

The problem isn't AI-assisted development. The problem is that AI lowered the barrier far enough that people can simulate understanding they don't have, convincingly enough to ship before the gap catches up with them.

That's not new. It happened with WordPress. With no-code builders. With every tool that made the act of building cheaper. When entry cost drops, the distance between surface-level capability and actual domain knowledge gets exploited faster. The AI just made that gap faster to reach.

"If you've earned the judgment, AI makes you faster. If you haven't, it makes you wrong faster."

Domain knowledge does the work

The article that kicked this piece off is a good example of the right argument made from the wrong angle. The author built a security research platform, converts bug bounty writeups into interactive challenges, and caught heat for vibe coding it. He's been a security researcher for years. He's hunted vulnerabilities. He knows how attackers think.

He used AI to write the code. His decade of domain knowledge handled everything else.

Take away the domain knowledge and you don't have a faster developer. You have a faster way to ship something that looks functional and leaks session tokens.

The critics aren't wrong that AI-generated code gets abused. They're wrong about who's doing the abusing. It's not the people who built the expertise first and are now moving faster. It's the people using AI to fake the expertise they skipped.

AI can write the code. It cannot read the room.

The only question that actually matters: do you understand what you're building well enough to know when it breaks?

Not "does it throw an error." Can you read the error as a signal about what's actually wrong? Can you tell the difference between a bug in the code and a bug in your understanding of the problem? Can you see the gap between what was reported and what's actually broken?

That's the diagnostic work. It doesn't compress. AI can generate a solution once you know what you're solving for. It cannot tell you whether you've correctly identified what needs solving. The room-reading has to happen first, and no amount of AI capability changes that.

Typing your own code never guaranteed you understood the system. Neither does reading the output. What matters is whether you have the context to know when something's wrong before your users find it for you.

Tools as prosthetics, not optimization

I'm a self-taught engineer. No CS degree. I learned to code on a card table at 1:30am because I had an idea and no other way to build it. I took screenshots of what I was doing so I could trace back exactly where I broke something. I worked that way for months, not because it was efficient, but because it was the only system I had.

I use AI tools now. Every day. To build FlashFusion. To move faster than I could otherwise.

But here's the thing about how I think about them: they're not optimization. They're scaffolding for a brain that runs at speed but doesn't always hold everything it needs to. The tools address specific gaps. They're prosthetics, not shortcuts.

The AI tools are the same category. External support for judgment I earned by doing it wrong first, many times, in ways that cost me something. The judgment comes first. The speed layer runs on top of it. Reverse that order and you don't have faster building, you have faster failure that looks like progress until it doesn't.

The floor

The gatekeeping is real and it's stupid. Plenty of what passes for legitimate development is bad architecture, bad security, and bad decisions written in syntactically correct code by people who typed every character themselves. The method was never the quality signal.

But the criticism of people using AI to fake expertise is legitimate. Both things are true at the same time.

The strongest version of the defense isn't "stop judging how I built it." It's simpler: show the problem. Explain why it exists. Describe what breaks if you get it wrong. That's the domain knowledge no AI generates for you. That's what separates vibe coding as acceleration from vibe coding as hallucination.

The floor has never been the code.

It's whether you understand what the code is supposed to do, and what it costs when it doesn't.
