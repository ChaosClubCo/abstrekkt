Chaos Club · Onboarding

Onboarding flow + process

First-90-seconds path through Chaos Club. Designed so a person in distress hits a meaningful moment before hitting any friction. The longer the path, the higher the drop-off; the lower the friction, the worse the matching. This flow holds the tension.

The 9 steps, in detail

Step 1 — Landing
Anonymous arrival, no friction
User hits chaosclub.co. No popup. No newsletter signup. No "we use cookies" wall on top of the experience. The page explains what Chaos Club is in one paragraph and offers a single primary action: "Find someone to talk to." That action is the entry into Step 2.
Frontend: Next.js / static · No auth required to land · Time on page target: under 30 seconds
Step 2 — Crisis check
Acute risk routing before anything else
A single screen with one question: "Are you in immediate crisis?" Two options: "Yes — I need help right now" routes to 988 / local emergency contact info with no further routing. "No — I want to talk to someone" continues to Step 3. This is non-negotiable.
Required: 988 link, regional crisis numbers, "leave site fast" exit option · Backend: nothing logged on crisis route
Step 3 — Profile (3 fields)
Minimum viable identity
Three fields, no more. (a) Pseudonym (or "skip" — generates one). (b) What's the focus right now (single multi-select with 5-6 generic categories — relationships, work stress, family, identity, "I don't know yet"). (c) Time window for the first session (within an hour / today / this week / no rush). Submit. The longer this form gets, the worse the conversion.
Backend: Supabase row, soft delete after 30 days if no further action · Schema: pseudonym, focus_tags[], session_window, created_at
Step 4 — Match offered
First match within 60 seconds
The match algorithm prioritizes availability over fit at first touch. Better a 70%-match human now than a 95%-match human in three days. Show one match: pseudonym, brief profile (3-4 sentences they wrote themselves), what they're typically helpful with. Two buttons: "Talk to them" or "Show me someone else." No infinite scroll — max 3 alternates before showing a wait-list option.
Algorithm: weighted score = 0.6 × availability + 0.3 × focus overlap + 0.1 × recent feedback signal · Stored: match_offers table
Step 5a — Decline path
Resources, not gatekeeping
If the user declines all matches or aborts: do not punish. Show a curated resource page (books, articles, support orgs, free hotlines). Give them the ability to come back later without re-doing Step 3 (cookie-based session preservation, 7 days).
Resource list: maintained manually, refreshed quarterly · No tracking on resource clicks
Step 5b — Accept path
Choose modality and start
User chooses: async text (asynchronous chat thread, sometimes faster to start, no scheduling) or live audio (scheduled call, requires a calendar handshake). Default: async text — lower friction. Send a notification to the matched peer; show the user a "your message has been sent" state with an estimated response window.
Async: in-app messaging, no SMS/email by default · Audio: scheduled via Cal.com or equivalent, never includes phone numbers
Step 6 — Session held
No timer, no script
The session itself is unconstrained. Async threads can run for days; live calls can be 10 minutes or 90. The platform doesn't intervene. If something concerning surfaces (self-harm signals, abuse disclosures), the system flags for human review without breaking the conversation. Trained moderator, not automated escalation.
Critical: never use AI to summarize or rewrite peer conversations · Storage: encrypted, peer-only access, 90-day retention then anonymized
Step 7 — Light feedback
Three emoji, one optional note
After the session naturally winds down, both parties get a single screen: pick one of three emoji (helpful / mixed / not helpful), and optionally write a short note. That's it. No 5-star rating. No required text. The signal feeds the matching algorithm and the platform's quality monitoring.
Stored: feedback_events table · Used in: matching weight calculation, peer reputation (private), platform quality reports
Step 8 — Loop offer
Same person, scheduled
If both parties marked "helpful," the system offers a continuation — schedule a next session with the same peer. This is the compounding move. Most peer support platforms re-shuffle on every visit; Chaos Club explicitly enables relationship continuity if both parties want it.
Booking: in-app, never reveals personal contact info · Cap: max 4 scheduled sessions before a "do you want to keep going" check-in
Step 9 — Ongoing relationship (or not)
Single-session is also a successful outcome
The user can return for a single session, build an ongoing relationship with one peer, or never come back. All three are successful outcomes. Chaos Club doesn't optimize for retention as a vanity metric — it optimizes for the user getting what they came for, even if that takes one conversation.
Tracked: cohort outcomes (single-session helpful, multi-session ongoing, never returned) · Reported: monthly platform quality summary

Architectural notes

Tech stack (current)

  • Frontend: Next.js / React / Tailwind
  • Backend: Supabase (auth, database, real-time channels)
  • Messaging: Supabase real-time + custom presence layer
  • Audio (if used): Cal.com for scheduling, third-party WebRTC for the call itself (no phone numbers ever)
  • Moderation: Hybrid — automated flagging on keyword + sentiment, human review queue, never auto-action without human

Data discipline

  • Conversation content: encrypted at rest, peer-only access, 90-day retention then anonymized
  • Profile data: minimum necessary (3 fields), 30-day TTL if no follow-up activity
  • Crisis-routing data: not logged at all
  • Feedback events: aggregated only, never linked back to individual conversations after 30 days
Hardest design tension: friction-low onboarding wins users; friction-low matching loses quality. The flow above resolves it by making profile setup <90 seconds (Step 3) but sequencing the match algorithm to weight availability over deep fit (Step 4). Quality is recovered through the feedback loop (Step 7) and peer reputation, not through up-front gating.

Open questions

  • Peer onboarding: not addressed in this flow. Separate document required for who becomes a peer, training, screening, code of conduct.
  • Moderation SLA: the human review queue's response time hasn't been defined. Probably needs to be under 4 hours for flagged content. Cost implications.
  • Sustainability model: not addressed here. The platform is free for users — what funds it? (Donations, grant funding, low-cost subscription for "premium" features that don't gate the core experience.)
  • Legal: peer support is not therapy. The product copy must make this distinction relentlessly. Liability waiver in TOS, regular legal review.
