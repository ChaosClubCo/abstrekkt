The QA Loop Nobody Runs

Two infographics. One argues for checking your work. The other argues that most AI output doesn't need to be an artifact at all. They're both right — and together, they point at the same blind spot.

"Tokens spent on formatting are tokens not spent on thinking."

There's an infographic circulating that makes a case against HTML artifacts for most AI workflows. Its core argument: a markdown report uses around 800 tokens; the same content wrapped in styled HTML uses 2,500 to 4,000. The formatting consumes context that could be spent on reasoning.

Separately, a "System Prompt QA Suite" diagram has been making rounds — a structured check→fix→report→repeat cycle for inspecting AI system outputs before they ship. It's a prompt collection designed to catch errors, security gaps, and logic problems before they reach users.

These seem like different topics. They're not. They're both pointing at the same hole: most people build AI outputs and never verify them. The first argues you're building too much. The second argues you're checking too little. Both are correct.

The 3-5x Tax You're Not Tracking

3-5×
The token multiplier of styled HTML vs. markdown. The same content. The same information. Three to five times the context window consumed on div tags, CSS properties, and class names that the reader doesn't need and the model can't reason about.

This isn't a formatting preference — it's a resource allocation question. Every AI conversation has a context window. The context window is the model's working memory. When you fill it with formatting instructions, you're reducing the space available for the thing you actually care about: the quality of the thinking.

I've caught myself doing this. Building an elaborate HTML dashboard to present data that would have been clearer as a table in markdown. Creating a styled artifact when the reader was going to copy-paste the text into Slack anyway. The output looked impressive. It also took four times longer to generate and carried zero additional insight.

When HTML Actually Wins

The honest version: HTML is the right tool about 10% of the time. Interactive dashboards where the user clicks things. Data visualizations where spatial relationships matter. Calculators and tools that need state. Client deliverables where visual polish directly translates to perceived value.

For the other 90% — reports, summaries, analyses, recommendations, plans, research — markdown is not just sufficient, it's better. Better because it's portable (copy into Notion, Slack, email, GitHub). Better because it's scannable (headers and bold text, not nested divs). Better because it forces the writer to make the structure do the work instead of hiding behind styling.

The rule I use
If the output is going to be read, use markdown. If the output is going to be used — clicked, dragged, filtered, calculated — use HTML. If you're not sure, it's markdown. The answer is almost always markdown.

The QA Cycle That Should Be Default

The System Prompt QA Suite diagram shows a cycle: generate a source-of-truth document, run checks (logic, security, architecture, UI, performance), generate fixes, produce reports, repeat. It's meant for production systems, but the principle applies to every AI output you ship.

Here's what I run before anything goes out:

Step 1: Read it as the recipient, not the requester. The person who asked for the output knows what they meant. The person who receives it doesn't. Read it as them. Does it stand on its own? Does it answer the question that was actually asked, not the question you wish was asked?

Step 2: Check the claims. Every factual claim in the output is either sourced (verifiable) or generated (the model's inference). I tag them. [SOURCED] means I can point to where the fact came from. [GENERATED] means the model reasoned it and I should verify before relying on it. If more than half the claims are generated, the output needs more research, not more polish.

Step 3: Find the gap. What's not in the output that should be? What question would a skeptical reader ask that the output doesn't preempt? This is the GAPS/BLINDSPOTS footer. It's the hardest step because it requires thinking about what you don't know, not what you do.

Step 4: Kill the formatting that's hiding weak content. Bold text and headers create the illusion of structure. Remove them. Read the raw text. If it sounds thin without the formatting, the content is thin. Formatting should amplify good content, not prop up weak content.

Why This Compounds

The QA loop isn't about perfectionism. It's about trust calibration. Every time you send an AI output without checking it, you're implicitly telling the recipient: "I trust this model's judgment as much as my own." That's a bold claim. For most people, it's also wrong.

The correction loop — check, tag, gap-find, strip — takes five minutes on a short output. It catches errors that would take hours to correct after the fact. And each time you run it, you get faster at diagnosing the specific failure modes of the model you're using. The QA loop trains you, not just the output.

The best AI output isn't the most polished. It's the most verified.

Gaps

• Doesn't address code output, where formatting (syntax highlighting, line numbers) is genuinely useful even in a "read" context.

• The QA loop described is solo-practitioner. Team workflows with review stages may already catch some of these issues through existing processes.

• "Tokens spent on formatting" argument weakens as context windows grow larger — at 1M+ tokens, the 3-5x multiplier matters less.
