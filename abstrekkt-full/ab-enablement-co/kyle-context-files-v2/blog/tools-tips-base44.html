Six Things I Wish I Knew Before Moving to Base44

I migrated my front door off Wix this week. Six tips, organized by where they bit me — onboarding, schema, deploy, MCP, debug, and what's actually worth using it for.

Kyle Rosebrook · 4 min read
§ The Tool
Base44
TypeApp platform
UseSchema-first AI apps
StackMongoDB-style
MCPYes (read-only)

I shipped FlashFusion's AI Setup Audit Scorecard on Base44 in under a day, then started moving my personal site over from Wix this week. The platform is good. It's also opinionated in ways the docs don't fully prepare you for. These are the six things that would have saved me time on day one.

§ Setup & Schema
Tip 01

Entity count is a terrible signal of app readiness.

The platform surfaces entity count prominently. I assumed early that more entities meant a more mature app. It's the opposite, often. My most-used app has 16 entities and three real test runs of actual data flowing through. My biggest schema has 101 entities and zero real data — it's a blueprint, not a product.

Pattern-match on data presence and recency, not entity count. The entities are the easy part. The data is the work.

If an app has lots of entities and no recent records, it's a sketch. Treat it accordingly.
Tip 02

Enum values must match the schema exactly or the field drops silently.

This one cost me an afternoon. If you POST a record with an enum value that doesn't match the schema's allowed list — case-sensitive, no fuzzy matching — Base44 doesn't reject the record. It accepts the record and silently drops the offending field. No error. No warning. The record just shows up missing that value.

The first time you debug this, you'll waste an hour assuming your code is broken. Your code is fine. Your enum is wrong.

When a field "isn't saving," your first check is the enum. Compare the value byte-for-byte against the schema definition.
§ MCP & Integrations
Tip 03

The MCP is read and create, not update or delete.

If you're planning to mutate records programmatically through Claude or another MCP client, plan around this constraint up front. Base44's MCP exposes create_entities and query_entities as the substantive write/read primitives. It does not expose update or delete endpoints.

If you need to update records, the workarounds are real but ugly: write a new record and tombstone the old one, route through a separate workflow tool, or do it in the UI. Don't architect a system around mutations the API doesn't support.

Architect around the API surface that exists today. The capability gap may close, but don't build assuming it will.
Tip 04

Custom domains via Cloudflare CNAME — proxy off.

The setup is straightforward but the proxy setting matters. Point your subdomain to base44.onrender.com via CNAME with the Cloudflare proxy disabled (the gray cloud, not the orange one). Proxy on will produce SSL handshake failures that look like Base44's problem and aren't.

I had audit.flashfusion.co live in about ten minutes. If your domain isn't resolving, check the proxy setting first. It's the #1 cause of the issue and the easiest to miss.

Cloudflare gray cloud (DNS only), not orange. Base44 handles its own SSL termination.
§ Debug & Deploy
Tip 05

Treat the schema as the source of truth, not your app code.

Base44's strictness — the silent enum drops, the rigid schema enforcement — is actually a feature once you stop fighting it. The fastest path to a working app is to treat the schema as the canonical contract and write your app code against it, not the other way around.

I lost time on the first build trying to get the app to "work around" schema constraints. Don't. Update the schema, then update the app. Build forward. The platform rewards builders who think in entities first; it punishes builders who think in code first.

Schema-first means: change the data model, then change the code. Not in the other order.
Tip 06

Use Base44 for what it's actually good at.

Production-grade AI apps with a schema that matters: yes. Internal tools with structured data and AI-touched workflows: yes. CRM-shaped apps with complex relationships: yes.

Drag-and-drop landing pages, marketing sites with twenty layouts, blog-shaped content sites: no. Use the right tool. I'm migrating my static personal site there because I want a single platform, not because Base44 is the best static-site builder. Don't pretend a tool is something it isn't.

Base44's strength is structured data with AI integration. Anything you'd build in Webflow or Framer is probably better built there.

Most tool friction is the gap between how the tool actually works and how the docs describe it. Closing the gap is where the time goes.
