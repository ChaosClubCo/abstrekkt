Case study.

The Cowork Plugin System

A canonical plugin specification for teaching Claude domain-specific work. Markdown and JSON, no build step — the instructions are the code.

The problem

Every team that adopts Claude reinvents the same three wheels: how to encode domain knowledge, how to expose it as reusable commands, and how to stitch it to external tools. Most end up with a Notion page of prompts and a prayer.

The Cowork plugin format answers all three with one contract, readable by a human and executable by a model.

The contract

A plugin is a directory. Required: a manifest (plugin.json) that gives it an identity. Optional but expected: commands/ as user-triggered entry points, skills/ as auto-triggered domain logic, .mcp.json for external tool bridges, and references/ for shared knowledge files.

Three components you always have: manifest, commands, skills. Three you reach for when you need them: MCP connectors, hooks, sub-agents. That's the whole surface.

The spec itself is derived from the Anthropic Cowork plugin repos and a corpus of 16 PDFs, 4 spreadsheets, and 2 docs of Cowork OS material — normalized into one canonical v1.0 reference.

Why plain-text wins

No build step. Edit a Markdown file, save, restart Claude. No compile, no bundle, no package publish. The feedback loop is seconds.

Git is the deploy system. Version control, code review, rollback — you get all of it for free because the plugin is just files.

Humans and models read the same source. A new hire reading SKILL.md learns the domain. The model reading the same file can execute it. The documentation is the implementation.

What I built

The spec. A v1.0 canonical reference covering directory structure, naming conventions, manifest schema, commands, skills, MCP integration, hooks, and sub-agents. The thing I wanted to read the first time someone asked me "how do I build a Claude plugin."

A generator. Scaffolds a valid plugin from a short description. 35 working scaffolds in the reference set.

A marketplace of plugins. Packaged, documented, installable. Designer skills, sales skills, engineering skills — each one a directory, each one reviewable as a pull request.

What I learned

The naming matters more than the code. A skill called review-pr gets found. A skill called engineering-workflow-v2-final doesn't. The manifest's keywords field is load-bearing.

Commands are for humans. Skills are for models. Commands are the doors the user walks through. Skills are the domain logic the model calls when a command — or another skill — needs it.

References are the secret weapon. Brand voice, ICP profile, style guide — putting these in references/ once and having every skill read from them means the domain stays coherent even as the plugin grows.
