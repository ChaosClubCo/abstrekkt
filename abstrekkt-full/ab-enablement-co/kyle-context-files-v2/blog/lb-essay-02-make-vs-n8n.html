Make vs n8n: Which One I'm Still Running

I'd been running n8n for most of a year. The first time I looked at what it was actually doing was the week I stopped.

Sixty-five workflows. None of them were running. That was the first thing the audit told me. The second thing it told me was that I hadn't noticed.

I'd been running n8n at krosebrook.app.n8n.cloud across multiple build phases — content pipelines, lead capture, newsletter triggers, CRM sync. All sixty-five were marked active in the dashboard. A Python script that parsed all sixty-five JSON exports pulled name, status, node count, trigger type, and execution history. It ran in a few seconds. The execution column came back zero across every single workflow.

The Silent Stack

Zero executions, active flag on, no errors logged. The standard reading is that something broke. That's not what happened.

The workflows weren't failing. They were idle. Triggers configured correctly and never fired — because the downstream conditions they waited on had either never been fully wired or had stopped occurring weeks earlier. n8n's dashboard showed sixty-five green indicators and nothing else. To see execution history, you open each workflow individually. Across sixty-five workflows, that's sixty-five manual checks I wasn't doing.

A tool that breaks loudly is fixable. Zero runs with no error is the absence of a signal. You can't fix what isn't reporting.

This is a different failure mode than a broken tool. A broken tool gives you something to fix. An idle tool wearing an active label gives you nothing — right up until the moment you need the workflow to have run and discover it hasn't.

A process inspector on the QC floor checks the defect gauge. The gauge reads normal. The defect rate has been climbing for a week. The gauge is technically correct — it's reading what it's reading. The problem is that nobody wired it to the thing that matters.

What Triggered the Audit

CVE-2026-33663 landed on the instance. That forced the decision: patch or migrate. I ran the Python audit to figure out which was worth doing.

The CVE made the decision easier. It wasn't the reason to migrate. The zero-executions data was. A vulnerability on an instance running nothing is a vulnerability you're paying to maintain for no running benefit. The CVE was just the occasion to look. The audit was the reason.

The same week, the n8n MCP connector had been in a CONNECTION_ISSUE state throughout recent sessions — couldn't introspect the instance, couldn't read scenario state, couldn't do anything useful from Claude. That was a token scope problem in theory. In practice, it was a second signal in the same direction: the tool I'd built around was invisible to the automation layer that was supposed to manage it.

Make had the same scope issue during initial setup. Its MCP returned "No approval received" on scenario writes. The difference: that error message said exactly what was wrong and exactly where to fix it (Profile → API → regenerate key). I fixed it in ten minutes. The n8n MCP connection was never fixed in the session. I stopped trying and ran the audit instead.

The migration wasn't a transfer. It was an inventory with a conclusion. The conclusion was that most of what I'd built hadn't been running anyway.

The nine P1 workflows became Make blueprints — properly this time, with error handling and tested endpoints. Two are live now: the lead capture automation for audit.flashfusion.co and the Load-Bearing newsletter trigger. The rest are queued behind Make's free-plan ceiling: two active scenarios, a thousand operations a month.

That ceiling used to feel like a constraint. It's not. It's the thing that prevents sixty-five idle workflows. You can't accumulate a silent stack when you're capped at two active scenarios. The limit forces the inventory discipline that unlimited workflows left to self-governance. I had sixty-five workflows because nothing stopped me from adding the sixty-fifth one. Make stops you at three.

What n8n Still Owns

The migration isn't a verdict on n8n as software.

For complex branching workflows — conditional logic across six or seven states, JavaScript code nodes that do real data transformation — n8n's visual builder handles it more cleanly. Make's scenario structure gets unwieldy when the decision tree is deep enough. n8n's code node is also more capable than Make's built-in functions for anything that requires actual data manipulation beyond simple field mapping.

The self-hosted option matters too. A self-hosted n8n instance with proper monitoring — a cron job that checks execution counts and pages you on zero-run active workflows — would have caught the problem I'm describing here before it became sixty-five workflows deep. The failure wasn't in n8n's architecture. It was in the absence of monitoring on top of it.

If the stack runs a hundred or more active workflows, the calculus is different. Make's per-operation pricing at scale is worse than n8n's flat subscription. The two-scenario cap forces painful prioritization decisions that a larger automation load can't absorb. At that point, n8n's power matters more than its monitoring gaps.

At ten or fewer active workflows, the cap is the right answer.

The better tool isn't the one with more features. It's the one whose failure mode you can read at 2am without opening the documentation.

Gaps

• The audit reflects one cloud n8n instance (krosebrook.app.n8n.cloud) that accumulated workflows across multiple build phases with no monitoring. A self-hosted n8n install with execution alerting configured would look different. The failure was in the operational layer, not the platform.

• No cost comparison included. Make vs n8n pricing was not the deciding factor here, so it's not in the essay. At scale the comparison changes meaningfully and deserves its own analysis.

• The 9 P1 blueprints were built as Make-importable JSON but only 2 are fully wired and live at time of writing. The migration is in progress, not complete.

• Make's free plan ceiling (2 scenarios, 1,000 ops/month) is a real constraint at higher automation volume. FF Sales WF-03 running every 15 minutes alone consumes ~2,880 ops/month — already past the free plan. The ceiling applies at current scale; it won't at Q3 scale if pipeline converts.

• n8n self-hosted vs cloud is a real distinction this essay collapses. The cloud version has different monitoring affordances than a self-hosted instance with full admin access.
