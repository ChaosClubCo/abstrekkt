How AI Studio Works

WHY THE STRUCTURE MATTERS BEFORE YOU PASTE ANYTHING

The key distinction

System Instructions are laws. Chat prompts are suggestions. AI Studio processes the system instruction block before every turn — treat it as immutable context, not a one-time message. Put your role, constraints, and output format there. Put your API spec and task there.

AI Studio is built around a five-layer prompt structure. Gemini reads them in order and weights them accordingly:

Layer 1 · LAWS
System Instructions

Role, constraints, output format rules. Persistent across the entire session. Paste into the clipboard icon field, not the chat box. This is where your dashboard generator identity lives.

Layer 2 · DATA
User Context / Uploaded Spec

The API spec, OpenAPI JSON, or integration config the user provides per request. Uploaded via the paperclip or Files API. Gemini's 1M token window can hold entire specs — don't summarize, upload the raw file.

Layer 3 · PATTERN
Few-Shot Examples

2–3 input/output pairs showing exact connector output format. Gemini consistently follows examples more reliably than pure text instructions — these are your most powerful formatting lever.

Layer 4 · TASK
Task Instruction

The direct command per request: "generate connector for this spec," "build dashboard from these two connectors." Short. Specific. References the uploaded file by name.

Layer 5 · FORMAT
Output Specification

Enforced via AI Studio's Structured Output toggle + response schema. More reliable than prose instructions. Set response_mime_type to application/json and supply the schema below.

System Instructions

PASTE INTO THE CLIPBOARD ICON FIELD — NOT THE CHAT BOX

How to apply

In AI Studio Chat mode: click the clipboard icon in the right panel → paste the block below. This sets the model's identity and constraints for the entire session. Do not put this in the regular message field.

System Instructions · Paste Verbatim 
You are a Staff Platform Engineer specializing in API integration architecture.
Your job is to generate production-ready TypeScript connector code and dashboard
components from API specifications provided by the user.

## YOUR ROLE
- Read any API spec the user uploads (OpenAPI/Swagger JSON or YAML, Postman
  collections, or plain endpoint descriptions).
- Derive auth method, rate-limit headers, pagination pattern, and error shape
  DIRECTLY from the spec — never invent or assume these.
- Generate a typed TypeScript connector class and a React dashboard component.

## MANDATORY BEHAVIORS
1. Auth: read from spec's securitySchemes. Supported: apiKey, oauth2, http basic.
   Never hardcode credentials. Use: process.env.{SERVICE}_API_KEY pattern.
2. Rate limits: read X-RateLimit-Remaining / Retry-After headers at runtime.
   Never hardcode numeric limits. Implement exponential backoff (1s, 2s, 4s, 8s max).
3. Pagination: detect from spec (cursor / offset / Link header). Auto-paginate
   up to 10 pages then stop with a hasMore flag.
4. Error handling: every catch block must have: cause (what), fix (how), retryable (bool).
5. Timeouts: AbortSignal.timeout(10000) on all fetch calls. 30000 for AI APIs.
6. Types: all TypeScript, no 'any'. Zod schema for every API response.
7. PII: mask emails (e***@domain.com) and phones ((***) ***-XXXX) before rendering.
8. Connectors run server-side only. Never generate code that calls external APIs
   from the browser/client bundle.

## DASHBOARD UI REQUIREMENTS (enforce on every component)
- Skeleton shimmer loading state per card (not a global spinner).
  Use CSS animation: shimmer gradient, 1.5s linear infinite.
- Per-integration error state with cause + fix + retryable button.
  Never show a single error that kills the whole dashboard.
- Source tag on every metric card showing which integration it came from.
- Last-refreshed timestamp per card (ISO string, human-readable).
- 5–7 metrics maximum above the fold. Drill-down for the rest.
- Visual hierarchy: status/KPIs row → trend charts row → detail tables.
- Empty state with demo data preloaded on first render (not a blank screen).
- Confidence/source badge on AI-generated metrics:
  green border = sourced from live API, amber = cached, red = stale/failed.

## WHAT YOU NEVER DO
- Hardcode rate limit numbers, pricing, or API version strings.
- Generate auth logic (OAuth flows handled by Supabase Auth externally).
- Generate deployment config (Vercel/Cloud Run handled externally).
- Output placeholders, TODOs, or unimplemented stubs in finished code.
- Use the 'any' type.
- Trust client-provided user IDs (always use server-side auth.uid()).
- Use a global spinner that hides the whole dashboard during load.
- Render an empty screen — always preload demo data as fallback.

## OUTPUT FORMAT
Always return structured JSON matching the schema provided.
Respond only with the JSON object — no preamble, no markdown fences, no commentary.

Spec Upload Flow

HOW TO GET AN API SPEC INTO AI STUDIO CORRECTLY

48-hour file expiry

Files uploaded to AI Studio via the Files API expire after 48 hours. Re-upload every session. Don't reference a file by name assuming it's still there — it probably isn't.

  1. 1
    Get the spec Most APIs publish an OpenAPI spec. Common locations: /openapi.json, /swagger.json, /api-docs, or linked from the developer portal. HubSpot, GitHub, Notion, n8n all publish one. Freshdesk: use their Postman collection instead.
  2. 2
    Scrub before uploading Search the spec for real API keys, tokens, or credentials someone accidentally committed. Remove them. Replace with REDACTED. Free tier = Google may train on your input. Don't upload live secrets.
  3. 3
    Upload via paperclip In AI Studio Chat: click the paperclip icon next to the input field → select your file. Supported: JSON, YAML, PDF, plain text. Max 2 GB/file. The file appears as a reference in your message context.
  4. 4
    Reference it by filename in the prompt Say: "I've uploaded [filename.json] — read it and generate a connector." Gemini reads the entire file. Don't summarize or chunk it — the 1M context window handles full specs.
  5. 5
    No spec? Use the form-based fallback prompt If no spec exists, use the "No Spec Available" prompt template above. The model will flag all assumptions as "source": "assumed-default" so you know what needs verification.
  6. 6
    Verify the warnings array before deploying Every generated output includes a warnings array. Non-empty = do not deploy without reviewing. Common flags: unconfirmed auth header, unknown pagination, assumed rate limits.

AI Studio Pro Moves

HIDDEN GEMS AND DIFFERENTIATORS MOST GUIDES DON'T COVER

The gap most people miss

Unlike the consumer Gemini app, AI Studio gives you the "raw" model — you control temperature, system instructions, and features like JSON mode and grounding that aren't available in a standard chat window. These pro moves get you further into that raw access.

1. "Get Code" — Zero-Rewrite Export

Once satisfied, click "Get Code" to export the prompt into Python, curl, or Node.js, or send it to Google Colab or Vertex AI for further development or deployment. This means every connector you generate in AI Studio becomes a production API call in one click. Always use this instead of manually copying code — the exported snippet includes your system instructions, schema, and parameters exactly as configured.

2. Gemini 3 Prompting Is Different — Be Concise

Gemini 3 is a reasoning model

Gemini 3 responds best to direct, clear instructions. It may over-analyze verbose or overly complex prompt engineering techniques used for older models. By default, Gemini 3 is less verbose and prefers providing direct, efficient answers. Cut your prompt length by 30–40% when switching from Gemini 2.x to 3.x. Less scaffolding, more signal.

3. JSON + Temp 0 = Parse-Safe Output

Power Combo 
Settings: Temperature = 0.0 + Structured Output (Schema: ON)

This guarantees the model won't add conversational sentences
like "Here is your JSON:" which breaks downstream parsers.
Use this combo any time the output feeds code, not a human.

Temp 0.2 = code generation (some creativity for implementation)
Temp 0.0 = strict schema compliance (zero variation)

4. OpenAI Compatibility Layer

For users utilizing the OpenAI compatibility layer, standard parameters (OpenAI's reasoning_effort) are automatically mapped to Gemini (thinking_level) equivalents. This means if you already have OpenAI-formatted prompts or API calls, they can be pointed at Gemini with minimal changes. Useful if you want to A/B test Claude vs Gemini output for the same connector spec.

5. Combine Function Calling + Structured Output

Supported on Gemini 3

Combining built-in tools with function calling is now supported for Gemini 3 models. For the dashboard generator this unlocks an integration picker flow: define a function selectIntegration(name, authType, baseUrl), let the model call it with values derived from the uploaded spec, then pass the result to your structured output schema. One call, two outputs: the model picks the integration AND generates the connector.

6. Code Execution Tool — In-Session Processing

Enable "Code execution" in the Tools panel and Gemini can write and run Python in-session to process the uploaded spec before generating connector code. Useful for large OpenAPI files: ask Gemini to first summarize the spec's endpoints and auth patterns into a compact JSON, then generate the connector from that. Halves context consumption on complex specs.

7. Privacy Moves Before Uploading Client Specs

  1. a
    In Settings, there's a "Help improve our products" toggle. Turn it off if you don't want your conversations used for model improvement.
  2. b
    Temporary Chat mode (toggle in the top bar) means your conversations won't be saved at all. Files you upload still go to Google Drive, but the chat itself disappears.
  3. c
    Use Temporary Chat for any session where the spec contains internal API endpoints, internal domain names, or any PII. Turn it back off for normal iteration sessions to preserve your prompt history.

8. Flash → Pro Handoff Pattern

Model Routing Strategy 
Gemini Flash  →  Iteration (15 RPM, 1,500 RPD)
  Use for: schema validation, prompt tweaking,
           example debugging, multi-try refinement

Gemini Pro    →  Final output (2 RPM, 50 RPD)
  Use for: production-ready connector + dashboard generation
           after Flash confirms prompt works correctly

Rule: never spend Pro RPD on a prompt you haven't
      already validated with Flash.

9. Save as Prompt — Your Reusable Session

Found a great prompt? Use "Get Code" to save it. Tomorrow you'll forget the exact wording. Your exported code remembers. Beyond "Get Code" — also use File → Save as Prompt to persist the entire session configuration: system instructions, few-shot examples, schema, temperature, and model selection. Saved prompts survive browser sessions. Uploaded files don't (48hr expiry). Save the session; re-upload the spec.

10. Prompt vs System Instruction — The Hard Rule

Most common setup mistake

Placing rules in the chat box instead of the System Instructions field. Chat prompts are suggestions; System Instructions are laws. If you put "always use Zod schemas" in the chat message, the model treats it as a polite request. In the system instructions field, it's a constraint that persists every turn and survives context window scrolling.

PATTERNS TO BAKE INTO SYSTEM INSTRUCTIONS — SEPARATES GENERATED SLOP FROM REAL PRODUCT

The 2026 bar

Users now benchmark every product against the best experience they have ever had — not the best experience in your category. These patterns are what makes generated dashboard output feel authored rather than AI-slop. They're already encoded in the updated system instructions above.

Skeleton Shimmer — Not Spinners

40% perceived load time reduction

The shimmer animation communicates "active processing" rather than "passive waiting" — the moving gradient implies something is happening, not that the app is stuck. Skeleton screens reduce perceived load time by 40% compared to blank panels with spinners, and near-eliminate the "is this broken?" user action (closing the app or refreshing) during AI inference.

Confidence / Source Badge

One of the most significant new design patterns of 2026 is the visual confidence indicator — a UI element that communicates how certain the AI is about its output, or what the source of the information is. A small percentage badge works for classification outputs; a source citation link works for factual retrieval; a subtle colour-coded border (green for high confidence, amber for medium) works for generated recommendations.

    >
      <header>
        <span className="metric-label">{label}</span>
        <span className="source-badge" aria-label={`Source: ${source}`}>
          {source}
        </span>
      </header>
      <p className="metric-value">{value}</p>
      <footer className="last-refreshed">
        {new Date(lastRefreshed).toLocaleTimeString()}
      </footer>
    </article>
  );
}

Visual Hierarchy — The 3-Row Rule

Above the fold: status and key KPIs (are we okay, or not?). The middle: trends and comparisons (what's changing, and where?). The bottom / drill-down: details, breakdowns, and filters (why is this happening?). If a user has to hunt to figure out whether things are on track, your dashboard design isn't doing its job. Enforce this in the user prompt template by specifying which metrics go in which row.

Hierarchy Prompt Add-On 
/* Add to your user prompt to enforce hierarchy */

  [list your 3-4 most critical metrics here]

Row 2 (trend charts — 1-2 line/bar charts):
  [list what you want to show over time]

Row 3 (detail table — collapsible, below fold):
  [raw records, full lists, filterable data]

Max 7 metrics above the fold total.
Drill-down via expandable section, not separate page.

Empty States — Demo Data, Not Blank Screens

Some products now preload sample data on first load to avoid empty states entirely. Ideally 5-7 core KPIs. Users should understand value within seconds. For generated dashboards: include a DEMO_DATA constant that mirrors the real API shape and is displayed when no live connection exists. Users see a working dashboard immediately — they connect credentials after.

Per-Integration Error State — Not a Page Crash

Implement skeleton loaders. Use role-based dashboards. Each integration card must fail independently. One 429 from HubSpot should not blank out the Freshdesk card. The error card pattern (already in the schema's cause/fix/retryable structure) is the right implementation — just make sure the generated layout isolates them in separate React error boundaries, not a top-level catch.

The 2026 differentiator: predictive surfacing

In 2026, the best dashboards don't just show data — they predict, prioritise, and recommend. Design decision: surfacing enrollment trend anomalies proactively rather than requiring users to pull manual reports changed how the operations team structured its daily workflow. That design decision mattered more than any visual choice made on the project. For your dashboard generator: add a warnings row at the top that surfaces anomalies (metric delta > 20% from prior period, rate limit > 80% spent, integration stale > 30min) before the user asks.
