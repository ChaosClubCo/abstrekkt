Why Your Agent Is Doing the Wrong Work

Most agent workflows fail at the architecture level, not the prompt level. Here's the pattern.

By Kyle Rosebrook June 2026 Topic Agent Architecture

Most agent workflows fail the same way. One agent, complex brief, and context contamination that compounds until the output is expensive garbage.

You give a general-purpose agent a multi-part task. It starts on part A. While working, it reads context for part B. Part B's context bleeds into part A. The output for A is now built on assumptions about B. You fix it, feed it back, and the cycle runs again.

This isn't a model failure. It's an architecture failure. You built a generalist when you needed specialists.

Sub-agents vs. agent teams

The difference is the communication pattern.

Sub-agents report back to a central coordinator. One hub, multiple workers. Tasks go out, results come back in. The coordinator's context holds everything.

Agent teams communicate directly with each other. Specialists can interrogate each other's outputs before proceeding. No single context holds all the noise.

Both patterns are correct in different situations. Neither is universally better.

Use sub-agents when
Tasks are sequential with clear handoff points. Each task produces a defined output the next one consumes. Context contamination between tasks is your primary risk.
Use agent teams when
Tasks can run in parallel without step-sequencing. Specialists need to interrogate each other's work before acting. A reviewer needs to see the researcher's output before the builder proceeds.

The three-agent pattern in practice

For most research-plus-build tasks, I use a three-agent setup.

  • Researcher — pulls external data through MCP connectors, deposits structured output. Sees nothing from the builder's context.
  • Builder — acts on structured research output. Sees nothing of the raw research. Context stays focused on the build.
  • Reviewer — reads output from both. Flags conflicts before anything gets committed. Produces nothing executable.

The Researcher never sees the Builder's code. The Builder never sees the Researcher's raw notes. The Reviewer sees both but produces nothing autonomous. Each agent's context window stays focused on the thing it's actually responsible for.

This isn't sophisticated agent design. It's basic scope management applied to agents instead of functions.

# settings.json — enable agent teams
{
"experimental": {
"agentTeams": true
},
"permissions": {
"allow": ["read", "git", "test"],
"deny": ["delete", "install", "**/.env"]
}
}

Context rot in agentic workflows

Long agent sessions degrade. At 85-90% context capacity, instruction primacy fades. The agent starts dropping constraints you set two hours ago. It hallucinates file paths. It becomes agreeably wrong.

In an agent team, this happens per-agent. A Researcher that's been running too long will start producing lower-quality output independently of what the Builder is doing. You manage context at the agent level, not just the session level.

  • Set handoff states explicitly between agents rather than letting context accumulate
  • Use /compact on long-running agents before they hit capacity
  • Structure agent.md so each agent has clear scope boundaries — what it owns and what it passes

On permissions — the part people skip

An agent that doesn't need to delete files should not have permission to delete files.

That sentence is obvious. It's violated constantly in production builds because permission management feels like overhead when you're moving fast. It stops feeling like overhead when an agent deletes the wrong thing with high confidence at 2am.

Scope permissions to what each agent actually needs. The Researcher needs read and web access. The Builder needs read and write. The Reviewer needs read only. None of them need delete.

What this means for client builds

When I'm scoping an AI implementation, the agent architecture conversation happens before the tooling conversation. What tasks genuinely benefit from parallelism? Where are the real handoff points? What context needs to persist across the session versus what gets cleared between agents?

The clients who treat these as engineering decisions end up with systems that work reliably at scale. The ones who treat it as a prompting exercise end up with demos that don't survive contact with real workloads.

The technology is available. The architecture decisions are what separate reliable agent workflows from expensive experiments.

Get the architecture right first. The prompts are the easy part.
