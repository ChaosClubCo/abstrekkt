The Six Phrases Are Primitives

The advice is correct the way a map is correct. The production constraints aren't on it.

Three sessions ago I parallelized four sub-agents on a codebase analysis. Wall-clock time dropped by two-thirds. The invoice was four times what the sequential run would have cost. Nobody mentioned that part in the video.

Or: you watched the tutorial. You wrote down the six phrases. You tried them. Some worked. The ones that didn't failed silently — plausible output, wrong by a measure you didn't think to check. The 80/20 automation that passes the taste test still breaks on the edge cases the initial run didn't cover.

The phrases are real. They're starting moves in a system, not the system itself. Here's the production layer that belongs under each one.

· · ·
Phrase 01 — "Launch Sub-Agents"

This is a dependency problem before it's an execution problem

The speedup is real. For genuinely independent tasks, parallel execution drops wall-clock time by 60–80%. That number holds. The constraint that number omits: cost scales linearly with agent count. Three parallel Sonnet agents costs roughly three times the sequential run. The wall clock improves. The invoice doesn't.

Beyond cost: sub-agents are isolated by design. They run, return a summary, close. They cannot communicate during execution. If Agent A's output should change what Agent B does mid-flight, that routing doesn't exist. You'd have to wait for A, process the result, then dispatch B. That's sequential. And if two agents write to the same file, you get a conflict, not a merge — give each agent ownership of distinct files or directories before you start.

The decision gate

Before spawning: Are these tasks genuinely independent — no shared write targets, no dependency between outputs? Is each task complex enough to justify spawning overhead (~3–5 seconds and a few hundred tokens per agent)? Is tripling token spend acceptable for this job? Yes to all three: parallelize. One no: sequence it.

The highway analogy holds until you add the lane count and the toll.

· · ·
Phrase 02 — "Write Me an Implementation Spec"

The spec needs an adversarial pass before the build starts

Spec before build is correct. The model surfaces its interpretation before it writes code. Wrong assumptions show up in the spec, not the implementation. This is worth doing every time.

What the advice skips: the model generated the spec, so it will review the spec with the same blind spots it used to write it. You need a second pass specifically designed to find problems.

Prompt one: write the spec. Prompt two: "Act as an adversarial engineer. Find every place this spec is ambiguous, makes an assumption that could be wrong, or leaves a failure mode unaddressed." Resolve the conflicts before the first line of code exists.

A spec the model generated and the model reviews unmodified isn't a validation step. It's a confidence inflation step.

The adversarial pass is cheap. The bug it prevents isn't.

· · ·
Phrase 03 — "Interview Me"

An interview produces a conversation. You need a contract

The elicitation pattern works. You don't know what you don't know. A good interview surfaces hidden requirements, scope edges, and assumptions you'd discover at bug time. No argument there.

The missing step is the artifact. The interview needs to produce a document — requirements, constraints, done criteria — that gets bound explicitly to every subsequent build prompt. Without the binding, the next session starts from the model's defaults, not the interview's conclusions.

Close the interview with: "Based on everything we just discussed, write a requirements document I can save and reference." Then open every build prompt: "Using the requirements document above as ground truth, implement..."

If the interview ends without a document, the interview didn't happen in any way the build can use.

· · ·
Phrase 04 — "Verify Before You Build"

This means acceptance criteria. Not a CLAUDE.md update

The persistent session file is RAM. Every line costs tokens on every turn. It earns its space by holding things true in every session — architecture, conventions, model selection, global rules. Project-specific verification criteria don't belong there. They're expensive to carry and stop being true the moment the project changes.

What the phrase is actually pointing at: define done before you write the first line. Observable success state. Top failure modes. Smoke test.

Structure the build prompt itself: "Build X. Success if: [specific, measurable]. Failure if: [explicit list]. Include a verification step that confirms [observable output]."

The phrase is right. The mechanism it suggests is a proxy for the actual thing. Write the acceptance criteria into the prompt, not the config file.

· · ·
Phrase 05 — "Build Me a Skill"

The description field is the whole game

Building from real conversations rather than abstract planning: correct, and the most important piece of advice in the original list. Planned skills are generic. Captured skills know what went wrong. The difference is specificity you can't manufacture from theory.

What the advice doesn't say: the description field isn't documentation. It's the routing rule. A vague description fires the skill on everything adjacent to the category. A sharp description fires precisely or not at all.

Community testing across 200+ prompts found that optimizing the description alone moves activation rate from roughly 20% to 50%. Adding concrete trigger examples in the body moves it to 90%. The instructions are the knowledge. The description is the routing. Bad routing makes good knowledge useless.

Write descriptions like a routing rule

Not: "helps with writing tasks." Instead: "activates when drafting LinkedIn posts, hot takes, or professional social content — also fires on 'write a post,' 'draft for LinkedIn,' 'social content,' thread, hook, or engagement." Specific enough that you know exactly which tasks trigger it and which don't.

Also: add a FAIL CONDITIONS section. Not "do this well" — "if the output contains X, the skill failed." The model's default failure mode is confident, average output. The fail condition catches average before it ships. Positive instructions define the target. Fail conditions prevent regression from generic.

· · ·
Phrase 06 — "Automate This"

The 80/20 question doesn't classify risk. You need both

The taste test and the 80/20 filter are reasonable first passes. They're not an architecture. The question missing from both: what happens when the automation fails at scale on a job that matters?

The production decision is risk tier — reversibility, measurability, blast radius:

Tier Profile Pattern
Full auto Reversible · objective criteria · contained blast radius Ship it. Monitor error rate.
Human on the loop Partially reversible · partially objective Process runs. Human monitors. Intervention available but not required.
Human in the loop Irreversible · subjective · wide blast radius Process stops. Human approves. Then continues.

The 80/20 question applies only inside the full-auto tier. For anything touching customers, money, or state you can't roll back, the threshold isn't accuracy — it's error rate monitoring and a defined rollback path before you ship.

Automation without observability is a liability, not a system. The pipeline that breaks silently at 2am on your most important client's workflow isn't a technical problem. It's a trust problem.

Before any automation goes live: what's the failure detection mechanism? How do you know it's breaking? How do you stop it? These questions are easier to answer before deployment than after.

The Pattern Across All Six

The original list treats the phrases as the leverage point. The actual leverage is what surrounds each one — the dependency map before the parallel dispatch, the adversarial review before the build, the bound artifact from the interview, the acceptance criteria in the prompt, the routing-rule description in the skill, the risk tier before the automation decision.

Prompts are operations. Systems have failure modes. The phrase is the starting move.

The system is everything around it.

Gaps

• Cost data for sub-agents varies significantly by model tier, session configuration, task type, and prompt caching. No single source provides a reliable per-task cost model — monitor with actual usage, not estimates.

• Skill activation statistics are community-tested, not Anthropic-published benchmarks. The 90% figure may not hold for narrow or unusual task types.

• The three-tier HITL model doesn't specify confidence thresholds for escalation. Choosing where "medium risk" begins requires domain-specific calibration not covered here.

• The adversarial spec review pattern has no published error-rate data. The claim that it catches problems early is logical, not empirically cited.

• All six patterns are Claude Code-specific unless noted. Portability to other agent frameworks (LangGraph, OpenAI Assistants, Cursor) is unstated and may require adaptation.
