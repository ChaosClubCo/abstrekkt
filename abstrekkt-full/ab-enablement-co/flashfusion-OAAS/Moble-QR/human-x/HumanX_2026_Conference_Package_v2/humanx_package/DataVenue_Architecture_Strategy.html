AWS (Nov 2025): Lambda Tenant Isolation Mode

AWS released native tenant isolation for Lambda in November 2025. This eliminates the need for custom isolation logic in serverless architectures — the platform enforces that execution environments used for individual tenants remain completely separate. Key implications:

  • Compute isolation is now a platform feature, not custom code
  • Same-tenant invocations still benefit from warm execution (no performance penalty)
  • Available in all commercial AWS regions
  • Combined with RDS RLS at the data layer = full-stack tenant isolation without custom vault code

Envelope Encryption with KMS

The recommended pattern for per-tenant encryption on AWS:

  1. Each tenant gets a Key Encryption Key (KEK) in AWS KMS
  2. Data Encryption Keys (DEKs) are generated per-record or per-table
  3. DEKs are encrypted by the KEK and stored alongside the data
  4. To decrypt: retrieve encrypted DEK → KMS decrypts DEK using KEK → DEK decrypts data
  5. DEK rotation doesn't require re-encrypting all data — only re-wrap the DEK

This is the "Keys-per-Tenant" model — one KMS instance, multiple tenant keys. Cost-effective at scale with full tenant-level key isolation.

INT's Recommended Hybrid Approach

ARCHITECTURE RECOMMENDATION

Silo for HIPAA/regulated clients (separate RDS instances, dedicated KMS keys, VPC isolation). Pool for standard clients (shared PostgreSQL with RLS, IAM-scoped access, CloudTrail audit). Bridge as migration path — start Pool, graduate to Silo when compliance requires it.

This hybrid approach maps directly to an MSP pricing model: Pool clients pay $2K/mo, Bridge clients pay $3.5K/mo, Silo clients pay $5K+/mo. Compliance requirements drive tier selection, not arbitrary upselling.

Skyflow — Deep-Dive

Data Privacy Vault architecture, LLM integration, and MSP relevance

Architecture

Skyflow implements the Data Privacy Vault pattern (originated by Apple, Netflix, Google — now IEEE-recommended). Core architecture:

  • Isolate: Vault is segregated from customer infrastructure, accessible only through privileged API access
  • Protect: Polymorphic encryption — multiple encryption types tailored per data type, supports operations on encrypted data without decryption
  • Govern: Policy-Based Access Control (PBAC) combining RBAC + ABAC, row-level security, audit logging
  • Use: Tokenization replaces PII with opaque tokens; deterministic tokens preserve referential integrity across systems

LLM Privacy Vault Pattern

Most relevant to Data Venue's "AI data exposure" requirement:

  1. User input → Skyflow de-identifies sensitive data, stores plaintext in vault, replaces with deterministic tokens
  2. Tokenized input → sent to LLM (no PII reaches the model)
  3. LLM response with tokens → Skyflow re-identifies authorized tokens based on governance policies
  4. Clean response with appropriate PII → returned to user

This preserves referential integrity — the LLM can reason about "Customer_A_Token_123" consistently without ever seeing the actual PII.

Commvault Data Rooms — Deep-Dive

Backup-to-AI activation — GA early 2026

What It Is

Commvault Data Rooms transforms backup data — one of the most complete and trusted datasets an organization owns — into AI-ready assets. Launched October 2025, targeting early 2026 GA. This is the "backup-to-AI" paradigm the original Conference Playbook referenced.

Architecture

  • Discovery: Automated data discovery + classification across on-prem and cloud backup repositories
  • Governance: Policy-based redaction, sensitivity tagging, audit trails — all within zero-trust architecture
  • Curation: Self-service workspace for preparing governed datasets
  • Export: AI-ready formats — Apache Parquet, Apache Iceberg — to Snowflake, Azure, data lakes
  • Security: RBAC, encryption at rest + in transit, traceable from backup to activation

Key Differentiation

COMMVAULT'S APPROACH VS. SKYFLOW

Skyflow: PII never leaves the vault. Tokens go to applications. The vault IS the system of record.

Commvault: Data leaves backup (governed) → exported to AI platforms. The backup IS the trusted source. Data Rooms is the preparation layer, not the execution layer.

These are complementary, not competing. Commvault activates historical data for AI. Skyflow protects PII during AI inference. An MSP could deploy both.

MSP Relevance

If INT's MSP clients already use Commvault for backup (common in the MSP market), Data Rooms is the lowest-friction path to "AI-ready data." Schema & RLS Policies

Production-pattern database design for the PoC

Core Schema

-- Tenant registry
CREATE TABLE tenants (
  id          uuid PRIMARY KEY DEFAULT gen_random_uuid(),
  name        text NOT NULL,
  slug        text UNIQUE NOT NULL,
  tier        text CHECK (tier IN ('pool', 'bridge', 'silo')),
  compliance  text[] DEFAULT '{}',  -- e.g. {'hipaa','soc2'}
  created_at  timestamptz DEFAULT now()
);

-- Client data (multi-tenant, RLS-protected)
CREATE TABLE client_records (
  id          uuid PRIMARY KEY DEFAULT gen_random_uuid(),
  tenant_id   uuid REFERENCES tenants(id) NOT NULL,
  category    text NOT NULL,
  data        jsonb NOT NULL,
  pii_flag    boolean DEFAULT false,
  created_at  timestamptz DEFAULT now(),
  updated_at  timestamptz DEFAULT now()
);

-- Audit log (append-only)
CREATE TABLE audit_log (
  id          bigint GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
  tenant_id   uuid NOT NULL,
  user_id     uuid,
  action      text NOT NULL,  -- 'SELECT','INSERT','UPDATE','DELETE','AI_QUERY'
  table_name  text,
  record_id   uuid,
  metadata    jsonb DEFAULT '{}',
  ip_address  inet,
  created_at  timestamptz DEFAULT now()
);

RLS Policies

-- Enable RLS on tenant-scoped tables
ALTER TABLE client_records ENABLE ROW LEVEL SECURITY;

-- Policy: users can only see records for their tenant
-- auth.jwt() ->> 'tenant_id' reads tenant from Supabase JWT
CREATE POLICY "tenant_isolation" ON client_records
  FOR ALL
  USING (
    tenant_id = (auth.jwt() ->> 'tenant_id')::uuid
  )
  WITH CHECK (
    tenant_id = (auth.jwt() ->> 'tenant_id')::uuid
  );

-- Policy: audit log is append-only (insert only, no update/delete)
ALTER TABLE audit_log ENABLE ROW LEVEL SECURITY;

CREATE POLICY "audit_insert_only" ON audit_log
  FOR INSERT
  WITH CHECK (
    tenant_id = (auth.jwt() ->> 'tenant_id')::uuid
  );

CREATE POLICY "audit_read_own" ON audit_log
  FOR SELECT
  USING (
    tenant_id = (auth.jwt() ->> 'tenant_id')::uuid
  );

Audit Trigger

-- Auto-log every data access to audit_log
CREATE OR REPLACE FUNCTION log_data_access()
RETURNS TRIGGER AS $$
BEGIN
  INSERT INTO audit_log (tenant_id, user_id, action, table_name, record_id, metadata)
  VALUES (
    COALESCE(NEW.tenant_id, OLD.tenant_id),
    (auth.uid()),
    TG_OP,
    TG_TABLE_NAME,
    COALESCE(NEW.id, OLD.id),
    jsonb_build_object(
      'timestamp', now(),
      'operation', TG_OP
    )
  );
  RETURN COALESCE(NEW, OLD);
END;
$$ LANGUAGE plpgsql SECURITY DEFINER;

CREATE TRIGGER audit_client_records
  AFTER INSERT OR UPDATE OR DELETE ON client_records
  FOR EACH ROW EXECUTE FUNCTION log_data_access();

API & AI Orchestration Layer

Tenant-scoped AI query pattern for the PoC

Middleware: Tenant Context Extraction

// middleware/tenantContext.ts
import { createClient } from '@supabase/supabase-js';
import { NextRequest } from 'next/server';

export async function getTenantContext(req: NextRequest) {
  const token = req.headers.get('authorization')?.replace('Bearer ', '');
  if (!token) throw new Error('No auth token');

  // Decode JWT to extract tenant_id claim
  const payload = JSON.parse(
    Buffer.from(token.split('.')[1], 'base64').toString()
  );

  if (!payload.tenant_id) throw new Error('No tenant context');

  // Create tenant-scoped Supabase client
  const supabase = createClient(
    process.env.SUPABASE_URL!,
    process.env.SUPABASE_ANON_KEY!,
    { global: { headers: { Authorization: `Bearer ${token}` } } }
  );

  return { tenantId: payload.tenant_id, supabase, userId: payload.sub };
}

AI Query Endpoint (Tenant-Scoped)

// app/api/ai-query/route.ts
import { getTenantContext } from '@/middleware/tenantContext';
import { NextRequest, NextResponse } from 'next/server';

export async function POST(req: NextRequest) {
  const { tenantId, supabase, userId } = await getTenantContext(req);
  const { query } = await req.json();

  // 1. Fetch tenant-scoped data (RLS enforces isolation)
  const { data: records, error } = await supabase
    .from('client_records')
    .select('*')
    .textSearch('data', query, { type: 'websearch' })
    .limit(20);

  if (error) return NextResponse.json({ error }, { status: 500 });

  // 2. Log the AI query to audit trail
  await supabase.from('audit_log').insert({
    tenant_id: tenantId,
    user_id: userId,
    action: 'AI_QUERY',
    table_name: 'client_records',
    metadata: {
      query,
      records_accessed: records?.length || 0,
      timestamp: new Date().toISOString()
    }
  });

  // 3. Build context for AI (tenant data only)
  const context = records?.map(r => JSON.stringify(r.data)).join('\n');

  // 4. Call AI with tenant-scoped context
  const aiResponse = await fetch('https://api.anthropic.com/v1/messages', {
    method: 'POST',
    headers: { 'Content-Type': 'application/json' },
    body: JSON.stringify({
      model: 'claude-sonnet-4-20250514',
      max_tokens: 1000,
      system: `You are analyzing data for tenant ${tenantId} only.
               Do not reference or infer data from other tenants.`,
      messages: [{ role: 'user',
        content: `Context:\n${context}\n\nQuery: ${query}`
      }]
    })
  });

  const ai = await aiResponse.json();
  return NextResponse.json({
    answer: ai.content[0].text,
    records_accessed: records?.length,
    tenant_id: tenantId,
    audit_logged: true
  });
}
IMPORTANT CAVEAT FOR HUMANX CONVERSATIONS
This PoC demonstrates the pattern — tenant-scoped data retrieval → audit logging → AI inference with isolated context. In production, you'd add: input sanitization (DOMPurify + Zod), rate limiting per tenant, token budget controls, PII detection/redaction before LLM calls (this is where Skyflow's LLM Privacy Vault adds value), and response filtering. The PoC intentionally omits these to keep the demo clear and focused on isolation mechanics.
