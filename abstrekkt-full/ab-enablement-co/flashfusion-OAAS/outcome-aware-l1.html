I built a maturity model for outcome-aware AI. Then I walked my own work through it.

By Kyle Rosebrook

I'm an L1 service desk tech who builds AI work on the side. I spent some time writing a five-level diagnostic for how mature an MCP-using system is at verifying its own outcomes. The first thing I did with it was walk my own service desk operation through the rubric.

I scored L1.

Out of five levels. The lowest one. The "tools deployed, outcomes unknown" tier.

That's not the result I wanted. It's the result that's true.

What the framework checks

The thesis is small and concrete. Most current work on MCP servers is tool-side — more servers, more connectors, more capabilities. Almost none of it is outcome-side. When an MCP server says "I updated the page," there is no standard way to verify the page actually changed. Most observability stops at "the call succeeded" — HTTP 200, no exception thrown. That is not an outcome. It is an absence of error.

The framework has five levels:

  • L1 Output-only. Tools deployed. Outcomes unknown.
  • L2 Tracked. Tool calls logged with coherent metadata.
  • L3 Claimed. Tool wrappers emit structured receipts of what changed.
  • L4 Verified. Claims are independently probed against the world.
  • L5 Optimizing. Verdict signals feed back into how the system runs.

Paired with each level is a catalog of anti-patterns that pin teams in place. Tool Sprawl pins you at L1. Trust-Me Telemetry and Phantom Determinism pin you at L2. The universal anti-pattern across every level is Outcome Theater — dashboards that say "outcomes" while showing call counts and latencies.

What my own desk showed

I ran the rubric on a managed-services L1 operation. About thirty client endpoints. Standard MSP stack — ITSM platform, RMM agent, EDR, softphone, VPN, MFA. AI work on the side: a couple of custom MCP servers, n8n bridging webhook events, a coding assistant on the operator's machine.

The L1 qualifier passed easily. Tools are deployed. Of course.

The L2 questions are stricter than they look. "Is every tool call logged with consistent metadata?" Partial — three logging surfaces with no run_id correlating across them. "Do tool failures surface within five minutes?" No. Failures are discovered when a ticket ages past SLA. Median time-to-notice: fifteen to forty-five minutes.

L2 has four questions. You need four out of four. I scored zero strict, two partial. Not cleared.

L3, L4, and L5 are blocked by L2 anyway, so I stopped there.

The diagnosis: L1 — Output-only. Operative anti-patterns: Tool Sprawl across logging surfaces (not across MCP server count, which is how the catalog originally framed it — useful finding for v0.2). Outcome Theater — the dashboards that exist optimize for ticket lifecycle, not for whether the underlying issue actually got solved. Closed is not resolved. In MSP work, a closed ticket can mean the user stopped responding, or the issue came back as a new ticket on a different endpoint, or the resolution was a workaround that masked the actual cause.

The gap most teams miss

Most teams have some telemetry. They will not self-report L1. They will self-report L2 or L3 because they "have observability." The rubric's four-out-of-four gating is what surfaces the difference between telemetry and coherent telemetry. The difference between "we log things" and "we can answer: what did this agent run actually change in the world."

That gap is operational. It's not about more dashboards. It's about whether the dashboards measure outputs or outcomes — call counts versus world-state changes. Almost every current dashboard, including the ones I've built, measures outputs and calls them outcomes.

That's Outcome Theater. The framework names it because the failure mode is universal.

What's in the repo

The spec is on GitHub. Three combos:

  • 01 Outcome Receipts × Forgery Detector. The assert-verify primitive. Servers emit structured claims; a separate probe layer verifies whether the claim is true.
  • 02 Eval-as-MCP × Sycophancy Telemetry. Runtime anti-sycophancy. A streak counter watches for multi-turn agreement drift and fires an adversarial eval pass when it crosses threshold.
  • 03 Anti-Pattern Catalog × Maturity Model. The diagnostic I ran on my own desk. Five levels, ten anti-patterns, twenty-one yes/no rubric questions.

Combo 03 is content. You can use it today. Combos 01 and 02 are blueprints — schemas and build sequences for someone to implement.

The case study from my own desk is in case-studies/msp-service-desk-l1.md. It's what an honest self-assessment looks like when the framework actually works on you.
