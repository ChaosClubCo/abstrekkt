Claude Code at Ninety Days: What Held

Most of what I built in the first month, I rebuilt in month three. The tool was the same. I wasn't.

I started keeping a list of sessions that produced nothing I shipped. Not failed sessions, sessions where Claude delivered exactly what I asked for and I deleted it anyway. That list got longer than I expected.

Claude Code has been my primary development environment for the better part of this year. I use it daily across both the CLI and the claude.ai project context. The ninety-day window this essay covers is the one where the patterns got specific enough to name.

The Yield

I built fifty Claude skills. About fifteen fire regularly. Thirty percent. That's not a failure rate, it's a yield rate. The distinction matters when you're deciding whether to keep building or stop and audit first.

The dead seventy percent breaks down roughly like this: a third are too narrow (the task comes up quarterly, not daily, not enough reps to justify dedicated encoding), a third are too broad (the description triggers the skill on adjacent tasks it wasn't built for, adding noise to sessions that didn't need it), a third are under-maintained (the instructions were right when I wrote them and the environment shifted since). None of them failed at deployment. They just stopped getting used.

The fifteen that held have something in common: they encode judgment I had already formed before I wrote the skill. Not instructions I drafted to teach the model how to think about something I was still figuring out, instructions I wrote because I already knew exactly how that task should go and wanted to stop repeating the same corrections every session.

Planned skills are the weakest. Captured skills compound. The difference is whether the judgment existed before the skill was written, or whether you were hoping the model would develop it for you.

The thirty percent is an accurate reading of where my own judgment was specific enough to encode versus where I was still negotiating with the problem. The model can't negotiate that for you. It surfaces where the negotiation hasn't happened yet. That's different from doing it.

What Doesn't Ship

The list I was keeping wasn't a failure log.

A production gap session looks like this: I'm building an integration. I ask Claude Code to wire the auth flow against the existing session pattern. It does. Clean code, right idioms, passes lint without a flag. I look at it and delete it. Not because it was wrong, because it handled the happy path and nothing else. The error states aren't there. The retry logic isn't there. The failure mode I've been burned by twice in this codebase wasn't in the prompt, so it's not in the output.

The model delivered exactly what I asked for. I asked for the wrong thing. Those are different problems that look identical in the session log.

The model built what you asked for. You asked for the wrong thing. It will never tell you that's what happened.

The hard part is that production gap output is plausible. It passes the taste test. You have to run it against something real, against the error states, against the edge cases that live in your head and nowhere else, to find that the floor isn't there. By then you've already spent the session.

The list I was keeping was tracking this: how often I arrived without a complete picture of what I needed, let the model generate against an incomplete frame, and deleted the output when the incompleteness surfaced. The answer was: often enough to be the main pattern worth fixing.

Context Is Architecture

The one change that made the sessions that followed more useful: I stopped treating each session as a fresh task and started treating it as the next turn in a known architecture.

In practice, three layers, each doing a different job:

What loads and when
CLAUDE.md
Always loaded. Stack, conventions, global constraints. The stuff that's true in every session.
Skills
Loaded on trigger. Specific workflows for specific tasks. Only worth writing when the judgment already exists.
Session context
Loaded manually, per session. The task-specific frame: spec, failure modes, definition of done. This is the layer that was missing on the deleted-output list.

The model doesn't remember the previous session. The architecture around the model does. CLAUDE.md isn't a configuration file, it's a persistent context layer. Keeping it current is the discipline. The deleted-output list got shorter when I took that seriously. Not because the model improved. Because the sessions started better.

"1" in the stats row is the count on changes that materially affected output quality across the ninety days. Everything else was tuning on top of a broken layer. This was fixing the layer.

What the Model Doesn't Know

Claude Code is faster than anything I've used for implementation work. It is not smarter about what to implement. That distinction carries more weight than most of what gets written about the tool.

The sessions that worked were the ones where I arrived with a complete picture: spec, failure modes, edge cases, definition of done. Sessions on the deleted-output list were the ones where I was still figuring out what I needed while the model was generating against whatever frame I'd given it. The model optimized toward plausible output on the frame. When the frame was thin, the output was plausible and wrong.

A senior engineer using this well doesn't get more output. They get earlier signal on where the spec was thin. The tool reveals where your thinking is underdeveloped. Quickly. That's not a limitation, it's the most useful thing it does, once you stop expecting it to substitute for thinking you haven't done yet.

The tool can build anything you can describe precisely. After ninety days, that's still the limit.

The skill is a file. The judgment layer is what you built before you opened Claude Code. Ninety days confirms which one you actually had.

Gaps

• The 90-day window spans a model string change (claude-sonnet-4-20250514 → claude-sonnet-4-6, June 15 2026). Any quality observations that span that boundary have a possible confound I can't isolate.

• All counts are approximate. Claude.ai doesn't expose session-level usage analytics. The thirty-percent figure is a count I made manually from memory and spot-checks, not from a dashboard.

• The production gap pattern is specific to my work during this window: solo development on production stacks, mix of CLI and project context, Sonnet as the primary model. Different task types, greenfield exploration, pure documentation, analysis work, may show different patterns.

• Doesn't cover sub-agent or multi-agent workflows. That's a different cost and quality profile that deserves its own window and its own essay.

• The context architecture prescription worked for how I work. Someone running greenfield prototypes with less accumulated codebase context has a different starting problem.
