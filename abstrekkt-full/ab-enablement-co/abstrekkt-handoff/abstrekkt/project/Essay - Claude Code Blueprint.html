The Claude Code Blueprint Nobody Posts

Five cheatsheets went viral this month. Here's what they get right, what they skip, and what my actual project structure looks like after 50+ skills and six months of production use.

Every week, a new Claude Code infographic hits LinkedIn. Perfect folder trees. Color-coded architecture diagrams. Clean terminal screenshots where nothing is broken.

They're not wrong. Most of them are describing real features, CLAUDE.md, skills, hooks, MCP configs, agents. The problem is they're describing the menu, not the meal. The distance between "here's the folder structure" and "here's what happens when you actually use it for six months" is where every interesting lesson lives.

I've been running Claude Code across multiple projects since late 2025. I have 50+ skills in active rotation. I've broken things that the cheatsheets don't warn you about. Here's what I've learned, organized around the five things everyone keeps posting, and where I disagree.

1. CLAUDE.md: Keep It Under 200 Lines Is Wrong

The most common advice: keep your CLAUDE.md short. Under 200 lines. "Claude loads it at session start, so keep it lean."

Where I disagree
The 200-line rule optimizes for the wrong thing. It treats CLAUDE.md like a config file instead of what it actually is: persistent memory for an agent that forgets everything between sessions. If your CLAUDE.md is short, your Claude Code sessions start cold every time. You re-explain the stack, re-explain the conventions, re-explain the gotchas. That's not efficiency. That's amnesia tax.

What actually matters is information density per line, not line count. A 400-line CLAUDE.md that prevents five minutes of re-prompting per session pays for itself in the first week. A 50-line CLAUDE.md that reads like a README helps nobody.

My approach: CLAUDE.md carries the hard rules, stack, conventions, security constraints, testing patterns, and the things Claude gets wrong repeatedly. Everything else goes into skills (which load on-demand and don't burn context until triggered).

2. Skills Are the Actual Superpower (But Most Guides Undersell Them)

The cheatsheets all mention skills. "Markdown files that Claude auto-invokes." Correct. What they skip: skills are the difference between Claude Code as a fancy autocomplete and Claude Code as a system that compounds your judgment over time.

What the guides get right
The description field is critical for auto-activation. If your description is vague ("helps with testing"), the skill won't fire when it should. Pushy, specific descriptions with trigger phrases make skills reliable.

What they miss: skills encode your mistakes, not just your process. Every time Claude gets something wrong and I correct it, the fix goes into a skill, not as a positive instruction, but as a gotcha with a FAIL condition. "If the output contains X, the skill failed." That's what makes the system learn. The cheatsheets show you the folder structure. They don't show you the correction loop that makes it work.

After 50+ skills, the pattern is clear: the best skills aren't the ones I planned. They're the ones I captured retroactively after watching Claude make the same mistake three times.

3. Hooks: The Safety Net Nobody Configures

Boris Cherny's CLAUDE.md file (one of the images that prompted this post) gets something right that most guides skip: verification before done. Never mark a task complete without proving it works.

Hooks are the enforcement mechanism for this. PreToolUse hooks can block dangerous operations. PostToolUse hooks can auto-lint after every write. But here's the gap in every cheatsheet I've seen: none of them address the compliance problem.

The compliance gap
Hooks designed for Claude Code (which runs in a terminal with real shell access) don't work the same way in claude.ai's skill system. If you're building skills for Cowork or claude.ai projects, hooks that reference shell scripts will silently fail. Your safety net has holes you can't see. I learned this by deploying skills that "worked" in testing and silently skipped enforcement in production.

The fix: separate your skill library into "Claude Code native" and "claude.ai portable" categories. Test each in its target environment. Don't assume a skill that works in one context transfers to the other.

4. Project Structure: What You Actually Need vs. What Looks Good on a Poster

The production-ready app diagram (tiltit.video) is the most honest of the batch. It shows a real Next.js project with real infrastructure, Supabase, Stripe, PostHog, Sentry, GitHub Actions. That's what a shipping project looks like.

But it's also a specific project. Here's what I'd change for a multi-project setup where Claude Code works across different codebases:

What I actually use

project/
├── CLAUDE.md              # Hard rules, stack, conventions (>200 lines, sue me)
├── .claude/
│   ├── settings.json      # Permissions, model, hook registry
│   ├── settings.local.json # My machine only (.gitignored)
│   ├── skills/            # Auto-activated markdown packs
│   │   ├── skill-name/
│   │   │   ├── SKILL.md
│   │   │   └── references/  # Supporting docs the skill can read
│   │   └── ...
│   ├── commands/          # Slash commands (legacy but still useful)
│   └── agents/            # Subagent definitions (own context window each)
├── .mcp.json              # MCP server configs (root only, never nested)
└── src/                   # Actual code

The key differences from the poster versions:

⚡
settings.local.json is non-negotiable Personal overrides that never touch git. API keys, local paths, dev-only permissions. Every cheatsheet mentions .gitignore. Almost none mention settings.local.json specifically.
⚡
Skills get references/ subdirectories A skill that needs to read a 3-page API reference shouldn't embed it inline. Put supporting docs in references/ and the skill reads them on-demand. Keeps the SKILL.md focused on decision logic.
⚡
.mcp.json stays at root MCP configs don't nest. One file, one place. The moment you start splitting MCP configs across subdirectories, you introduce a debugging nightmare where Claude connects to the wrong server.

5. The Self-Improvement Loop Is the Whole Point

Boris Cherny nails this and most other guides miss it entirely. After any correction from the user, update a lessons file. Write rules that prevent the same mistake. Review lessons at session start.

This is the only thing that separates Claude Code from a chatbot. Without the correction loop, you have a very fast typer. With it, you have a system that gets measurably better over weeks.

My implementation: every skill has an implicit fail condition. When Claude produces output that trips the fail condition, I don't just fix the output, I update the skill with a new GOTCHA entry that describes the failure mode. The next time the skill fires, the gotcha is in context. The mistake rate on that specific pattern drops to near-zero.

The cheatsheets show you the architecture. The correction loop is the engine.

The Bottom Line

Five viral infographics, and the most important lesson isn't in any of them: Claude Code's value isn't in the folder structure. It's in the judgment you encode into it over time. The structure is scaffolding. The skills, hooks, and correction loops are the building.

If your Claude Code setup looks exactly like the cheatsheet, you've built the scaffolding. The question is whether you've started building yet.
