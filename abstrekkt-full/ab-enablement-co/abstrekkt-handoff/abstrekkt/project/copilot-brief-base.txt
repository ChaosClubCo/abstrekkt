# Copilot Build Brief — Abstrekkt Design System Repository

## Project identity
Generate a complete repository for **Abstrekkt**, a parent studio for AI enablement work and the software products it produces. The working title for this design language is "Reading Room at Midnight." This is a dark-first, literary, editorial system — the opposite of a neon SaaS dashboard. It should read like a private library after hours: warm ink backgrounds, a single brass accent, serif display type, generous whitespace, and unhurried pacing. Treat every visual decision through that lens before reaching for a generic web-design default.

Abstrekkt is the parent studio and default surface for shared work. Two sub-lanes exist and must stay visually distinct: **Load-Bearing** (secondary accent forest #1B2B1A, "structural AI for systems that must hold") and **Abstrekkt Products** (interim accent emerald #34d399, used only inside that lane, never elsewhere). A separate, unrelated brand called FlashFusion uses a void/purple/pink/cyan palette — never import any of those colors, gradients, or glow effects into this repository under any circumstance.

## Repository structure to scaffold
Produce the following top-level layout:

- styles.css — the single global entry point that consumers link; it should only contain @import statements pointing at the token files below, nothing else.
- readme.md — documentation describing the system, its sources, and its caveats (mirrors this brief).
- SKILL.md — an Agent-Skills-compatible manifest so the system can be consumed as a Claude Code / Copilot skill.
- tokens/fonts.css — Google Fonts @import rules for Fraunces, Crimson Pro, and JetBrains Mono.
- tokens/colors.css — CSS custom properties for ink, surface steps, foreground, brass, borders, the two sub-brand accents, and semantic aliases (e.g. --color-bg, --color-surface-1, --color-fg-primary, --color-accent-brass).
- tokens/typography.css — font-family variables, the display/body/mono type scale, and named roles (display, body, kicker/label, mono-meta).
- tokens/spacing.css — the 4px base spacing scale (4/8/12/16/24/32/48/64/96/128), corner-radius tokens (2/4/6px, plus a pill token for rare chip cases), and layout width tokens (1200px content container, 720px narrow reading column).
- tokens/effects.css — shadow tokens (shadow-1/2/3, all colorless black at low alpha), the single top-anchored brass radial ambient background treatment, the paper-grain noise overlay (~35% opacity, mix-blend-mode: overlay), and motion tokens (standard ease cubic-bezier(0.2,0,0.2,1), expressive-out ease cubic-bezier(0.16,1,0.3,1), durations 140/260/420ms).
- components/actions/Button.* and components/actions/IconButton.* — primary/secondary/ghost button variants and a stroke-icon-only button.
- components/typography/Display.* and components/typography/Kicker.* — the Fraunces headline component (supports the brass-italic emphasis device inline) and the uppercase JetBrains Mono eyebrow/label component.
- components/surfaces/Card.* and components/surfaces/Rule.* — a raised hairline-bordered surface (with an optional 2px brass left rail) and an editorial divider that can carry a centered brass mono label like a chapter break.
- components/data-display/Badge.* — a small status/tag chip.
- components/forms/Input.* — a text input styled with an inset "pressed into the page" well shadow.
- components/feedback/Callout.* — an inline note/aside block.
- ui_kits/studio/ — a working marketing site with Home, Work, and Enquire views, composed entirely from the primitives above, with an index.html entry point that also serves as a starting-point template.
- guidelines/ — specimen pages for Colors, Type, Spacing, and Brand, suitable for a "Design System" documentation tab.
- Component namespace: export every component under the JS namespace AbstrekktDesignSystem_00b28e so consumers can destructure e.g. const { Button, Card } = window.AbstrekktDesignSystem_00b28e;.

## Color tokens (author these exact values, do not invent new ones)
Base ink is warm near-black, not blue-black: page background #0d0c0a, deepest/footer/vignette #080705. Surfaces step up through three warm greys: #1a1a1d → #232328 → #2c2c33. Foreground text is warm bone #e8e0cc, dimming through secondary #94907e to tertiary #5e5b50. The single accent is brass #C8A86A, with a soft/hover variant #d9bd87, a deep/pressed variant #8B7548, and a 7%-opacity wash rgba(200,168,106,0.07) reserved for tints and highlight fills — brass is punctuation, never a fill color for large areas. Borders come in a hairline #2e2e35 and a strong #3d3d44, plus a distinct warm editorial-rule color #252520 used specifically for chapter-break dividers. Sub-brand accents: Load-Bearing forest #1B2B1A; Abstrekkt Products emerald #34d399 (scoped only to that product lane, nowhere else in the parent studio surface).

## Typography system
Display type is set in Fraunces at an optical size around 144, spanning weights 400–600 with italics available, tight leading (roughly 0.96–1.05), and letter-spacing of -0.02em — this is the dominant house voice and should appear on every hero and section header. Body copy is set in Crimson Pro at 400/500 weight, sized near 15px with 1.65 line-height — tuned for sustained reading, not skimming. Labels, kickers, timestamps, and metadata use JetBrains Mono at 9–10px, uppercase, with 0.22–0.24em letter-spacing, colored brass. Inter exists only as a system fallback stack for the rare case Fraunces/Crimson Pro fail to load — never assign it to a display role, and note in the readme that no Inter font file ships with the system (its fallback stack renders until one is supplied).

## Signature type device: brass italic emphasis
Abstrekkt has exactly one emphasis convention and Copilot should implement it as a reusable inline span/component, not ad hoc styling: within an otherwise plain Fraunces line, the emphasized phrase switches to brass-colored italic. Never use bold, never use underline, never fill an entire headline with color. Example headline construction: "A studio for work that bears weight." renders with "bears weight" in brass italic and the rest in plain Fraunces roman.

## Voice and content rules for any sample copy generated
Write in a quiet, literary, first-person-plural voice ("we build," "we read everything ourselves") that treats the reader as a peer rather than a sales lead. Prefer confident understatement over hype language, complete and sometimes long sentences over choppy fragments, and never use exclamation marks or growth-hacky imperatives ("Sign up now!", "Don't miss out!"). The governing metaphor throughout the product is a library/reading room: work is "kept," projects are "chapters," an index of work is a "shelf." Display and body copy use sentence case; headlines are never Title Case. Meta text, kickers, labels, and button text are uppercase JetBrains Mono with wide tracking (e.g. "FIELD NOTES — 03"). Section indices are zero-padded mono numerals ("01", "03"); use dates and version strings in mono as well. Numbers should appear sparingly and only when they carry real meaning — do not generate vanity metrics, stat blocks, or filler statistics anywhere in sample content. Use "we" for the studio and "you" for the reader or client; avoid "I" entirely. Do not include emoji anywhere — they are explicitly not part of this brand. When writing specimen or placeholder copy, favor lines in the register of: "A studio for work that bears weight." · "Things we kept." · "Tell us what needs to hold." · "Reading Room at Midnight." · "Field Notes — 03."

## Layout and spacing rules
Use a 4px base spacing scale throughout (4, 8, 12, 16, 24, 32, 48, 64, 96, 128) and be generous with vertical rhythm — this is an editorial layout with real breathing room, not a dense dashboard grid. Target an ideal reading measure of about 66 characters per line for body copy. The main content container should cap at 1200px wide; a narrower reading column variant should cap at 720px for long-form text. Corner radii stay small and sharp because this system reads as print, not app-chrome: 2px for small elements, 4px for medium, 6px for large surfaces like cards; pill radii are reserved for rare chip/tag cases only and should not appear on buttons or cards by default.

## Card, border, and elevation rules
Cards are a raised surface using the #1a1a1d background, a 1px hairline border in #2e2e35, 6px corner radius, and a soft shadow-1. Support an optional accented variant with a 2px solid brass left rail for cards that need to stand out (e.g. featured work, pinned notes). On hover (opt-in, not default on every card), the border should brighten to #3d3d44 and the card should lift by 2px — implement this as a transform + border-color transition using the standard ease token, not a box-shadow glow. Never add colored glows, colored shadows, or gradient fills to cards. Section and layout boundaries throughout the whole system should be defined by background-color shifts between the surface steps, not by drawing borders around every section — reserve borders for cards, dividers, and hairline rules specifically.

## Shadows and elevation values
Shadows are deep and colorless — black at low alpha, never tinted with brass or any hue. Use three elevation steps: shadow-1 for resting cards (0 1px 2px equivalent), shadow-2 for popovers/dropdowns (0 4px 16px equivalent), and shadow-3 for modals/high-elevation overlays (0 16px 48px equivalent). Inputs and other "well" surfaces (search bars, textareas) should use an inset shadow instead of an outer shadow, so they read as pressed into the page rather than floating above it.

## Background treatment and texture
Apply exactly two subtle background layers site-wide, never more: first, a single brass radial ambient glow anchored at the top of the page, peaking around 10% opacity and fading out by 60% down the page — there should only ever be one of these per page, not one per section. Second, a paper-grain noise overlay fixed over the whole page at roughly 35% opacity with mix-blend-mode: overlay, so all content reads as if printed on textured stock under warm lamp light. Do not add any other visible patterns, do not add full-bleed gradients anywhere else in the system, and avoid anything that reads as "gradient-tech" or glassy SaaS chrome.

## Transparency, blur, and motion
Reserve translucency and backdrop blur for exactly one use: a sticky header that uses a translucent ink background plus roughly 12px of backdrop blur, so page content slides warmly underneath it as the user scrolls. Do not use blur or glassmorphism decoratively elsewhere. All motion should feel slow and considered — favor fades and eases over springs or bounces. Use the standard ease cubic-bezier(0.2,0,0.2,1) for most transitions and the expressive-out ease cubic-bezier(0.16,1,0.3,1) for entrances that should feel like a settling-in rather than an arrival. Standard durations are 140ms for micro-interactions, 260ms for typical transitions, and 420ms for larger layout or page-level movements. Hover states: text and links shift to brass or brass-soft; primary buttons lighten toward brass-soft while secondary buttons pick up a brass border and ghost buttons pick up the brass-wash tint; icon buttons fill with the brass-wash background on hover; cards lift and brighten their border as described above. Press states are physical: buttons translate down by 1px on press, with no scale-shrink and no color flash — the button should feel like it is being pushed into the page.

## Imagery guidance
No photography assets ship with this system yet, so scaffold image placeholders rather than sourcing stock art. When real photography is eventually used it should read warm, low-key, and grainy — lamp-lit interiors, paper textures, brass hardware, wood grain — and should never include cool or blue-toned imagery or bright, glossy product shots, since that would clash with the ink-and-brass palette.

## Iconography
No brand icon set or icon font is supplied, so Copilot should implement any needed UI glyphs (menu, close, chevrons, arrows) as inline stroke SVGs at roughly 1.5px stroke weight in the current text color — thin and quiet, matching the editorial feel, not filled or duotone icons. Where a broader icon set is genuinely needed beyond a couple of custom glyphs, use Lucide icons at 1.5–2px stroke as a documented substitution (flag it clearly as a stand-in for a first-party set, should one ever be provided). Icons must always render monochrome, either in the current foreground color or in brass for emphasis — never multicolor, and never mixed filled-and-outlined within the same interface. Do not use any emoji as icons or bullets anywhere in the generated repository.

## Logo and wordmark
No logo file exists for this brand, and Copilot should not invent one. Everywhere a mark would normally appear (header, footer, favicon fallback), set the brand name as a Fraunces wordmark reading "Abstrekkt" followed by a brass-colored period, rather than fabricating an icon or symbol mark.

## Components to implement in detail
Button: implement primary (filled ink-on-brass or brass-on-ink per the surface it sits on), secondary (bordered, transparent fill), and ghost (no border, brass-wash hover) variants, plus disabled and pressed states following the physical 1px press-down rule above. IconButton: a square/circular button holding a single inline stroke SVG glyph, with the brass-wash hover fill described above. Display: the primary headline component wrapping Fraunces at the display scale, exposing a way to mark a sub-phrase for the brass-italic emphasis treatment. Kicker: the small uppercase JetBrains Mono eyebrow label component, always rendered in brass, used above headlines and above section content to introduce it in the "FIELD NOTES — 03" register. Card: the raised hairline-bordered surface described above, with a boolean prop for the brass left rail and a boolean prop for hover lift. Rule: a horizontal divider that can render as a plain hairline or, in its "chapter break" mode, center a small brass Kicker-styled label over the line. Badge: a small pill or rounded-rect tag for statuses or category labels, rendered quietly (surface background, hairline border, small mono label) rather than in a saturated color. Input: a text field with the inset well shadow, hairline border that brightens to brass on focus, and label/placeholder styled in the type system above. Callout: an inline aside/note block using a subtle surface-step background and optional brass left rail, for editorial asides distinct from a Card.

## The studio UI kit (ui_kits/studio/)
Build a working, interactive marketing site for the parent studio composed entirely from the primitives listed above — do not hand-roll new one-off styles for this kit. It needs three views: Home (a hero built around the Display component and the brass-italic emphasis device, an introduction to the studio's two lanes, and a Kicker-labeled section previewing recent "kept" work as a set of Cards), Work (an index/shelf of project Cards, each with a mono metadata corner showing a date or ID, filterable or grouped by lane), and Enquire (a simple, quiet contact/enquiry view built around the Input and Button components, framed with the library metaphor — e.g. "Tell us what needs to hold." as the section headline). Ship index.html as both the working entry point and a "Starting Point" template other builders can fork.

## Explicit non-goals and caveats to record in the readme
Do not add a light-mode variant — this system is dark-first with no light theme, by design, not by omission. Do not introduce any additional accent colors beyond brass, the Load-Bearing forest, and the Abstrekkt Products emerald — and keep those two sub-brand accents strictly scoped to their own lanes. Do not import or reference any FlashFusion tokens (#0B0B14, #A855F7, #EC4899, #22D3EE) anywhere in this repository. Do not round corners heavily anywhere — this is a sharp-cornered, print-inspired system, not a bubbly app-chrome system. Do not add drop-shadow glows, colored shadows, or neon borders to any component. Do not use Inter for any display or heading role. Do not add emoji, stock gradients, or generic SaaS iconography (a plain hamburger glyph is fine, but avoid trendy blob shapes, isometric illustrations, or gradient-mesh backgrounds). Note plainly in the readme that this system was authored from a written brand specification only, with no prior codebase, Figma file, or screens to source from, and that the component inventory (Button, IconButton, Display, Kicker, Card, Rule, Badge, Input, Callout) was an intentional addition sized for a literary/marketing surface rather than a dense application, since no source material defined one. Flag the three placeholder gaps clearly wherever relevant: no Inter font file is bundled (fallback stack renders until one is supplied), no logo or icon set was supplied (Lucide is a documented substitute for icons, and the Fraunces wordmark is the substitute for a logo), and no photography ships with the system (image slots should be left as clearly marked placeholders). Make clear that any sample copy shipped in the studio UI kit is plausible placeholder content demonstrating the system's voice, not real Abstrekkt work history, so it should not be presented as factual case-study material.

## Acceptance criteria for the generated repository
Every color used anywhere in any generated file must trace back to a token defined in tokens/colors.css — no ad hoc hex values in component or page code. Every headline must be set in Fraunces and every body paragraph in Crimson Pro, with JetBrains Mono reserved strictly for kickers, labels, and metadata. The brass accent must never occupy more than a small fraction of any given view — it should read as punctuation (a rule, a label, an emphasized phrase, a hover state, an icon) rather than as a fill color for large surfaces or backgrounds. Every page must include exactly one top-anchored brass ambient background and the fixed paper-grain overlay, and no page should introduce a second competing background treatment. All interactive states (hover, focus, press, disabled) must be implemented for Button, IconButton, Input, and Card per the rules above, using only the motion tokens defined in tokens/effects.css. The repository must build and preview with zero references to any FlashFusion token, zero light-mode styles, and zero emoji in UI copy or documentation.

## Responsive behavior
Design mobile-first but let the editorial feel scale up rather than compress down: at desktop widths (1200px+) the content container should sit at its full 1200px cap with generous side margins; at tablet widths (768–1199px) the container should fluidly narrow while preserving the 8px spacing rhythm; at mobile widths (below 768px) the Display component should step down to a smaller but still serif-forward size (never smaller than roughly 32px for a primary headline), the 12-column implied grid should collapse to a single column, and the sticky translucent header should remain but simplify its contents to the wordmark plus a single menu IconButton that opens a full-height ink-colored drawer using the same brass-wash hover states as desktop navigation. Kickers and mono metadata should never wrap awkwardly — truncate with an ellipsis or stack them onto their own line rather than letting tracked-out uppercase text break mid-word. Cards in a Work-index grid should reflow from a multi-column grid at desktop to a single column at mobile without changing their internal padding scale, so the reading rhythm stays consistent across breakpoints.

## Accessibility requirements
Even though the palette is dark and moody, contrast still matters: verify that body text in warm bone (#e8e0cc) against the base ink (#0d0c0a) and against each surface step meets at least WCAG AA for normal text, and that brass (#C8A86A) used for interactive text and links against the ink background also clears AA at the sizes it is used. Every interactive element (Button, IconButton, Card when used as a link, Input) must expose a visible focus state distinct from hover — a brass outline or brass border-brighten is appropriate, but focus must never be removed via outline: none without a replacement. All IconButtons must carry an accessible label (aria-label) describing their action, since their only visual content is a stroke glyph. Form fields in the Enquire view must have properly associated labels (not placeholder-only), and validation or error states should be communicated with text, not color alone, given the restrained palette. Respect prefers-reduced-motion: users who request it should get the fade/opacity portion of transitions without the position/transform movement, particularly for the card-lift hover and the settling-in entrance animations. Maintain a logical heading hierarchy on every page (one Display-level H1 per view, Kickers are not headings themselves but sit adjacent to the heading they introduce).

## Technical scaffolding notes for Copilot
The existing reference implementation for this design system is plain, dependency-light front-end code: CSS custom properties for every token file, and components authored as small reusable React pieces (functional components, no class components) that a plain script tag can consume without a bundler, alongside plain HTML/CSS versions of the same pages inside ui_kits/studio for use without a JS build step. When scaffolding new files, follow that same dependency-light approach unless the surrounding project already has an established framework (Next.js, Vite, etc.) — in that case adapt the component API surface (props, variants, naming) described in this brief to that framework's idioms rather than introducing a second, conflicting stack. Keep each token file focused on exactly one concern (fonts, colors, typography, spacing, effects) so a consumer can override or extend a single concern without touching the others. styles.css must remain a pure @import manifest — never add rules directly to it, so consumers can always trust it as a single, predictable entry point. Name CSS custom properties with a consistent --color-, --font-, --space-, --radius-, --shadow-, and --ease- prefix scheme so autocomplete and documentation generation stay coherent as the token set grows.

## SKILL.md contents
SKILL.md should describe, in Agent-Skills-compatible frontmatter plus a short body, what this design system is for, when an agent should reach for it (any Abstrekkt-branded surface, and by extension the Load-Bearing and Abstrekkt Products lanes when their scoped accent is layered on top), and a short pointer to styles.css, the components/ folder, and the ui_kits/studio reference implementation as the three things an agent building a new Abstrekkt page should load and study before writing new markup. It should restate, briefly, the single hard rule that most protects the brand from drifting into generic SaaS territory: brass is punctuation, never a fill; the page is dark by default with no light theme; and Fraunces carries every headline.

## Naming and file conventions
Use lowercase-with-hyphens for CSS token files (already reflected above) and PascalCase for component files (Button.jsx, IconButton.jsx, Display.jsx, Kicker.jsx, Card.jsx, Rule.jsx, Badge.jsx, Input.jsx, Callout.jsx), each colocated with its own minimal stylesheet or styled-in-JS following whatever pattern the surrounding project already uses. Keep guideline/specimen pages named after the concern they document (colors.html or Colors.jsx, type.html or Type.jsx, spacing.html or Spacing.jsx, brand.html or Brand.jsx) so the guidelines/ folder reads as a predictable index on its own.

## What "done" looks like
A reviewer should be able to open ui_kits/studio/index.html, land on a Home view that opens with a Fraunces hero line containing exactly one brass-italic emphasized phrase, scroll to a Kicker-labeled preview of a few Card-based work entries with mono metadata in their corners, navigate to a Work view that lists more of the same Cards in a responsive grid, navigate to an Enquire view with a quiet Input-and-Button contact form framed by library language, and at every step see the same single top-anchored brass ambient glow, the same fixed paper-grain overlay, the same warm ink background, and never a stray FlashFusion color, a light background, a bold headline, an emoji, or a heavily rounded corner anywhere in the experience.

## Governance checklist before calling any generated page finished
Run through this list against every new page or component before considering it complete. Confirm the page never renders on a light background under any state (including print or forced-colors media queries) — dark-first is a hard constraint, not a default that other code paths can override. Confirm no component references a raw hex value; every color must resolve through a CSS custom property defined in tokens/colors.css, so a future palette adjustment only requires editing one file. Confirm every headline-level element uses the Display component or its underlying Fraunces styles, and no heading anywhere falls back to a sans-serif system font except in the documented Inter-fallback failure case. Confirm the brass accent's total visual footprint on any given screen stays small — a rule, a kicker, an emphasized phrase, an icon, a hover or focus state — and never becomes a large fill, a full-width band, or a background wash covering more than a small highlighted region. Confirm the single top brass ambient glow and the fixed paper-grain overlay are both present exactly once per page, with no page shipping zero background texture or, conversely, stacking additional gradients or patterns on top. Confirm every interactive element has hover, focus, and press states implemented per the rules in this brief, using only the eases and durations defined in tokens/effects.css rather than ad hoc transition values. Confirm no emoji, no vanity stat blocks, no exclamation marks, and no Title Case headlines exist anywhere in shipped copy. Confirm the two sub-brand accents (Load-Bearing forest, Abstrekkt Products emerald) appear only inside their own named lanes and never bleed into the parent Abstrekkt surface or into each other's lane. Confirm zero FlashFusion tokens or FlashFusion-style neon/glass treatments exist anywhere in the repository, including in code comments or example values left behind from scaffolding. Confirm the readme's caveats section still accurately lists the three known gaps (no Inter font file, no logo or icon set, no photography) so future contributors know exactly what is a deliberate placeholder versus a finished asset.
