I built a maturity model for outcome-aware AI. Then I walked my own work through it.

By Kyle Rosebrook

I'm an L1 service desk tech who builds AI work on the side. I spent some time writing a five-level diagnostic for how mature an MCP-using system is at verifying its own outcomes. The first thing I did with it was walk my own service desk operation through the rubric.

I scored L1.

Out of five levels. The lowest one. The "tools deployed, outcomes unknown" tier.

That's not the result I wanted. It's the result that's true.

What I was trying to add

The thesis is narrow on purpose. There is already meaningful work on MCP server provenance and AI observability — and I'll name it in the next section. What I think is still loosely specified is the distinction between cryptographically authenticated tool calls and independently verified world-state outcomes. A signed receipt can prove a tool was called, by whom, with what payload, and that nothing was tampered with in transit. It cannot prove the page actually changed. Those are two different verifications and most current work covers the first.

That gap — "the call was real" vs. "the claim matches the world" — is what the framework tries to make legible.

What already exists

A short and incomplete list of work already in the space:

  • The NSA's May 2026 Cybersecurity Information Sheet on MCP (U/OO/6030316-26) calls out observability as essential and recommends logging tool/model invocations with "cryptographic hashes of results or output."
  • Production MCP servers already issue signed tool-call records. AgentSeal records every agent action in a SHA-256 hash chain. arkforge-mcp stamps every tool call as a signed, timestamped Agent Action Receipt (AAR). causallayer-mcp issues Bitcoin-anchored CausalCertificateV1 receipts for liability attribution. (Catalog: TensorBlock/awesome-mcp-servers.)
  • The MCPS spec (draft-sharif-mcps-secure-mcp) defines per-message JSON-RPC signing patterns the NSA CSI later described — message-level integrity work merged into the MCP cheat sheet on March 26, 2026.
  • Microsoft's AI observability post (March 2026) makes the same outcome/output point in different words: "traditional health metrics stay green: no failures, no errors, no alerts. The system is working exactly as designed… except a boundary between untrusted external content and trusted agent context has been compromised."
  • Ali Arsanjani's Agentic AI Maturity Model describes Verifier Agents — independent agents that monitor production agents' tool-call outputs as a "checks and balances" system. He sketches the architecture; my work tries to specify the message primitives.
  • Runtime-verification research is active. RvLLM applies formal specifications to validate outputs post-generation. AgentSpec introduces declarative action policies. Pro2Guard explores probabilistic runtime enforcement. "Watchdogs and Oracles" (Nov 2025) frames RV as a lightweight safety layer around untrusted models.
  • Maturity-model space is crowded. Practical DevSecOps' AI Security Maturity Model (5 levels) names exactly the pattern I found in my own desk: "Most organizations are at Level 1 and calling it Level 3 because they have a prompt filter running." Credo AI, Sema4.ai, 3Pillar, ELEKS, Gartner, Harness, and Grid Dynamics all ship adjacent frameworks.

What this framework tries to add is narrower than any of those: a rubric that gates specifically on outcome verification — not security generally, not governance generally, not engineering maturity — with the message primitives spec'd at the MCP layer.

The five levels

The model is deliberately narrow. It scores one dimension only.

  • L1 Output-only. Tools deployed. Outcomes unknown.
  • L2 Tracked. Tool calls logged with coherent metadata.
  • L3 Claimed. Tool wrappers emit structured receipts of what changed.
  • L4 Verified. Claims are independently probed against the world.
  • L5 Optimizing. Verdict signals feed back into how the system runs.

Anti-patterns paired with each level are the standard suspects, named tightly. Tool Sprawl pins you at L1. Trust-Me Telemetry and Phantom Determinism pin you at L2. The universal one across every level is Outcome Theater — dashboards that say "outcomes" while showing call counts and latencies. The phrase is mine; the underlying pattern is widely observed.

What my own desk showed

I ran the rubric on a managed-services L1 operation. About thirty client endpoints. Standard MSP stack — ITSM platform, RMM agent, EDR, softphone, VPN, MFA. AI work on the side: a couple of custom MCP servers, n8n bridging webhook events, a coding assistant on the operator's machine.

The L1 qualifier passed easily. Tools are deployed. Of course.

The L2 questions are stricter than they look. "Is every tool call logged with consistent metadata?" Partial — three logging surfaces with no run_id correlating across them. "Do tool failures surface within five minutes?" No. Failures are discovered when a ticket ages past SLA. Median time-to-notice: fifteen to forty-five minutes.

L2 has four questions. You need four out of four. I scored zero strict, two partial. Not cleared.

L3, L4, and L5 are blocked by L2 anyway, so I stopped there.

The diagnosis: L1 — Output-only. Operative anti-patterns: Tool Sprawl across logging surfaces (not across MCP server count, which is how the catalog originally framed it — useful finding for v0.3). Outcome Theater — the dashboards that exist optimize for ticket lifecycle, not for whether the underlying issue actually got solved. Closed is not resolved. In MSP work, a closed ticket can mean the user stopped responding, or the issue came back as a new ticket on a different endpoint, or the resolution was a workaround that masked the actual cause.

The gap most teams miss

This is not a new observation. Microsoft, Maxim AI, LangChain, and others make versions of it: technical metrics can stay green while outcome quality degrades silently. Practical DevSecOps names the L1-self-reporting-as-L3 pattern directly.

What the rubric adds is the strict four-of-four gating per level. That gating is what surfaces the difference between telemetry and coherent telemetry — the difference between "we log things" and "we can answer: what did this agent run actually change in the world." Most teams have some telemetry. They will not self-report L1. They will self-report L2 or L3 because they "have observability." The four-of-four gate breaks the curve grade.

What's in the repo

The spec is on GitHub. Three combos, each positioned against existing work:

  • 01 Outcome Receipts × Forgery Detector. The assert-verify primitive. Servers emit structured claims about world-state change; an independent probe layer verifies whether the claim is true. Builds on existing tool-call provenance work (AAR, hash chains, MCPS message signing); adds the world-verification layer signed receipts don't provide.
  • 02 Eval-as-MCP × Sycophancy Telemetry. Runtime anti-sycophancy. A streak counter watches for multi-turn agreement drift; when it crosses threshold, an adversarial eval pass fires as a callable MCP. Sycophancy detection is an active area (Silicon Mirror, Giskard work); the MCP-native callable-eval pattern is the part I haven't seen specified.
  • 03 Anti-Pattern Catalog × Maturity Model. The diagnostic I ran on my own desk. Five levels, ten anti-patterns, twenty-one yes/no rubric questions. Closest precedent: Arsanjani's Agentic AI Maturity Model with its Verifier Agents. Mine is narrower (outcome verification only) and ships the rubric.

Combo 03 is content. You can use it today. Combos 01 and 02 are blueprints — schemas and build sequences for someone to implement.

The case study from my own desk is in case-studies/msp-service-desk-l1.md. It's what an honest self-assessment looks like when the framework actually works on you.
