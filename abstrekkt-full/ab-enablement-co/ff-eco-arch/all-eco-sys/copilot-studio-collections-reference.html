Dataverse schema

Corrected component-collection topology

A collection is not a bot replacement ID. Public Dataverse metadata exposes a dedicated botcomponentcollection table, a bot_botcomponentcollection many-to-many intersect, and a collection-to-component relationship via parentbotcomponentcollectionid.

bot botcomponentcollection botcomponent

PK: botid. Primary name: name.

Architect note: Component membership uses parentbotcomponentcollectionid. Agent-to-collection sharing uses bot_botcomponentcollection. Keep parentbotid distinct — it still exists on bot components and must not be repurposed as a collection pointer.

Schema explorer

Import dependency resolution

Bottom-up release gate

Stage platform prerequisites before agent assets, then validate children after the collection and agent references exist. Microsoft documents Add required objects and flags missing components as a common import failure cause.

1

Environment readiness

Validate target environment, security role, Dataverse availability, connector availability, and Dataverse search where knowledge requires it.

2

Platform dependencies

Import custom connectors before the solution using their connection references. Confirm environment variables have target values.

3

Collection and agent solution

Import managed package downstream. Inspect import log immediately if failed; missing required components are high probability.

4

Post-import binding

Reconfigure agent authentication, publish imported agent, verify collection-linked topics, actions, and knowledge paths.

5

Regression evidence

Run golden prompts, action invocations, auth-denied tests, and cross-agent collection reuse tests. Store screenshots/logs with release notes.

Risk matrix

Known failure classes

Missing required objects

Symptoms: import fails or agent is incomplete post-import. Control: run Add required objects before export and inspect the dependency list.

Direct solution component edits

Symptoms: export/import breaks after deleting or modifying components directly. Control: change topics and agent assets through supported authoring flows only.

Connection reference mismatch

Symptoms: imported flows/actions exist but fail at runtime. Control: remap connections and validate least-privilege service accounts.

Knowledge source drift

Symptoms: wrong or stale answer sources. Control: source registry, owner sign-off, index refresh check, and answer-citation regression tests.

Cosmetic transfer gaps

Symptoms: icons/channel details require manual follow-up. Control: post-import checklist with visual verification.

Application lifecycle management

Managed vs unmanaged operating model

Solutions are the ALM vehicle for moving Power Platform components across environments. Collection-heavy agents need stricter dependency and governance gates than simple single-agent builds.

DimensionManagedUnmanaged
Best useTest, staging, productionDevelopment and authoring
CustomizationControlled by managed propertiesFast edits, higher drift risk
RollbackVersioned solution replacementHarder when manual changes accumulate
GovernanceStrong release disciplineWeaker audit trail
RecommendationDefault downstream postureSource/dev environments only
Decision rule: Author in unmanaged dev. Export managed for controlled environments. Do not hotfix production by hand unless you have a documented break-glass path and back-port plan.

Programmatic control

Safe API / CLI workflow

Use Dataverse APIs and PAC CLI carefully. The public schema supports create, update, retrieve, assign, access control, and state operations for component collections and bot components. For production automation: read first, validate ownership and ETag/version, then patch with a narrow payload.

Pattern: Read → Validate → PATCH → Publish → Regression

Use ETags for exactness

Retrieve the row first and use conditional operations rather than blind overwrites. If-Match: * is a minimum; use a real ETag when concurrency matters.

Patch only narrow fields

Never overwrite content/configuration blobs without comparing the pre-change value, owner, release ID, and target environment.

Publish and test

A data-layer change is not a release until the agent is published and runtime behavior has been verified against regression prompts.

Governance model

Collection ownership contract

1. Name and schema discipline›

Use stable prefixes such as hr_, it_, or finance_. Names should reveal domain, asset type, and lifecycle tier — e.g. HR_Global_Knowledge_Collection.

2. Owner and approver registry›

Every shared collection needs a business owner, technical owner, security reviewer, and fallback owner. This prevents orphaned shared assets that nobody is accountable for.

3. Knowledge source approval›

Any URL, SharePoint site, file, Dataverse table, or external source needs an owner-approved purpose statement, scope boundary, and forbidden-use note before inclusion.

4. Regression prompt pack›

Maintain golden prompts, abuse prompts, data-boundary prompts, and source-citation prompts for every collection. Run them before and after every deployment.

5. Scheduled review cadence›

Quarterly: owner review, knowledge source validity, access review. Annually: full schema audit against Dataverse public metadata to catch platform-driven changes.

Drift detection

What to snapshot

Take a pre-release snapshot of each item below. Compare post-release. Unexplained delta = blocked deployment until root-caused.

Agent configuration

statecode, statuscode, versionnumber, configuration blob hash

Collection membership

bot_botcomponentcollection row count per agent per collection

Component inventory

botcomponent count by componenttype per collection

Environment variables

All variable names and schema names (not values — never log secrets)

Connection references

connectionreferenceid, schemaname, connectorid per solution

Flow / action bindings

Cloud flow GUIDs bound to agent actions and their statecode
