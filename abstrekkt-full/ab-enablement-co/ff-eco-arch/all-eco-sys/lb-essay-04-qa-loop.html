The QA Loop Nobody Runs

AI-generated code runs. That's not the same as it doing the right thing. The gap between those two statements is where production breaks.

Kyle Rosebrook · Load-Bearing · flashfusion.co

The fastest I've ever shipped something broken was the month I started using AI to generate code.

It wasn't because the code was buggy. It ran. It passed lint. It passed my quick manual test. It did the thing the test covered, did it correctly, and I shipped it before I noticed that the thing the test covered wasn't the thing the production system needed.

That's the failure mode AI introduced that I didn't have a name for at the time: confident incorrectness. The code is correct. It's solving the wrong problem with professional accuracy.

What the Old QA Loop Caught

Before AI code generation, my QA loop was mostly about correctness at the syntax level. Does it run. Does the output match the expected value. Does it handle the null case. These are the things unit tests check, and the things you catch when you write the code yourself, because writing it forces you to think through the execution path.

That loop still works. It's just not sufficient anymore.

When I write code myself, I understand it in a way that reveals what it's not doing. When AI writes it, I understand what it's doing — which is different. The AI's code is usually well-structured, clearly commented, and follows patterns I recognize. It reads well. Reading it is not the same as reasoning about whether it maps correctly to the problem.

The New Failure Mode

I was building a data processing pipeline. It needed to handle three document types differently depending on a field value. I described this to the AI, got back code that handled three document types, ran it, and the output looked right.

The field value it was checking was the wrong field. Not wrong by much — close enough that my manual test, which used clean data with obvious values, passed. The edge case it missed was the one that appeared in real data: documents where the primary field was null and the secondary field held the routing value.

That's a domain knowledge gap. The AI doesn't know my data. It knows what I told it about my data, which is always an incomplete translation. The code was correct given the specification. The specification was incomplete.

AI doesn't have access to what you didn't say. Every missing constraint is a confident assumption.

The QA Loop You Need Now

The loop that caught me was:

The gap between "does it run" and "does it do the right thing"

Does the logic match the domain? Not does the code match the spec — does the spec capture the domain correctly. These are different questions. The first is a code review. The second is a requirements review. You need both.

What assumptions did the AI make that you didn't state? Paste your AI-generated code back to the AI and ask it to list every assumption it made that isn't in your prompt. You'll find at least one thing you forgot to specify.

What does this do with bad data? Real data is dirty. Your test data isn't. Run the code against the messiest data you have before you ship.

What's the failure mode? Not the error case — the wrong-but-no-error case. Where does this produce output that looks right but isn't?

None of this is new QA wisdom. It's old QA wisdom applied to a new failure surface. The surface is confidence. AI-generated code fails silently in a way that handwritten code often doesn't, because handwritten code carries the uncertainty of the person who wrote it. You can feel the edges. AI-generated code presents as complete.

The Audit That Changes How You Use AI

I started running a five-minute audit after every AI-generated block before merging:

What did I not tell the AI? What assumption is embedded in this code that I didn't specify? If this runs on real data instead of test data, what breaks silently?

The last question is the one that matters most. "Breaks silently" means: produces output without throwing an error, with output that looks plausible but is wrong. That's worse than a crash. A crash tells you something. Silent wrong output accumulates.

The QA loop I described above takes about five minutes. I ran it after I got burned. I should have designed it before I started using AI for production code.

That's the thing nobody posts about AI development workflows: not how fast you can generate, but how you validate what you generated before it touches real data. The generation speed creates pressure to skip the audit. The audit is the part that makes the speed useful.
