The Claude Code Blueprint Nobody Posts

The setups you see on Twitter have 50 MCP servers and perfect CLAUDE.md files. This is the one that runs in a real working environment with real constraints.

Kyle Rosebrook · Load-Bearing · flashfusion.co

Every Claude Code setup post follows the same template. Here's the CLAUDE.md. Here are the MCP servers. Here's the skills folder. Here are the agents. Clean, complete, screenshot-ready.

Nobody posts the version where you've connected 80 MCPs but only Base44 tools load in the active session because MCP tool surface is determined at session initialization and new sessions are required to pick up newly enabled connectors. Nobody posts the version where your skills fire in Claude Code but break silently in the cloud environment because the enforcement mechanism — a PostToolUse hook — doesn't exist in that runtime.

That's the real version. Here's what I've learned building it.

What Actually Compounds

The Claude Code components that accumulate value over time are the ones that encode what went wrong. Not best practices — corrections. Every skill I built from a correction loop compounded. Every skill I built from anticipating a future need sat unused.

The CLAUDE.md file that works isn't the one with comprehensive documentation of everything the model should know. It's the one that passes a single test: would removing this line cause Claude to make a mistake? If no, the line doesn't belong there.

I've written CLAUDE.md files with 400-line system prompts. They don't outperform the 80-line version. Context is expensive. Every line of system prompt is a line that costs tokens in every session. The shorter file that answers the right 15 questions beats the longer file answering 60 questions you haven't had yet.

The Environment Split

Skills behave differently depending on where they run. This is the part no setup post covers, because most people testing skills are testing them in one environment.

Claude Code in the CLI has shell access. Skills can reference hooks — PostToolUse, PreToolUse — that call bash scripts. These work. They're powerful. They're also invisible in the claude.ai project environment, which doesn't have shell access. A skill that relies on a hook to auto-format code after every write just… doesn't. No error. The instruction is present. The mechanism it depends on doesn't exist.

Deployment checklist before writing any skill

Where will this run? CLI only, claude.ai Projects only, or both? The answer determines which enforcement mechanisms are available.

Does any instruction depend on a hook? If yes, that instruction needs an inline enforcement version for the environments where hooks don't fire.

Does the description actually route correctly? The description field is what Claude uses to decide whether the skill is relevant. Test it with the phrases you actually use, not the phrases you imagine using.

Four of my fifty skills fail silently in the deployment environment I care most about. I can't ship them there until I refactor the hook-based enforcement into inline instructions. I haven't done it yet because I set a rule: fix before expand. No new skills until the compliance gaps are closed. The rule exists because I kept expanding before fixing and the library kept accumulating debt.

MCP Server Reality

I have 80+ MCPs connected. In most sessions, I can use maybe 15 of them. The rest either don't initialize in the active session, require authentication re-flow that breaks mid-session, or are available in principle but produce unreliable results in practice.

Having an MCP connected is not the same as having it available. It's not the same as having it reliable. Those are different properties.

The useful MCP servers I actually use repeatedly are ones where I've documented the exact call pattern that works, including the parameters that don't behave as documented and the workarounds. That documentation lives in my CLAUDE.md files. Without it, I would rediscover the same edge cases every session.

The list_entity_schemas tool in Base44, for example, returns nested JSON where the actual schema data is inside d[0]['text'] as a string requiring json.loads() to parse. This is not in the documentation. I found it by getting a TypeError, investigating, and writing it down. That note has saved me the same twenty-minute debugging session at least eight times.

The Blueprint

What I'd tell myself at the start: build the smallest thing that solves a real problem in your actual work. Not the most comprehensive thing. The smallest useful thing. Then write down what it got wrong the first time. That correction is the next version. The library grows from corrections, not from plans.

The goal is a setup you understand completely. Where every component is there because you needed it and you know exactly what it does. Where the failure modes are documented because you've hit them. That's more useful than the impressive screenshot.
