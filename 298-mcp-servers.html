MCP Servers for Claude Desktop

Three production servers I've built and run in Claude Desktop. Each solves a problem that wasn't tractable with chat alone.

github-automation-suite

The problem. 318 repositories, one maintainer. At ~30 minutes each for real hygiene, that's 159 hours a week. Mathematically impossible. So nothing gets maintained, and the signal-to-noise ratio of the whole portfolio collapses.

What it does. Triages 300+ repos into five buckets — Archive, Playground, Active, Production, Monorepo — using activity analysis, commit history, and naming patterns. Then applies 2025 best practices (ESLint, Prettier, GitHub Actions CI, security policies) to the 40-50 active repos with concurrent processing and rate limiting.

Outcome. Before: 318 × 30 min = 159 hrs/wk. After: ~200 archived (0 hrs), ~70 tagged playground (minimal), ~40-50 on automated hygiene (2-3 hrs/wk). A two-order-of-magnitude change in maintenance cost.

What's in the MCP. The repo-triage report generator, the hygiene enforcer, interactive repo selection, dry-run preview, detailed logging. Everything dangerous is gated behind confirmation prompts.

base44-prompts-v2

The problem. Prompts drift. Good ones get lost in chat history. Bad ones get cargo-culted. No one remembers which version of the "write a feature spec" prompt worked last quarter.

What it does. Serves a versioned library of prompts over MCP — Claude Desktop asks for a prompt by name and gets the current canonical version, with changelog. Supports tagging, search, and composition (one prompt calling another).

GithubRepos (source-of-truth bridge)

The problem. Claude Desktop reasons best with current context. Git repos are the authoritative state, but a chat-only interface can't browse them. Without a bridge, you copy-paste files and hope the model still remembers the structure twelve messages later.

What it does. Surfaces GitHub repos, files, and recent changes as MCP resources. Includes the Claude Code Development Kit and a Notion MCP bridge for cross-surface source-of-truth work.

What I learned building these

Small servers compose. Three narrow MCPs beat one monolithic one every time. Each can be tested, shipped, and reasoned about in isolation.

Dry-run is table stakes. Any MCP that can mutate external state needs a preview mode. Not optional.

The interface is the spec. What a tool does gets defined by what it exposes over MCP. If the resource names and argument schemas are wrong, the model will route requests poorly no matter how good the implementation is underneath.
