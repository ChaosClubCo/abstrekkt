When I started building MCP servers, my instinct was to consolidate — one server per domain, exposing every useful tool behind it. A "GitHub" server with 25 tools. A "Notion" server with 40. Neat in theory. Broken in practice.

The servers that actually work are small. Narrow scope. Five tools or fewer. One responsibility each.

Why big servers fail

Routing gets muddy. Twenty tool descriptions in one server start crowding each other. The model loses the ability to pick clean. You start seeing it call the wrong tool, or worse, no tool, because nothing stood out.

Failures cascade. When the GitHub server crashes on a bad auth token, every GitHub-adjacent capability disappears at once. When a small, dedicated server crashes, you lose one thing, not a category.

Deploys get scary. A change to one tool in a 25-tool server makes you nervous about redeploying the other 24. You stop iterating.

The actual pattern

Think of MCP servers like Unix tools. One job, well defined, composable. The three servers I actually run in Claude Desktop:

  • One for repo triage and hygiene at scale
  • One for versioned prompt retrieval
  • One for source-of-truth bridging across GitHub and Notion

Three servers, about a dozen tools total across all of them. Each one I could delete tomorrow without breaking the others. Each one has a single sentence I can say out loud that describes what it does.

The heuristic

If you can't describe a server's job in one sentence without using the word "and," it's two servers.

Split early. You'll iterate faster, the model will route cleaner, and your config file will read like a tool belt instead of a graveyard.
