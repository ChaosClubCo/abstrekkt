Issue Tracking Didn't Die.
It Got Promoted.

Kyle Rosebrook · May 2026

In March, Karri Saarinen — the CEO of Linear, a company that has spent years making issue tracking beautiful — declared the category dead. The argument was clean: issue trackers were built for a world where human coordination was the bottleneck. When agents can read context directly, that translation step is friction. Eulogize it and move on.

Then OpenAI open-sourced Symphony, and Linear became the literal control plane for the most ambitious autonomous coding system anyone had shipped. Some internal teams saw a 500% increase in landed pull requests. The thing Saarinen had just eulogized was now the substrate that made all of it work.

He was right about the user experience. He was wrong about the infrastructure. And that distinction is worth sitting with, because it reprices every boring tool in your stack.

What Makes a Tool Agent Infrastructure

Not every software system is equally useful to an agent. A well-designed dashboard tells a human what's happening. An agent needs something different: structured state it can read and write, an audit trail it can use as context, a dependency graph it can traverse, permissions it can act within, and an API it can call without a human in the loop.

Issue trackers — the boring ones, the ones we've been complaining about since 1998 — have all five. That's not an accident. It's the accumulated residue of building coordination infrastructure for humans who can't hold the whole system in their heads at once. Turns out agents can't either. They need the same external scaffolding.

The assignee field. The status transitions. The dependency links. The comment history. The audit log. None of that was designed for agents. It was designed for humans who forget things. Agents are just another kind of thing that forgets things.

"The translation step is going away. The state machine is staying. Those aren't the same thing."

The UX Choice Was Actually a Data Choice

Linear became the agent substrate by accident. Saarinen spent a decade obsessing over clean interfaces, fast load times, keyboard shortcuts, no cruft. He wasn't building for agents. He was building for humans who were tired of Jira.

But the discipline that produced a clean UX also produced clean data. Fewer freeform fields. Consistent status taxonomy. Predictable schema. Every decision that made Linear feel fast to a developer also made it legible to an agent. Design taste accidentally became data hygiene.

This is the part that changes how I think about tool selection from here. The question isn't just "does this have a good interface?" It's "does this produce data structured enough that something other than a human can act on it?" Those are different questions. They haven't always had different answers, but they do now.

The Atlassian Repricing

Jira is the anti-Linear. Bloated, configurable to the point of incoherence, documentation written in 2009 that still somehow governs enterprise IT today. I work service desk. I have opinions about Jira.

And yet Atlassian is one of the most interesting companies in this transition, for the same reason Linear is. They have something no one else has: decades of enterprise workflow data, locked into a schema that agents can actually use. The MCP server they shipped, the Anthropic partnership, the acquisition speculation — all of it makes more sense when you frame Jira's installed base as a strategic AI asset rather than technical debt the market is waiting to replace.

The cruft is a liability for the UX. The data is an asset for the agent. Those two things can both be true at the same time.

Which of Your Tools Are Next

Five questions. Run them on every system in your stack.

Does it have structured state — not freeform text, but typed fields with defined transitions? Does it maintain history — a log of what happened, who changed it, when? Does it model relationships — this depends on that, this blocks that? Does it have an API that something other than a human can call? And does it have a permission model that can scope what an agent is allowed to do?

CRMs score high if you've kept the data clean. ERPs score high on structure, lower on API accessibility depending on vendor. Service desks — yes, obviously, this is literally what they're for. Calendars have structured state but weak relationship modeling. Spreadsheets are a trap: they look structured but the schema lives in the user's head, not the file.

The thing I keep noticing: The tools that were "good enough" and never got replaced are the ones that quietly accumulated the cleanest data. The flashy new thing that got adopted fast often built for the demo, not the audit trail. Right now, boring wins.

What to Do About It

Three things, in order of priority.

First: audit your data, not your interfaces. The question isn't whether your team likes the tool. It's whether the data the tool produces is structured enough to be agent-readable. If your CRM is 60% free text notes, you don't have a CRM. You have a very expensive notepad.

Second: build the MCP layer for anything you can't replace. If a system has the right data but no API that an agent can call, an MCP server is usually faster to build than a migration. You're not changing the source of truth — you're giving agents a door into it.

Third: treat schema discipline as a competitive advantage. Every time someone adds a freeform field instead of a structured one, they're trading future agent leverage for present convenience. That's not always the wrong call. It's just a decision that should be made deliberately, not by default.

The Actual Lesson From Saarinen

He wasn't wrong. The coordination overhead — the human updating the ticket so the other human knows where things stand — that part really is going away. Agents update their own tickets. They don't need a status meeting.

But he conflated the coordination layer with the state layer. Those are different systems doing different jobs. One is friction. The other is the ground truth that all coordination runs on top of.

The state machine doesn't disappear when agents enter the picture. It becomes more important. You need to know what's assigned, what's blocked, what's done, and who (or what) is responsible — especially when the thing doing the work isn't a human you can tap on the shoulder.

Started as a bug tracker in 1998. Became the most strategic infrastructure in the enterprise stack in 2026. Not because it changed. Because everything around it did.

That's how these transitions work. The boring thing that already had all the properties survives. The shiny thing built for the old workflow gets rebuilt from scratch. Run the five questions. Figure out which of your tools is about to get promoted.
