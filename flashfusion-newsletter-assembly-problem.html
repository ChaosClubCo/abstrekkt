The Assembly Problem

Why the retrieval debate is aimed at the wrong layer — and what the stack looks like when you fix it.

Retrieval Architecture Agentic AI 9 min read

There's a debate going on right now about whether vector search is obsolete. That's the wrong layer to be arguing about.

The agents I'm watching fail in production aren't failing because the retrieval method is wrong. They're failing because the retrieval system can't assemble what the agent actually needs before it starts acting. A vector database can find text semantically related to a question. That's useful. It's nowhere near enough.

Agents need the current account record, the user's permissions, the controlling policy, the right section of a long document, the table behind a metric, the prior decision from a meeting, and the source trail that lets a human reviewer reconstruct why the agent did what it did.

When the system doesn't prepare that context, the model improvises — and the cost shows up everywhere except the place you're looking. Wrong refunds get issued. Stale policies get cited. Outdated metrics make it into board decks. The agent burns tokens and wall-clock time rebuilding context every run, and when the answer finally lands, it lands confidently — which is the most expensive way to be wrong.

That's the new RAG problem. Not a retrieval problem. An assembly problem.
01

Why Classic RAG Worked — And Where It Stops

The original RAG architecture solved a real problem. Before it, you had two bad options: fine-tune on proprietary data (expensive, staleness baked in) or paste document chunks into prompts until you hit the context limit (expensive, noisy). RAG gave you a third path: embed your corpus, store in a vector database, pull the semantically closest chunks at query time. Fast, composable, cheap to prototype.

That works well when the agent's task is lookup. Question-answering over a corpus. Summarization. Semantic search where "close enough" is acceptable. Most demo-level RAG is exactly this — and it demos beautifully.

The problem surfaces when the task is action. Not "what does the policy say" — but "apply the correct version of this policy to this specific customer in this account state." Three things break simultaneously when you cross that line.

Chunk boundaries destroy context. Semantic similarity finds the paragraph about the policy. It doesn't know whether that paragraph is current, whether it's been superseded by an amendment three pages later, or whether the exception clause in section 7 applies to this customer segment. The embedding doesn't know any of that.
Structured data was never in the corpus. The agent also needs the account record, the user's permissions, the queue state, the decision logged from last week's meeting. Vector search can't retrieve what was never embedded.
There's no provenance. When the output is wrong — and it will be — there's no trail. Every wrong answer becomes a black box, and black boxes in production are expensive to diagnose and impossible to audit.
02

What Four Companies Are All Saying

Four vendors made major moves in the last two weeks. On the surface they look unrelated. Together, they're describing the same architectural shift.

Pinecone Nexus

Pinecone built the category. They also just publicly acknowledged the failure mode at the core of it. In their Nexus announcement, they put a number on the problem: roughly 85% of an agent's effort in a classic RAG pipeline goes to knowledge retrieval — not reasoning, not acting. Task completion rates stuck at 50–60%. Unpredictable latency. Token costs that collapse production ROI.

Their answer is a context compiler that processes source data before queries happen. Task-specific knowledge artifacts built at ingestion time, not inference time. The same underlying data produces different artifacts for different agents. The product Pinecone is now shipping isn't an improvement to a vector database. It's a knowledge engine with vector search as one component inside it.

VectifyAI PageIndex
From a different direction: PageIndex drops vector similarity search entirely for long-document retrieval. Instead of embedding chunks, it builds a hierarchical tree index — essentially a structured table of contents — and uses LLM reasoning to navigate that tree at query time. The result: whole sections instead of arbitrary chunks. Tables intact. Arguments connected to their conclusions. For complex policy documents, technical specs, and long contracts — exactly the content that breaks classic RAG at the chunk boundary — that's a materially better approach.
SAP + Dremio Acquisition — pending Q3 2026
SAP's stated acquisition rationale is precise: enterprise AI stalls not because the models are wrong, but because the data isn't ready for agents — fragmented, locked in proprietary formats, stripped of the business context that makes it meaningful. Dremio's "Agentic Lakehouse" gives agents federated queries without ETL pipelines and a semantic layer so every agent draws from the same source of truth. Structured, governed, context-rich data access is the product. The query is the interface. You can't separate them.

Vector search doesn't disappear in any of these architectures. It gets demoted from the architecture to one component inside the architecture. The "vectors versus something else" debate is happening at the wrong layer.

03

7 Questions to Test Your Knowledge Layer

These separate a knowledge layer capable of supporting a production agent from a retrieval system that works in demos. Most teams are at two or three. That gap is where agent failures actually live.

  • 1 Can it deliver structured and unstructured data together? The account record and the policy document need to arrive in the same response. If your retrieval layer handles only one type, you're assembling context inside the model — which is where it goes wrong.
  • 2 Does it know the current version of a document? Policies change. A system that returns a superseded policy with high confidence is actively dangerous. Temporal awareness belongs in the knowledge layer, not the prompt.
  • 3 Does it enforce access control at retrieval time? The agent should never see data the requesting user can't see. Post-retrieval filtering is a leak surface. Permission checks belong at the query layer.
  • 4 Can it navigate document structure instead of returning a similar chunk? Section 7, paragraph 3 and a chunk about "exception clauses" are not the same thing. For long documents and policy trees, structure navigation is not optional.
  • 5 Does it produce a provenance trail? Every answer that can be acted on needs to be reconstructable. Field-level citations, source documents, confidence scores. Without this, root cause analysis after an error is archaeology.
  • 6 Does it support memory across sessions? A decision made in a previous run is context for the next one. An agent that starts cold every time rebuilds state that should already exist.
  • 7 Can the agent write back to it? A knowledge layer that only gets read from slowly diverges from reality. Agents that can log decisions, flag stale content, and register confirmed facts close the loop.
04

What Could Go Wrong

This architecture solves real problems. It also introduces new ones.

Overbuilding
The right answer to "our RAG isn't working" might be better chunking, not a full semantic data model. Do the failure triage first. Complexity added to the wrong layer makes debugging harder.
Fast-changing data
Pre-compiled knowledge artifacts are excellent for policy documents, stable reference data, and product catalogs. They're a mismatch for real-time data — an active CRM record, a live queue, a financial feed. Know which data changes faster than your compilation cycle before you architect around it.
Compliance surface
Detailed source citations are exactly what you want for debugging. They're also a detailed record of every data point an agent consulted when it made a consequential decision. In regulated environments, that trail has legal implications. Build it intentionally.
Semantic layer drift
A layer that adds business context needs to be maintained when the business changes. When the layer drifts from reality, you've introduced a failure that's harder to debug than a hallucination — because it looks authoritative.
Vendor lock-in
Switching LLMs is relatively cheap now. If your compiled knowledge artifacts are in a proprietary format, your switching cost moves to the data layer — where it's expensive and slow.

Three Artifacts — Paste Ready

These cover the three states you'll hit when working on retrieval. Copy and adapt.

Artifact 01
Retrieval Contract Spec
Define the context guarantee before you build the agent. If you can't fill this out, you're not ready to build.
RETRIEVAL CONTRACT — [Agent Name]
Version: 1.0

GUARANTEED CONTEXT  (must be present before agent acts)
Structured:   [entity types — e.g. account_record, user_permissions]
Unstructured: [document types — e.g. policy_document, meeting_log]
Temporal:     [version constraint — e.g. current as of query time]
Session:      [prior decisions from previous runs]

ACCESS CONTROL
Permission check: [at retrieval layer / at application layer — pick one]
Data scope:       [what requesting user context is allowed to see]

PROVENANCE
Citation level:       [field-level / document-level / none]
Confidence threshold: [minimum score — e.g. 0.80]
Conflict resolution:  [most recent / first-write wins / flag for review]

ON INCOMPLETE CONTEXT
If guaranteed context missing:       [halt + flag / proceed with logged assumption]
If temporal constraint unverifiable: [halt / proceed with stale warning]

WRITE-BACK
Agent may write:  [decisions / confirmations / flags / none]
Format:           [structured log / record update / session memory append]
Artifact 02
Failure Triage
Use when an agent produced a wrong answer. Find the actual failure point before you touch anything.
STEP 1 — Was the wrong answer in the retrieved context?
  YES → retrieval failure. Go to Step 2.
  NO  → generation failure. Prompt or model issue.
        Knowledge layer is not the problem.

STEP 2 — Was the right information retrievable?
  YES → wrong content selected. Check:
        chunk boundaries, version staleness, access control
        leaks, similarity threshold, structured data excluded.
  NO  → knowledge gap. Not in corpus, not ingested, or
        in a format that blocks retrieval (scanned PDF,
        locked table, meeting notes never logged).

STEP 3 — Was the context assembled correctly?
  YES → Go to Step 4.
  NO  → assembly failure. Check:
        structured + unstructured delivered together,
        session memory included,
        permissions enforced at retrieval layer.

STEP 4 — Was there a provenance trail?
  YES → Review it. Identify which source was over-weighted.
  NO  → Root cause analysis not possible.
        Add field-level citations before the next run.
        This is your new Step 0.

STEP 5 — Is this failure mode repeatable?
  YES → Systemic. Redesign the affected layer.
  NO  → Edge case. Log it, add regression test, monitor.

That's the shift. Vector search isn't going anywhere — but "we have a vector database" stopped being an architecture answer about six months ago. The actual answer is whether your knowledge layer can make and keep a retrieval contract with the agent before it starts acting.

The three artifacts above are where to start — not the destination.
