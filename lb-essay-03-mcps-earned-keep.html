The MCPs That Earned Their Keep

I've connected over a hundred MCPs. Three ran last month. The rest taught me what earning daily driver status actually takes.

The number in my bio is 244. That's the claude-code-plugins-plus catalog — a GitHub repository of Claude Code plugins I built for distribution. It's a product, not a description of what I personally run.

The number currently connected and authorized in claude.ai is somewhere over a hundred. Connected means I approved the OAuth handshake at some point and haven't revoked it. The list doesn't get shorter when I stop using something. There's no churn signal.

Three numbers. The third one is the essay.

Catalogued Is Not Called

A tool archaeology I ran in April 2026 verified every platform in the stack and landed on roughly thirty tools mastered and active at any time. Not a hundred. Not 244. Thirty. That number came from counting what I reached for without thinking — not what I'd technically authorized.

The gap between connected and mastered is the gap between "I can access this" and "I reach for it when the task comes up." One is infrastructure. The other is instinct. A hundred-plus MCPs are connected because connecting is cheap. Find a relevant server, click authorize, it goes in the list. That's thirty seconds and a decision I haven't revisited.

Connected means I approved the OAuth handshake and haven't revoked it. That's a different claim than daily driver. Daily driver means the tool is in the path of a task that happens repeatedly.

The April archaeology also surfaced the pattern that explains the thirty-to-three gap: most of the connected tools have a use case, but not a recurring use case. Supabase is in the active stack. I work in it weekly. But I reach it via dashboard and direct API — the MCP surface hasn't found the task that needs it yet. Connected. Not called.

Three Got Called

In the last thirty days, three MCPs were called in production sessions and produced something real. The rest produced OAuth records.

Base44 first. Every session involving a production app went through this MCP. SparkAcademy, Involuer, the AI Setup Audit tool, Velo — create entities, query records, update schemas, manage custom domains. Four or more sessions in the window, multiple calls per session. This is the app layer. No other MCP in the connected list touches more of the actual product.

Make second. One week old. Two live webhooks created in the first session: the lead capture automation for audit.flashfusion.co and the Load-Bearing newsletter trigger. The Make MCP had a scope issue during setup — scenarios_create came back "No approval received." It said why and where to fix it. Fixed in ten minutes. One week in and it already has two artifacts pointing to its endpoints.

HubSpot third. One session. Called search_crm_objects, got back real data — four contacts, three deals. Did what it was called for. One session is not daily driver evidence. It's "worked on first call," which is a lower bar than the other two. It clears it.

The One That Was Supposed to Run the Stack

n8n MCP.

This was the expected automation control plane. Sixty-five workflows in the instance. The MCP was supposed to mean: list what's running, check execution counts, build new scenarios from a conversation. That was the plan going in.

The MCP that was supposed to tell me whether my automations were running couldn't run itself. The sixty-five-workflow audit had to be done by parsing exported JSON files, because the control plane was dark.

Throughout every session in the thirty-day window, n8n MCP returned CONNECTION_ISSUE. Not an auth error with a specific fix. CONNECTION_ISSUE. No scenarios_create. No scenarios_get. No connections_list. The MCP designed to introspect and manage the automation layer couldn't be introspected itself.

The migration audit that led to moving from n8n to Make — sixty-five workflows parsed, nine kept, thirty-eight archived — was executed via a Python script against exported JSON files. Because the thing that should have provided that view couldn't provide it.

n8n is capable automation software. This is not a verdict on n8n. It's a verdict on the MCP connector during this window. But the distinction starts to blur when the control surface for a tool doesn't work and the tool's only value is what you can reach through that control surface. The migration wasn't because n8n broke. It was partly because Make's MCP worked, and n8n's didn't.

What Earns the Status

The pattern across the three that ran: each is in the direct path of a high-frequency task.

Base44 sits in the path of every production app session. There's no session involving a client-facing app that doesn't need entity operations. When the task happens every time you open Claude, the MCP calls happen automatically. Make sits in the path of the active automation work — live webhooks for current client pipelines. HubSpot sits in the path of the sales cycle.

The ninety-seven-plus connected but never called MCPs aren't bad tools. Most of them probably work fine. What they don't have is a high-frequency task they sit in the path of. The alignment between tool and recurring task is what generates calls. Without that alignment, the OAuth record just sits there, looking like a capability.

Daily driver status isn't granted by connecting. It's earned by being the thing that gets reached for when the task comes up — not once, and not because nothing else was available. Three times a week. Automatically. Before you've thought about it.

A hundred-plus connected. Three ran. The gap isn't a confession. It's the load test.

Gaps

• The April 2026 ~30 mastered figure is two months old. The n8n-to-Make migration and other stack changes since then mean the current active count may differ. Directionally right, not re-audited for this essay.

• "3 called in production" comes from 20 recent chat summaries. Some MCP calls may not be captured in session summaries — the actual count could be slightly higher. I don't have instrumented MCP call logs.

• The 97+ dark MCPs include tools used actively in the stack via non-MCP surfaces. Supabase and Vercel are used daily via dashboard and direct API. "Not called via MCP" is not the same as "not in the stack." The essay draws this distinction; the gap section makes it explicit.

• n8n's CONNECTION_ISSUE may be a fixable token scope problem rather than a structural failure. The essay doesn't diagnose the root cause — it documents the observable state during the window.

• The claude-code-plugins-plus 244 catalog deserves its own essay. This essay clarifies what it's not; what it actually is — a distribution catalog of community Claude Code plugins — is a separate story.
