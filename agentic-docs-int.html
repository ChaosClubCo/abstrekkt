Problem Statement

If you can't diagram it, you don't understand it well enough to build it

Agentic systems fail silently in ways monolithic apps don't. When a chain of LLM calls produces wrong output, the error rarely surfaces cleanly at a stack trace — it surfaces as a wrong business decision six steps downstream. The fix isn't better logging after the fact; it's forcing a shared mental model before you write the first node. Documentation isn't maintenance overhead. It's the primary design tool.

Pattern Analysis

The Five Pattern Primitives

Every agentic system is a composition of these five. Pattern selection determines your failure blast radius. X-axis is build complexity (implementation cost). Y-axis is execution latency. Bubble size is throughput ceiling at scale.

Selection guide: Reflection's high latency is a feature when precision is non-negotiable — don't optimize it away. Parallelization's throughput advantage carries coordination overhead that's easy to underestimate. Multi-agent is justified only when sub-agent specialization produces measurable quality lift; otherwise you're paying orchestration tax for nothing. With extended thinking available at the model level (Claude 4), some use cases that previously required a reflection loop can be collapsed to a single node with an explicit reasoning budget — profile before adding a loop.

Automated vs. Manual Documentation

Code-driven, text-based generation wins on every operational axis. The one gap is custom layout — which matters less than teams think. You don't need a beautiful diagram; you need a correct, versionable one.

Execution Protocol

Four-Step Documentation Loop

Run this before writing any agentic code. Skipping to implementation is how you end up with undocumented state machines only one person understands. Architecture drift is cheaper to fix on a whiteboard than in prod.

1

Decompose from ground-truth source

Query official docs, agreed architecture decision records, or confirmed specs — not memory, not Slack threads, not PRs. Break the problem into independent sub-tasks. If no definitive spec exists, write one before continuing. Undocumented assumptions don't become visible until they fail in prod.

2

Select the right primitive — then justify it

Routing for intent disambiguation. Parallelization for independent workstreams. Reflection when output quality has a measurable acceptance criterion. Extended thinking when single-node reasoning depth is sufficient and latency budget allows. If you can't justify the choice in one sentence, reconsider it.

3

Prompt with structural terminology

Describe architecture using precise pattern names: hub-and-spoke, fork-join, reflection-loop, routing-diamond. Vague prompts produce vague diagrams. The diagram should be fully derivable from the description alone by someone who hasn't seen the code.

4

Render and version alongside code

Use a text-based format (Mermaid, D2, Structurizr DSL) so diagrams live in the repo and diff cleanly in PRs. A diagram not in version control will drift. Treat stale diagrams the same as failing tests — they're a signal that something changed without review.

Failure mode to watch: Step 4 is where teams stop treating docs as first-class artifacts. The moment diagrams migrate to Confluence or Notion-only, they decouple from the code lifecycle. Architecture docs outside the repo aren't architecture docs — they're archaeology waiting to mislead someone.

Resilience Patterns

Graceful Degradation in Agentic Systems

Agentic failures are not the same as API failures. A 500 from a REST endpoint is obvious. An LLM node returning confident nonsense is invisible until it's downstream damage. Every pattern below exists to make failure explicit, bounded, and recoverable — not to pretend it won't happen.

Circuit Breaker
Stop calling what's failing
Track consecutive failures per node. After threshold (typically 3–5), open the circuit: skip calls, return fallback, alert. Half-open after a cooldown to test recovery. Prevents cascading degradation when one model is rate-limited or degraded.
States: CLOSED → OPEN → HALF-OPEN
Fallback Chain
Degrade deliberately, not randomly
Define an explicit priority stack per node. The chain must be documented and version-controlled. An undocumented fallback is a silent behavior change waiting to ship.
claude-opus-4-6 → claude-sonnet-4-6 → claude-haiku-4-5 → cache → FAIL
Bulkhead Isolation
Contain blast radius by design
Partition agents into independent execution pools. A failure in the summarization agent should not starve the routing agent of resources. Separate rate limit budgets, retry queues, and timeout contexts per pool.
pool_a: router | pool_b: writers | pool_c: validators
Timeout Budgets
Every call needs a deadline
Set per-node timeouts and a total chain budget. Budget down: if chain SLA is 30s, allocate per-node budgets summing to 25s and reserve 5s for orchestration overhead and retries.
chain_budget=30s | node_max=8s | retry_reserve=5s
Dead Letter Queue
Nothing fails silently into the void
When a node exhausts its retry budget, the full input payload goes to a DLQ — not just a log line. This enables replay, manual review, and failure-class analysis. DLQ depth is also your early-warning signal for prompt drift.
retry_exhausted → dlq.push({payload, trace_id, reason})
Retry w/ Backoff
Jitter is not optional
Exponential backoff with jitter prevents retry storms when a provider is rate-limiting. Without jitter, all retrying agents hit the same window simultaneously. Cap at 3–5 retries before DLQ — infinite retries consume your token budget and hide the real failure signal.
wait = min(2^attempt + jitter(0–1000ms), 30s)
The hierarchy: Retry → Fallback → Degrade → Fail explicitly. Skipping any level means you're either hiding failures or blowing up unnecessarily. Silent success on degraded output is the worst outcome — it looks like the system worked.

Observability

Log → Alert → Act — not just log

Logging without alert thresholds and defined responses is archaeology, not operations. Every signal below needs a corresponding action — not just a dashboard widget.

Signal What to Capture Alert Threshold Action
Node latency p50, p95, p99 per node — not just averages p95 > 2× baseline Check provider status; consider model downgrade
Token burn rate Tokens per chain run, cumulative hourly cost Cost > 150% daily budget by noon Kill low-priority chains; alert on-call
Fallback activation Which tier triggered, frequency, and originating node >5% of runs hitting tier 2+ Investigate primary model health; review prompt drift
Routing confidence Classification scores and near-miss branch events Confidence <70% on >10% of routing calls Retrain or tighten routing prompt; add eval test cases
DLQ depth Item count, failure reason distribution, oldest item age Any item >1hr old, or depth >50 Page on-call; review failure class before replay
Output quality drift Eval score per chain run vs. baseline (LLM-as-judge or rule-based) Score drops >10% vs. 7-day rolling avg Check model version, prompt version, input distribution shift
Thinking token usage Budget tokens consumed per extended-reasoning node; overage events >80% of budget on >20% of runs Review thinking budget ceiling; check prompt scope creep
Circuit breaker state OPEN/HALF-OPEN events with timestamp and triggering node Any OPEN state Immediate alert; do not rely on auto-recovery alone
Output quality drift is the hardest to catch — latency and cost are easy to instrument. A model silently producing worse outputs at the same speed and cost is invisible without an eval loop running continuously in prod. If you don't have LLM-as-judge or rule-based evals against live output, you're flying blind on the most important signal. The same applies to thinking token creep: extended reasoning that quietly expands its budget will surface as cost, not quality — and you'll miss it until the bill arrives.
