Problem Statement

If you can't diagram it, you don't understand it well enough to build it

Agentic systems fail silently in ways that monolithic apps don't. When a chain of LLM calls produces wrong output, the error rarely surfaces cleanly at a stack trace — it surfaces as a wrong business decision six steps downstream. The fix isn't better logging after the fact; it's forcing a shared mental model before you write the first node. Documentation isn't maintenance overhead. It's the primary design tool.

Pattern Analysis

The Five Pattern Primitives

Every agentic system is a composition of these five. Pattern selection determines your failure blast radius. Complexity on the x-axis is build cost — how hard it is to correctly implement the pattern. Latency on the y-axis is execution cost. Bubble size is throughput ceiling at scale.

Patterns: Prompt Chaining (low complexity, low latency), Routing (moderate, low), Parallelization (moderate, very low, high throughput), Reflection (moderate, high, precision), Multi-Agent (high, moderate, highest throughput).
Key insight: Reflection's high latency is a feature when precision is the requirement — don't optimize it away. Parallelization's large throughput comes with a coordination cost that's easy to underestimate. Multi-agent is only justified when sub-agent specialization produces measurable quality lift; otherwise you're paying orchestration tax for nothing.
Tooling Trade-offs

Automated vs. Manual Documentation

Automated generation (code-driven, text-based) wins on every operational axis. The one place it falls short is custom layout precision — which matters less than engineers think it does. You don't need a beautiful diagram, you need a correct one.

Automated wins on speed (95), scalability (80), version control (90). Manual wins on custom brand styling (95) and manual precision (95).

Note: Automated tooling introduces semantic drift risk. Output must be sanity-checked by someone who understands the system — not just reviewed for visual coherence.

Execution Protocol

Four-Step Documentation Loop

Run this before writing any agentic code. Skipping to implementation first is how you end up with undocumented state machines that only one person understands. Architecture drift is cheaper to fix on a whiteboard than in prod.

1

Decompose from ground-truth source

Query actual docs (not memory, not PRs) and break the problem into independent sub-tasks. Use a tool like Notebook Connector. If you can't find a definitive spec, write one before continuing.

2

Select the right primitive — then justify it

Routing for intent disambiguation. Parallelization for independent workstreams. Reflection when output quality has a measurable acceptance criterion. If you can't justify the choice in one sentence, reconsider it.

3

Prompt with structural terminology

Describe the architecture using precise pattern names (hub-and-spoke, fork-join, reflection loop). Vague prompts produce vague diagrams. The diagram should be derivable from the description alone by someone who hasn't seen your code.

4

Render and version alongside code

Use a text-based format (Mermaid, D2, Structurizr DSL) so diagrams live in the repo and diff cleanly in PRs. A diagram that's not version-controlled is a diagram that will drift. Treat stale diagrams the same as failing tests.

Failure mode to watch: Step 4 is where teams stop treating documentation as a first-class artifact. The moment diagrams move to Confluence or Notion-only, they decouple from the code lifecycle. Keep them in the repo.
Observability Requirement

What must be logged in every agentic system

EACH NODE CALL

Input/output, token count, latency, model version, temperature

ROUTING DECISIONS

Which branch was selected and the confidence or signal that drove it

FAILURE EVENTS

Retries, timeouts, fallbacks — with full upstream context attached

COST TRACKING

Token cost per chain run, not just per call — alerts before bills arrive
