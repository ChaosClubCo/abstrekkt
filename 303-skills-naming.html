I've written a library of 507 skills. The biggest lesson wasn't about the prompts. It was about the names.

The quiet failure mode

A skill gets written and added to the library. It's good work. The prompt is tight, the logic is sound, the frontmatter is valid. And then the model never calls it.

Not because the skill is wrong. Because the model doesn't know it's relevant.

What the model actually reads

In most skill systems the model does not read the full skill body when deciding whether to invoke. It reads two fields: the name and the description. That's the entire surface area for triggering.

Which means: if your name is engineering-workflow-v2-final and your description is "Helper for engineering things," your skill is dark matter. It exists in the library. It never fires.

Four rules that actually move the needle

Name for the job, not the tool. review-pr beats github-pr-helper. The user is doing a job; the name should match the job.

Descriptions start with a verb. "Review pull requests for security issues and style drift" is a trigger. "A tool for PR review" isn't.

Include the failure mode. The model routes better when the description names what this skill handles that others don't. "Catches RLS policy leaks that OWASP scanners miss" tells the model when to pick this one over the generic security skill.

Keywords earn their weight. Three keywords that match real user vocabulary beat thirty generic ones. "Threat model," "attack surface," "STRIDE" — not "security," "check," "review."

The test

Write a plausible user prompt that your skill should handle. Feed just the name, description, and keywords (no body) to the model, along with 10 other skills. Ask it to pick. If it doesn't pick yours, your metadata is broken.

That's the real evaluation loop. Everything else is hoping.
