The real test isn't whether a tool works. It's whether you keep reaching for it when the work gets hard.

Thesis
The real test of a tool isn't whether it works. It's whether you keep reaching for it when you have five minutes and actual work to do. Most tools fail that test quietly, over time, without a single dramatic failure. The folder where those tools collect is more honest than any benchmark.
Construction lens
Inventory audit, QC version: which tools stay on the production line vs. get moved to the tool crib? Not because they failed — because something else was already in your hand every time the task came up. Different failure mode. Same audit.
Hook draft
"I have a folder called 'tools to revisit.' That's where things go when they work fine but I keep using something else instead. The folder is six months old. Most things in it haven't moved."
Key beats
1. The distinction: stopped using ≠ failed — different claims, different honesty required. This matters for what the essay is allowed to say.
2. Specific retirements with honest reasons — n8n (partial), specific MCPs from the catalog, specific automation approach that added friction instead of removing it
3. The pattern across retirements — what they had in common that only became visible after the list got long enough
4. The tool I almost retired but didn't — specific, not invented. What changed.
5. What I'm watching now to see if it earns keep or joins the folder
Closer direction
The folder isn't a failure list. It's an honest accounting of the gap between what your workflow actually needed and what you thought it needed when you added the tool.
