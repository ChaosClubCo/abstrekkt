Pre-Flight: What I Check
Before I Ship an AI App

Eight things I look for on my own stack, written so I don't forget. Shared because the Moltbook breach made it clear how many people building right now don't know what to check.

I'm not a security professional. I'm an L1 service desk tech who has spent the last year building AI apps on the side — Supabase, Vercel, Next.js, Cursor, the usual stack. This list is what I check before I ship. It's not a complete guide. It's the eight failure modes I've actually seen burn people, including in places I worked, and the specific way I look for them.

If you're a vibe coder, a self-taught builder, an indie hacker shipping AI apps with tools you didn't fully understand a year ago — this is for you. If you're a credentialed security engineer, you'll find this incomplete and probably patronizing in places. That's fine; it's not for you. It's for the version of me from twelve months ago, who would have shipped most of what I'm warning about.

The Moltbook incident on January 31 — 1.5 million API keys and 35,000 emails exposed because Supabase Row Level Security was off — is the canonical example. The founder, by his own account, didn't write a single line of code. He still got the breach. The lesson isn't "vibe coders are dangerous." The lesson is that most of these tools default to insecure, and shipping fast on insecure defaults is what produces Moltbooks. The list below is mostly settings, not code. Run it.

§ The Eight Checks
  • Row Level Security on every table
  • No service-role keys in client code
  • CORS that isn't wide open
  • Auth tokens that are actually verified
  • Storage buckets you remember setting
  • Webhook signatures, not just webhook URLs
  • Rate limits on the surfaces that cost you
  • Logs that don't become a second database of PII
Check 01

Row Level Security on every table.

This is the Moltbook killer. Supabase ships with RLS available but disabled by default on new tables — meaning until you turn it on and write policies, every row in that table is readable by anyone with your project's anon key, which is sitting in your client bundle. Wiz found Moltbook's data within minutes of looking at the JavaScript.

Open every table in your Supabase dashboard. Confirm RLS is on. Then confirm the policies actually do what you think they do — RLS being on is not the same as RLS being correct. A policy like USING (true) is technically RLS but functionally identical to RLS off. Test from a real unauthenticated client (an Incognito window with your live URL, browser dev tools open). If your data comes back, you have a problem.

Failure mode
Direct database read of every user's data via the public anon key.
Time to verify
10 minutes for a small app, longer if you have many tables.
Check 02

No service-role keys in client code.

Anything prefixed NEXT_PUBLIC_, VITE_, or REACT_APP_ ships to every visitor's browser. That's the design. The trap is treating .env.local as a vault — it isn't, for any variable that gets prefixed for client use.

Build your production bundle locally. Open the resulting JavaScript files. Search for sk-, pk_live, eyJh (the JWT prefix), and the prefix patterns of every service you integrate with. If you find a service-role key, an OPENAI_API_KEY, a Stripe secret key, or anything labeled admin — that key is not actually private, hasn't been since you deployed, and needs to be rotated immediately and treated as compromised. Server-only secrets stay server-only by going through API routes, not by hoping a prefix protects them.

Failure mode
Anyone with the URL can use your API keys, drain your AI provider credit, send mail as you, or write to your database with admin privileges.
Time to verify
5 minutes with grep and a build output.
Check 03

CORS that isn't wide open.

Access-Control-Allow-Origin: * is the lazy default. It's also the setting that lets any site on the internet call your API from a logged-in user's browser, with that user's session. The browser will happily forward the cookies. The user won't know.

Lock CORS to your actual origins. Vercel, Next.js, and Supabase all support this in config. Include localhost:3000 while you're developing. Remove it before you ship. The audit isn't checking that you set CORS correctly once — it's checking that every endpoint actually inherits the setting. One forgotten API route with a permissive default is the same as the whole thing being permissive.

Failure mode
Cross-site request forgery against authenticated users; data exfiltration via malicious sites.
Time to verify
15 minutes to audit every route's CORS headers.
Check 04

Auth tokens that are actually verified.

A JWT in a request header doesn't mean anything if you don't verify the signature. The most common trap I've seen in vibe-coded apps is decoding the JWT to read the user ID, but never validating that the token is real. Anyone can craft a JWT with any user ID — what stops impersonation is the signature check against the auth provider's public key.

Use middleware that verifies, not just decodes. Supabase's auth.getUser() on the server side hits the auth server and validates. Clerk's auth() in a server component does the same. If you're hand-rolling auth — and I'd advise against that as a non-credentialed builder — you need to use a library like jose or jsonwebtoken, validate the signature against a JWKS endpoint, and check expiration and audience claims. Reading the sub claim from a decoded JWT and trusting it is not authentication. It's a comment.

Failure mode
Anyone can impersonate any user by crafting a JWT with that user's ID.
Time to verify
30 minutes to audit auth middleware on every protected route.
Check 05

Storage buckets you remember setting.

Supabase storage, S3, R2, Cloudinary — every one of them has a public/private toggle that does what it says, and every one has been the source of public breaches because someone forgot which bucket was which. Open every bucket you have. Confirm visibility. Confirm the URL pattern your app uses honors that visibility.

If you're using a private bucket but generating signed URLs that don't expire — or expire in a year — those URLs are public for as long as the file exists. Anyone who got the URL once still has access. Set short TTLs (an hour, a day) and rotate. If you can paste a file URL into an Incognito window and see the file without logging in, your private bucket is public.

Failure mode
Direct download of any user's uploaded files (avatars, attachments, generated content).
Time to verify
10 minutes per storage provider.
Check 06

Webhook signatures, not just webhook URLs.

Stripe, Slack, GitHub, Clerk, Resend, every payment processor and every event source — they all sign their webhooks with a secret you can verify. If you're not verifying signatures, your webhook URL is a public endpoint that anyone can hit with arbitrary data. Someone POSTing fake "payment succeeded" events to your Stripe webhook is the kind of thing that produces free upgrades for everyone who finds the URL.

Every framework has a verification primitive. Stripe's library has stripe.webhooks.constructEvent(); Slack has verifySlackRequest; GitHub gives you X-Hub-Signature-256. Use them at the top of the handler, before any other logic runs. If verification fails, return 401 and exit. Nobody adds this by default. It is also the single most common omission I have seen in vibe-coded apps that take payments.

Failure mode
Forged webhook events trigger paid-tier upgrades, role escalations, or fake confirmations.
Time to verify
10 minutes per webhook endpoint.
Check 07

Rate limits on the surfaces that cost you.

Login endpoints. Password reset endpoints. Any free-tier API route that hits a paid LLM. Anything that costs you money or grants someone access. The default for most frameworks is no rate limit, which is also no defense against brute force, credential stuffing, or someone deciding to run your OpenAI bill to a million dollars overnight.

Vercel has built-in rate limits via the Edge Config. Upstash Ratelimit is one import and three lines of code in a Next.js middleware. Cloudflare has rate limiting in front of any domain you point at it. Pick one and apply it to the three or four endpoints where someone could either drain your wallet or break in. Don't try to rate-limit everything from day one. Identify the surfaces that matter, harden those.

Failure mode
Unbounded LLM cost, brute-force account takeover, denial-of-service on free tiers.
Time to verify
30 minutes to identify and protect critical endpoints.
Check 08

Logs that don't become a second database of PII.

Whatever logging service you ship to is now a database of your users' data. Most apps end up shipping logs to a third-party SaaS — Logtail, Datadog, Axiom, Vercel's own log drain. If your logs leak, you've leaked. Whatever's in them.

Search your codebase for console.log statements that take user input, request bodies, or error objects with embedded data. Email addresses, full names, payment details, API tokens, raw request payloads — all of it ends up in logs by default if you're logging objects directly. Switch to structured logging with an allowlist of fields. logger.info({ userId, action }) instead of console.log("User signed up:", userObject). The discipline is harder than it sounds. The cleanup after a breach is harder than the discipline.

Failure mode
A logging-provider breach exposes your users' PII and API tokens; you become liable for whatever was in the logs.
Time to verify
1–2 hours of grep and refactoring.
§ If you find one

Don't panic. Most of these are settings, not code. The fix is usually one configuration change and a redeploy. The order of operations matters: rotate the keys before you fix the leak, because the keys are already compromised the moment you find them in the bundle.

Then assume the data has already been read. If your RLS was off and the table held PII, the right move is to notify users, not to hope the breach didn't happen yet. You don't know what you don't know — that's the whole point of this list. The defensible posture is: I found the gap, I closed it, I told the people whose data was exposed, and I changed the way I ship so this doesn't happen again.

None of this is rocket science. The pattern that produces Moltbooks isn't ignorance — most builders could figure this stuff out. It's velocity without a checklist. The cure isn't more credentials. It's a habit of running the list. If you're building AI apps without a CS degree, this list is yours. If you're building them with one, you should already be running something like it.
