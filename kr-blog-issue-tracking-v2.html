Issue Tracking Didn't Die.
It Got Promoted.

Kyle Rosebrook · May 8, 2026

In March, Karri Saarinen — the CEO of Linear, the company that spent a decade making issue tracking beautiful — declared the category dead. The argument was clean. Issue trackers were built for a world where human coordination was the bottleneck. Agents can read context directly. That translation step is friction. Eulogize it.

Then OpenAI shipped Symphony, and Linear became the literal control plane for the most ambitious autonomous coding system anyone had put in production. Teams using the integration reported significant jumps in shipped work. The thing Saarinen had just eulogized was now the substrate that made all of it function.

He was right about one thing. He was wrong about what that thing implied. And the gap between those two positions is where most enterprise software strategy is about to get repriced.

What He Got Right

The coordination layer is going away. The human updating a ticket so another human knows where something stands — that part is dead. Agents update their own state. They don't need a standup or a status field hand-typed by a developer who'd rather be coding.

Saarinen was looking at the thing that made issue trackers annoying — the manual overhead, the duplicate updates, the ceremony of keeping the board current — and correctly identified that agents eliminate it. That part of the thesis is sound.

What He Got Wrong

He conflated the coordination layer with the state layer. Those are different systems doing different jobs.

The coordination layer is the human work of keeping the tool current. That goes away. The state layer is the structured ground truth the coordination runs on top of. That doesn't go anywhere. It becomes more load-bearing, not less, because now something other than a human is reading it and acting on it without asking for clarification.

The translation step is going away. The state machine is staying. Those aren't the same thing.

Agents need external scaffolding for the same reason humans built it in the first place. No single participant — human or model — can hold the full state of a complex project in working memory. The ticket isn't the ceremony. The ticket is the persistent record that makes distributed coordination possible without everyone being in the same room at the same time.

The Five Properties That Make a Tool Agent Infrastructure

Not every software system is useful to an agent in the same way. Here's the actual diagnostic. Run it on anything in your stack.

  1. Structured state. Typed fields with defined transitions — not freeform text. An agent can read "status: blocked" and act on it. An agent cannot reliably parse "yeah so this is kind of on hold for now" from a comment thread.
  2. Audit history. A log of what changed, when, and who (or what) changed it. This is how an agent reconstructs context without a human briefing. Without history, every session starts from zero.
  3. Relationship modeling. This blocks that. This depends on that. This is a child of that. Agents traverse graphs. A flat list of tasks isn't a graph. A dependency tree is.
  4. API accessibility. Something other than a human can call it and get a structured response. Not a scraper. Not a webhook that fires into a void. An actual interface with predictable inputs and outputs.
  5. Permission scoping. The ability to define what an agent is allowed to read, write, and transition — without giving it keys to everything. This is what makes autonomous operation safe enough to actually deploy.

Issue trackers built for serious engineering teams have all five. They accumulated these properties over twenty-five years of solving the human coordination problem. Agents have the same coordination problem. The infrastructure transfers.

The UX Choice Was Actually a Data Choice

Linear became the best agent substrate by accident. Saarinen spent a decade obsessing over clean interfaces, keyboard shortcuts, fast load times, and eliminating every unnecessary field. He wasn't designing for agents. He was designing for humans who were exhausted by Jira.

But the discipline that produced a clean UX also produced clean data. Consistent status taxonomy. Predictable schema. Minimal freeform fields. Every decision that made Linear feel fast to a developer also made it legible to an agent. Design taste accidentally became data hygiene.

This changes how tool selection works going forward. The question isn't just whether your team likes the interface. It's whether the data the tool produces is structured enough for something other than a human to act on. Those have always been correlated. They are not the same question, and the gap between them is now consequential.

The Atlassian Angle

Jira is the anti-Linear. Configurable to the point of incoherence. Documentation written in 2011 that somehow still governs enterprise IT. I work service desk. I have opinions about Jira that I'll spare you.

And yet Atlassian is one of the more interesting companies in this transition, for exactly the same reason Linear is. Decades of enterprise workflow data locked into a schema that agents can actually read. The MCP server they've shipped, the Anthropic partnership, the acquisition speculation that has been cycling through the analyst community — all of it makes more sense when you stop treating Jira's installed base as technical debt and start treating it as a strategic AI asset.

The cruft is a UX liability. The data is an infrastructure asset. Both of those things are true at the same time. The market is slowly figuring out that the second one outweighs the first.

Which of Your Tools Survives

Five questions. Run them on every system in your stack.

The Agent Infrastructure Diagnostic

  • Does it store structured state — typed fields with defined transitions, not freeform notes?
  • Does it maintain history — a log of what changed, when, and what triggered the change?
  • Does it model relationships — this blocks that, this is a child of that?
  • Does it have an API something other than a human can call with a predictable response?
  • Does it have a permission model that can scope what an agent is allowed to do without giving it everything?

CRMs score high if the data is clean — most aren't. ERPs score high on structure, inconsistently on API accessibility. Service desks hit all five by design; this is what they were built for. Calendars have structured state but almost no relationship modeling. Spreadsheets are the trap: they look structured because they're in rows and columns, but the schema lives in the user's head, not the file. An agent reading a spreadsheet is guessing at context a human left implicit.

What I keep noticing: The tools that were "good enough" and never got replaced are often the ones with the cleanest underlying data. The fast-adopted shiny tool frequently optimized for the demo and neglected the audit trail. In an agentic stack, boring data hygiene beats impressive interfaces. That repricing is already happening.

What to Do About It

Three things, in order of actual priority.

Audit your data, not your interfaces. The question isn't whether your team likes the tool. It's whether the data it produces is structured enough to be agent-readable. If your CRM is 60% free-text notes from sales reps who write like they're texting, you don't have a CRM. You have an expensive place to store unstructured context no agent can reliably use.

Build the MCP layer before you migrate. If a system has the right data but no API an agent can call, an MCP server is usually weeks of work, not months. You're not changing the source of truth — you're giving agents a door into it. That's almost always faster than a migration and carries a fraction of the risk.

Treat schema discipline as a forward-looking decision. Every time someone adds a freeform field instead of a structured one, they're trading future agent leverage for present convenience. That's not always wrong. It should be a deliberate call, not a default. The teams that have clean schemas in 18 months will have a structural advantage over the ones that don't. Not because they planned for agents — because they had the discipline to build data worth acting on.

The Actual Lesson

Saarinen wasn't wrong about the direction. The coordination overhead — the human updating the ticket so the other human knows where things stand — that's going away. Agents update their own state. They close their own tickets. They don't need a status meeting.

He was wrong about the conclusion that follows from it. The coordination layer disappearing doesn't mean the state layer disappears with it. It means the state layer is now the thing that autonomous systems run on, which makes it more critical, not obsolete.

A bug tracker started this category in 1998. It survived because it was solving a real problem — distributed coordination without shared memory — that agents turn out to have in exactly the same form. The implementation changes. The underlying requirement doesn't.

Run the five questions on your stack. Figure out which of your tools just got promoted. The repricing is already underway.
