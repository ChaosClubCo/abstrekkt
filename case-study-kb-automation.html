The Problem

Institutional memory walks out at ticket close.

The pattern is universal in any service desk: a senior engineer solves a hard problem, the ticket resolves, the institutional memory of how the problem was solved evaporates by the next morning. Six months later, someone else solves the same problem from scratch.

This isn't a discipline failure. It's a cost-benefit failure. The manual effort of writing a knowledge base article exceeds the perceived value for an agent under active ticket load. The recovery path — going back later to write it up — never executes, because the value of a KB article degrades the further you get from the moment of solution.

The result is operational: repeat issues triaged from scratch every occurrence, onboarding with no searchable history, escalation decisions delayed for lack of prior art, knowledge lost to attrition.

The Build

Four steps. Inside their own cloud. No agent action required.

The pipeline executes on ticket resolution. The agent does nothing — the work is captured forward from the moment of solution, not recovered backward from a later writing session.

01 · Trigger
Webhook fires
Ticket resolves in the service desk → webhook posts to the client's API gateway endpoint. No new infrastructure.
02 · Hydrate
Pull full ticket
Lambda function fetches subject, agent notes, resolution text, conversation thread via REST API.
03 · Generate
Structured article
PII redacted, sanitized, then Claude generates Problem · Symptoms · Root Cause · Resolution · Prevention.
04 · Publish
Draft in KB
Article POSTed to the KB API. Visible to agents in 60–90 seconds. Draft status for 30 days before publish.

What separates this from a weekend script is the construction posture: the failure modes were designed in, not bolted on. Every guardrail below was specified before the first deploy.

  • PII Redaction
    Input text scrubbed before the LLM ever sees it. Email addresses, phone numbers, internal identifiers — stripped at the function layer.
  • Token Budget Caps
    Daily and monthly hard caps on LLM API calls. One adversarial input cannot drain the budget.
  • 30-Day Draft Gate
    Every generated article lands in Draft status for the first month. Human review before public publish. Quality bar, not vibes.
  • Dead-Letter Queue
    Webhook misses don't become silent data loss. Failed triggers route to a DLQ with daily audit reconciliation.
  • Idempotent Retry
    Exponential backoff on rate limits. Same ticket retriggered does not produce duplicate articles.
  • Data Residency
    All ticket content stays inside the client's own cloud account. Cleanest possible audit posture for SOC 2.

What held

This is what Construction over Recovery looks like at the service desk.

The interesting question isn't whether the build worked. It worked. The interesting question is why the wrong answer was the default — a $9,600/year vendor upsell that nobody wanted, for a tier the firm didn't operate, with a token cost on top that nobody could predict.

The default failed because it assumed the recovery posture: ship a feature, hope teams adopt it, recover later if they don't. The build worked because it took the construction posture: anticipate where the manual process fails, design the verification in at the moment of work, never trust the path that requires someone to come back later.

This is the same posture FlashFusion brings to every engagement. The work isn't to install AI on top of broken processes. The work is to identify the recovery paths that aren't executing — the KB article that never gets written, the report that never gets read, the handoff that never gets made — and replace them with construction paths that capture the work forward, before institutional memory has a chance to evaporate.
