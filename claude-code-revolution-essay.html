The Best Code Is the Code You Never Wrote

The unit of work in software just changed. Not the syntax — the job. What Claude Code, a hidden A/B test, and a no-code iOS app tell us about what actually matters now.

Kyle Rosebrook · Grayslake, Illinois · 8 min read

An investor named Anish Moonka shipped a production iOS app last week. Sanskrit transliterations. Streak tracking. Bilingual support. 10 Minute Gita, live on the App Store. Moonka doesn't know a single line of code. He orchestrated the Claude Code ecosystem in plain English and moved from intent to a live product in days.

Career engineers have a predictable reaction to that sentence. Something between anxiety and dismissal. Neither is useful. The anxiety assumes the wrong thing is under threat. The dismissal assumes the wrong thing is safe.

What actually changed is the unit of work. We're moving from "write code" to "orchestrate agents that write code." That sounds like a semantic difference. It isn't. It's a job description change.

IThe unit of work changed. Most people haven't.

The value in software engineering was never syntax. It was always the ability to decompose a complex problem, model system boundaries, anticipate failure modes, and make defensible tradeoffs under uncertainty. Syntax was the tax you paid to do that work.

That tax is getting cheaper. The underlying work isn't going anywhere.

If you can't model the system, the fact that the syntax writes itself doesn't help you. It just means your bad architecture ships faster. The engineers who win in this environment aren't the ones who write the most code. They're the ones who can most clearly define the problem — and then get out of the way while the agents solve it.

IIWhat Anthropic is testing — and not announcing.

Researchers digging into the binary strings of Claude Code found something that didn't make the press release.

Ultra Plan — marketed as a faster web UI for reviewing logic and leaving inline comments — is running server-controlled A/B/C tests on system prompt variants. Your production environment is a telemetry node. You never pick which planning mode runs. Anthropic does.

Three variants exist internally: a simple plan, a visual plan, and a three-subagent critique architecture. Plan acceptance rates determine which reasoning logic becomes the default in the next generation of models. The user-facing UI is the cover story. The actual product is the data.

The implication

IDEs are no longer just tools. They're dynamic experiments. The interface you use to build is also measuring how you build — and using that measurement to decide what engineering reasoning looks like next.

I'm not surfacing this to alarm anyone. I'm surfacing it because it tells you exactly where the sophistication is going — and what kind of engineering judgment it's trying to encode.

IIIThe architecture behind the curtain.

The third Ultra Plan variant — the Deep Plan — is where the shift from prompt engineering to system engineering becomes concrete. When it runs on something non-trivial, it doesn't guess at an implementation. It deploys four subagents with specific mandates:

  • Code Architect — reads the existing architecture and ensures the solution fits established system boundaries. Not imposing foreign conventions. Reading what's already there.
  • File Finder — locates every impacted file across the codebase. The "incomplete implementation" problem — where a model fixes one file and breaks three others — is the reason this agent exists.
  • Risk Identifier — surfaces edge cases, version conflicts, and blast radius. The stuff a single-model pass misses because it can't hold the full dependency graph in working memory.
  • Plan Reviewer — critiques the plan before a single line of code generates. Finds missing steps. Flags logic gaps. Runs the adversarial pass before anything ships.

That architecture is not a productivity tool. It's a quality gate. When migrating a complex dependency — say, tRPC v10 to v11 — the Deep Plan doesn't suggest code. It audits the blast radius first. The difference matters more than it sounds.

IVVibe for discovery. Spec for production.

The industry has named a pattern: vibe coding. Fast, intuition-based prompting that fuels rapid discovery. It has genuine value. It also breaks in production, consistently, in the same way every time.

In frameworks like Angular or Spring Boot, an AI-generated outdated dependency or security gap doesn't surface immediately. It surfaces three sprints later in a postmortem. The vibe was good. The spec was missing.

The rule that actually works: vibe for discovery, spec for production. That means five things before production code generates:

  • Define the goal short, crisp, and testable
  • Map system boundaries and data flow — even just ASCII
  • Define API contracts and version policies explicitly
  • Write the test suite before the agent writes the code
  • Audit output against the original spec, not against whether it compiles

None of that is new discipline. It's just engineering discipline that now applies to AI output instead of human output. The spec didn't become less important when the implementation got faster. It became more important.

VSkills are tribal knowledge, compressed.

The extension model evolved. Static plugins became dynamic SKILL.md files — agent skills that use progressive disclosure to manage context pressure. A skill file stays under 150 lines; complexity offloads to a references directory. The model sees what it needs for the current task, not the entire library.

There are reportedly over 1,900 validated skills in open-source marketplaces now. That's not a syntax library. That's a repository of production patterns — specific failure modes for specific tools, Ansible quirks, Vercel deployment edges, auth gotchas — written by people who hit the wall and documented the way through.

The engineers who build those skills aren't writing more code. They're encoding judgment. That's the job now.

The skill activation flow is simple: install, declare trigger phrases, activate on match, execute the specialized instruction set. What's not simple is knowing what judgment to encode in the first place. That comes from having shipped the thing and watched it break.

VIThe redundant coder and the better question.

Sridhar Vembu — founder of Zoho — said recently that those who rely solely on technological prowess (meaning: the ability to write syntax) are facing a redundant future. He offered two paths.

One is centralized power, AI as a control mechanism. The other is this: technology becomes so advanced it disappears. Invisible. Trivial. Like the digital watch — complex internal machinery, seamless in use. And that invisibility frees people to focus on what was always the actual work.

"Family, nature, soil, art, music, and faith," he said.

I'd add: the problem the loop was supposed to solve.

The reframe

In a world where the code writes itself, the most important engineering skill is being able to define — precisely and completely — what "working" means before anything generates.

∞What this actually means.

The technical barrier to building dropped to the floor. The engineering responsibility didn't move.

Someone still has to model the system. Someone still has to identify the blast radius. Someone still has to define what "working" means before the code generates — and hold the agents accountable to that definition when the output drifts.

Moonka shipped a production iOS app in days. That's real. What's also real: if the architecture was wrong, if the data model was incoherent, if the failure modes weren't thought through — the app would have shipped faster into its own problems. The agents don't catch what the engineer didn't specify.

The best code is the code you never had to write. The question is whether you know enough to tell the agents what not to build.
